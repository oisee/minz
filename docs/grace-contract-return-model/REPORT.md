# PFCCO: модель выбора совпадает с применяемой конвенцией возврата

База `33146966`. Подтверждено замечание Astra: greedy OptimizeContracts перебирал классы возврата, но ApplyContracts менял только параметры. PBQP уже использовал parameter-only кандидаты.

Минимальный пример: функция возвращает u8=37 по фиксированному контракту ClassCounter (B), но её вычисление имеет ClassAcc. До исправления greedy записывал в решение return=acc, ApplyContracts оставлял return=counter. Независимые VM и собранный Z80 возвращали правильные 37: это подтверждённая ошибка соответствия модели и применения, а не найденный miscompile. Модель обещала устранить адаптер, который реально оставался в ASM.

Исправление: production greedy использует тот же генератор parameter-only кандидатов, что PBQP; неиспользуемый генератор изменения возвращаемых классов удалён. ApplyContracts сохраняет прежнюю безопасную семантику: ABI возвратов и классы производящих инструкций не переписываются. Greedy остаётся стандартным решателем, PBQP не включён по умолчанию. Speed/Size цели не изменены.

Проверки:

- Регрессия выбранный return = применённый return для greedy и PBQP: PASS.
- Кандидаты сохраняют все три возвратных слота (u8 counter, u16 index, bool flag), сохраняя несколько параметрических альтернатив: PASS.
- Независимый MIR2 VM возвращает 37; собранный Z80 получает B=37, переносит в A, восстанавливает SP=f000. BIN до/после одинаковый: `3100f0cd098078f3763e2547c9`; 60 T с загрузкой SP, CALL/RET и DI/HALT. Решение теперь counter и совпадает с применённым counter.
- Весь `pkg/mir2`: PASS, 7.124 s, включая существующие контрактные, PBQP и backend тесты.

Число тактов в этом примере не улучшилось. Глобальная оптимальность greedy, полная точность unary/edge cost и полезность PFCCO на реальном корпусе этим не доказаны. Полный pipeline не запускался. Дальнейшая оптимизация возвратов требует согласованного изменения производящих классов, всех return sites и caller ABI; эта работа не подменена небезопасным ApplyContracts патчем.
