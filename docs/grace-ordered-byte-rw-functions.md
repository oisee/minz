# PGO: совместный выбор ordered-byte read/write функций

После `rd16` следующий горячий helper `wr16` тоже вычисляет два адреса.
Он записывает u8(value) в arr[base], затем u8(value/256) в arr[base+1],
где base:u16=index*2. Кандидат вводит один pointer и сохраняет две отдельные
byte stores. Исходные выражения значений вычисляются на прежних местах:
low перед первой записью, high — после неё перед второй.

Совместный prototype на неизменённом hashmap и тех же 36 последовательных
вызовах: **123708 T / 965 B**, вместо read-only **126680 T / 980 B**.
Это ещё 2972 T (2,35%) и 15 байт. От исходного **133994 T / 984 B**
суммарный выигрыш — 10286 T (7,68%) и 19 байт. Production API уже измерил все четыре сочетания для обоих режимов.

Прототип прошёл 133760 raw случаев для каждого варианта: все u16 индексы
на границах адресов, несколько значений и маленькие heap с полной проверкой
памяти после частичной ошибки. Все индексы и значения проверены не как полный
cross product 2^32: исчерпывающая часть связывает value с index, дополненная
граничными сочетаниями. Отдельная независимая проверка 360 actual Z80 вызовов
подтвердила точные low → high byte writes, не более одной записи на инструкцию,
отсутствие лишних чтений/записей и сохранность RAM вне двух адресов и стека.

Новый opt-in контракт использует отдельную typed policy с Kind и Enabled.
ID функции остаётся привязан к полному набору исходных файлов, ABI, телу
и происхождению statements по функции и пути. Read-only API сохраняет прежний
набор допустимых функций. Новый combined API считает все допустимые read/write
helper в одном лимите: максимум четыре функции и 16 измеренных вариантов.
Число вызовов helper из LoopProfile не выводится; профиль проверяет свежесть
контролируемого полного workload.

Доказательство должно сохранять порядок исходных value expressions, типы,
ABI, metadata, обычные функции и циклы. Происхождение двух Assign переносится
к соответствующим двум Store по точному пути. Wide store, перестановка записей,
изменение адреса/значения, неизвестный Kind, чужая policy и stale source должны
отклоняться до выбора. Одинаковое исчерпание произвольного лимита шагов raw VM
не заявляется; machine emulator с wrap RAM не доказывает raw heap traps.

Текущий API получил четыре фактических результата: original — 133994 T / 984 B;
write-only — 131022 T / 969 B; read-only — 126680 T / 980 B;
оба — 123708 T / 965 B. Production raw store domain прошёл 132044 случая
для каждого варианта. Дополнительная проверка публичного API на Z80 прошла
360 вызовов с точным порядком byte writes.

Финальный native CLI отдельно измерил все четыре кандидата для обоих режимов.
Оба выбрали совместный вариант с SHA256
`514b51a2cf0e26d8cb3f0ccfdb46122872c4860631b447cf8703a9b7d01325df`.
Числовой порядок masks может различаться между API и CLI, поскольку ID зависят
от пути исходного файла; каждое решение читается по typed Kind, а не по номеру mask.
Независимые portable host и typed JSON аудиторы подтвердили все сохранённые
кандидаты, полное состояние, побайтовые обращения и evidence/binary SHA256.

Общие HIR / MIR2 / Nanz / C89 прошли за 19.738 / 5.235 / 1.739 / 5.594 с;
CLI — 20.697 с. Showcase: те же 31 известное падение, новых нет.
Полный pipeline прошёл за 293.893 с. Бюджетная проверка заново
скомпилировала четыре варианта за 250.486 с и независимо собрала их: source,
ASM и BIN совпали с предыдущим этапом, размеры 344 / 344 / 232 / 344 байта.
Прежняя длинная машинная проверка применима к тем же бинарникам; повторный
её прогон не заявляется.
