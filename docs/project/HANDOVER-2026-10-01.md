## Что это за проект сегодня

MinZ — исследовательский toolchain для классических машин, прежде всего Z80. Основной современный язык — Nanz; C89/ObjC, Lanz, Lizp, Frill, PL/M, Pascal, ABAP и другие frontends имеют разную степень готовности. Общая рабочая граница — типизированный HIR и MIR2. Для host-исполнения используется `mzv`/MIR2 VM; для Z80 — PBQP allocation, Z80 codegen, `mza` и эмуляторы. CLI и библиотека могут идти разными маршрутами, поэтому в каждом тесте фиксировать фактически вызванный путь.

```text
Nanz / Lanz / Lizp / C / другие source frontends
    → typed HIR                  (pkg/hir)
    → MIR2 + passes + Verify     (pkg/mir2; Verify структурный)
    ├── MIR2 VM                  (mzv; быстрая проверка семантики)
    └── contracts / PBQP / Z80  (pkg/pipeline, pkg/mir2/z80codegen.go)
          → .a80 → mza → binary → mze/mzx/emulator

VIR: offline oracle/research; LIR/ISLE+WFC: experimental/opt-in с fallback.
Grace: альтернативные декларативные MIR2 passes по UseGrace, не default MZV path.
```

Сила проекта уже реальна: общий IR для разных языков, структурный verifier, compile-time metafunctions, typed buffer printing без runtime vtable, PFCCO/contract-aware codegen, специализированная аллокация и тестируемые примеры. Но «IR построен», «VM вернула ответ», «ASM собрался» и «бинарь правильно работает» — разные ступени. `mir2.Verify` проверяет блоки, определения регистров и некоторые инварианты, **не** смысл программы и не полную dominance-семантику. Старые документы могут описывать VIR как default или делать широкие claims без нынешнего runtime-gate; при конфликте смотреть текущий код и датированный тест.

## Подтверждённый blocker: B6, signed ordering на Z80

В [синтетическом HIR отчёте](../../reports/2026-10-01-HIR-MIR2-Synthetic-Oracle-RU.md) один и тот же `signed_less(a:i8,b:i8)` даёт в VM ожидаемую signed-семантику, а собранный Z80 — unsigned. Для `(0,-128)` VM возвращает 0, Z80 — 1; для `(-128,0)` наоборот. Сгенерированный фрагмент `CP C; JRS NC` использует carry после вычитания, то есть unsigned ordering. В `pkg/mir2/z80codegen.go` signed `CmpLt` и unsigned `CmpUlt` сводятся к одному condition code `C`. Это **подтверждённый wrong code** на backend-границе, P0 для correctness.

При первоначальном опыте было второе расхождение на вложенной `u8` арифметике. Оно оказалось ошибкой bootstrap теста: функция получила ABI `B/C`, а тест записал аргументы в `A/C`. После правильной загрузки регистров все 36 Z80 сравнений проходят. Будущий общий harness должен читать `Func.Contract.Params`/allocation, а не угадывать ABI по числу аргументов.

Исправление B6 нельзя ограничить заменой `C` на один другой Z80 flag: signed `<` после `CP` зависит от комбинации sign/overflow. Нужны тесты `i8/i16`, четыре ordering оператора, оба порядка аргументов, равенство и границы, использование результата как branch и как материализованного `bool`, затем assemble/emulator comparison. Если оптимизация flags или swap меняет представление, тестировать и её. До этого новые signed Z80 cases не маркировать pass/skip как якобы закрытые.

## Договор о доказательствах и диагностике

Для каждой ошибки сначала зафиксировать **слой первого расхождения**. Сравнивать конкретные наблюдения: возвращаемые битовые значения, trap, память, output, side effects и termination. Для чистых scalar функций достаточно value/trap; для указателей, I/O и циклов нет. «Same VM before/after» ловит часть ошибочных rewrites, но общий дефект VM и pass пропустит; независимый Go model либо другой эмулятор нужен там, где claim сильнее.

```text
source/frontends → typed HIR → MIR2 raw → MIR2 optimized → VM observation
                                                    ↓
                                  allocation/ABI → ASM → MZA → emulator observation
```

Ступени evidence: `parse` < `lower` < `Verify` < `VM+independent oracle` < `assemble` < `Z80 execute+oracle` < `repeatable release scenario`. Таблицы оптимальных инструкций требуют дополнительно формальных предпосылок и независимого replay; меньше байт или T-states без семантического равенства ничего не доказывает. Сохранять минимальный input, ревизию, режим, seed/hash внешних данных, expected/actual и exact command. CI skip считать неизвестностью, не успехом.

Для provenance не строить сейчас огромный граф «строка исходника → каждая инструкция»: HIR nodes ещё не несут полноценные spans, MIR2 `SrcFile/SrcLine` заполняются неполно, часть rewrites теряет след. Первым делом достаточно функции, pass/rule, компактного before/after IR и входа, который выявил проблему. Если реальные failures потребуют traceability, добавить IDs/source spans и mutation test атрибуции. [План V/L-идей](../mir2-verification-traceability.md) разделяет семантическую проверку и объяснение происхождения.

## План: дерево с приоритетами и критериями приёмки

Легенда: **P0** — блокирует доверие к результату; **P1** — следующая практическая ценность; **P2** — после correctness baseline; **P3** — исследование. **Q** — узкий quick win, **F** — фундаментальная серия, **E** — эксперимент. Порядок ниже — порядок допуска; не надо параллельно переписывать все слои.

```text
R. Надёжный HIR/MIR2/Z80 и измеримые инновации
├── R0 [P0 F] Зафиксировать воспроизводимый baseline
│   ├── R0.1 [Q] Пиновать базу, команды и чистый test manifest; сохранить known failures
│   ├── R0.2 [Q] Развести VM, compile/assemble, Z80 execute в отчётах CI
│   └── R0.3 [F] Расширять required gate только после чистого PASS; broad suite вести отдельно
├── R1 [P0 F] HIR → MIR2: семантический контракт
│   ├── R1.1 [done] 181 синтетический случай + Verify + независимые expected values
│   ├── R1.2 [P1 F] i16/u24/u32: arithmetic, signedness, shifts, overflow, traps
│   ├── R1.3 [P1 F] CFG joins, block args, loop-carried state, break/continue, calls/returns
│   ├── R1.4 [P1 F] ptr/index/array/struct/global: memory image до/после, bounds и alias
│   ├── R1.5 [P1 F] Raw vs optimized MIR2: per-pass comparison + negative mutation controls
│   └── R1.6 [P2 F] Матрица coverage по HIR node × type × observation × pass
├── R2 [P0 F] MIR2 → Z80: correctness (начать здесь)
│   ├── R2.1 = B6 [P0 Q→F] Signed i8/i16 ordering, branch и bool; VM/Z80 parity
│   ├── R2.2 [P0 F] ABI-aware dual-run harness: аргументы, returns, flags, clobbers
│   ├── R2.3 [P0 F] Calls, live values, parallel copies, cyclic moves, tail calls
│   ├── R2.4 [P0 F] Арифметика/ширины: div/mod, cast, 8/16/24/32, flags/carry
│   ├── R2.5 [P1 F] CFG/block args, memory/struct/pointer, spills, IX/IY legality
│   ├── R2.6 [P0 Q→F] Undefined labels/unsupported op → явная ошибка, не «успех»
│   └── R2.7 [P1 F] Один и тот же corpus raw/optimized → ASM/MZA/emulator
├── R3 [P1 F] Защитить трансформации и доказательность
│   ├── R3.1 [Q] Инвентарь production passes и их условий допуска (MZV ≠ Grace)
│   ├── R3.2 [F] Local before/after oracle; effects/memory/termination как наблюдения
│   ├── R3.3 [F] Grace/peephole: preconditions, flags, clobbers, proof-status metadata
│   └── R3.4 [P2 F] Trace events для реальных passes; full provenance только по нужде
├── R4 [P2 F/E] Делать инновационные оптимизации пригодными к production
│   ├── R4.1 [F] Benchmark protocol: одинаковая семантика, bytes, T-states, time, failures
│   ├── R4.2 [F] PFCCO/PBQP ablation и allocation legality на calls, aliases, flags
│   ├── R4.3 [E] alt-reg/EXX/HLH'L' против DEHL/HLIX: замер с полной ценой переходов
│   ├── R4.4 [E] Arithmetic tables/constant mul-div: declared domain + independent replay
│   ├── R4.5 [E] WFC/LIR/Grace: holdout corpus, hit/fallback/unknown и end-to-end parity
│   └── R4.6 [F] Артефакты GPU: schema/version/hash, witness rescore, deterministic IDs
├── R5 [P1→P2 F] Реальные программы как ортогональный gate
│   ├── R5.1 [P1] Nanz/C компактный CP/M smoke и реальный output
│   ├── R5.2 [P1] Z3 маленькие fixtures и state traces: тот же core VM ↔ Z80
│   ├── R5.3 [P2] Полный Zork через mzv как долгий host regression, не PR fast gate
│   ├── R5.4 [P2] Spectrum 128K banked story, memory budget, loader/display/input
│   └── R5.5 [P2] Новый release workflow: host CLI, checksums, license, tag dry-run
└── R6 [parked] Frontend feature work и новые targets
    ├── Разрешены correctness fixes и маленькие repro, нужные R1/R2/R5
    ├── Не начинать новые closures/DSL/targets без конкретного E2E blocker
    └── После R2 baseline пересмотреть по реальным программам и поддержке
```

**Definition of done:** R1-family проходит MIR2 Verify и независимый oracle с указанным набором типов/наблюдений. R2-family дополнительно компилируется, собирается и исполняется в эмуляторе с ABI, прочитанным из фактического contract. R3-pass имеет negative control, безопасные preconditions и диагностику при отказе. R4-оптимизация допускается только при **R2 parity + measurable hit count + ablation**; «нашли красивую последовательность» ещё не integration. R5-сценарий воспроизводим из чистого checkout/пинованного внешнего asset и содержит expected output/state. Любой timeout/unsupported/rejected artifact — отдельный статус, не pass.

## Инновации: что есть и как не потерять сильные стороны

- **PFCCO и PBQP** — уже на основном Z80 пути. Исследовательская ценность — межпроцедурные contracts и allocator-aware стоимость, но quality claim требует R4.1/R4.2 с равной семантикой и учётом адаптеров. `FuncTrace` хранит pass counts/backend/fallback/label warnings; это полезный локальный диагностический каркас, не сквозной source provenance.
- **VIR** выведен из production и сохранён как offline oracle. **LIR/ISLE+WFC** существует и может fallback в PBQP; факт наличия WFC-кода не означает, что production выдаёт его решение. Сравнивать на holdout после legality и error/fallback accounting. [Экосистемный аудит](../../reports/2026-09-19-Ecosystem-Audit-RU.md) отделяет MinZ, gpuforce и z80-optimizer.
- **Математические таблицы gpuforce/z80-optimizer** — потенциальный источник узких «островков оптимальности». Для `u8/i8/u16/i16` есть отдельные фрагменты, `u32` — частичная DEHL/HLH'L' библиотека, `u24/i24` и `u64/i64` не имеют здесь подтверждённой полной базы. Старые метки `verified`/`optimal` читать вместе с доменом: ISA, входные/живые регистры, carry, flags, clobbers, pool и cost model. При 3+ дополнительных live regs часть старых проверок sampled. [Разбор](../mir2-verification-traceability.md#adjacent-arithmetic-track-semantics-before-z80-optimality).
- **GPU artifacts** требуют согласованного witness/cost, алиасной модели и стабильного shape ID. Исторический глубокий аудит обнаружил mismatch/sparse-index bugs; не грузить таблицу в production только потому, что loader принимает header. Порядок K5/G7→G8→G9→G2→независимая проверка→G3 из [бэклога](BACKLOG.md) остаётся исследовательской очередью, не gate компилятора по умолчанию.
- **Grace/V/L traceability**: V-идея — явные proof obligations и независимое before/after; L-идея — объяснимое происхождение output. Семантический oracle раньше глобального line-level trace. Добавлять provenance локально там, где он сокращает поиск реального сбоя.

## Открытые границы за пределами ближайшего backend-среза

- Lanz/Lizp пока молча дают `u8` неизвестным identifiers/types, return type forward call зависит от порядка, scope/signed mixed arithmetic не закрыты. `u16` VM-regression пройден; Z80 для него — будущий dual-run. [Аудит](../../reports/2026-10-01-Lanz-Lizp-Frontend-Audit-RU.md).
- Nanz closures с escaping/captured runtime значениями не реализованы; признанные iterator fusion и static aliases не обобщать. `@print` имеет экспериментальные caller conventions. Не расширять это сейчас, кроме случая, когда реальный backend gate упирается в frontend.
- Z3: host MZV не memory-unlimited; VM host pointer ABI 16 бит, хоть story до ~128 KiB и PC шире. Terminal status/sound/error boundaries, долгий gameplay, ZX 128K banked build ещё открыты. Story/лицензии/эталон надо пиновать; внешний CZECH и полный Zork в PR gate не запускаются.
- Релиз: `mz`, `mza`, `mze`, `mzv` строятся в CI; остальные host CLI и target output formats не имеют общего release smoke. `main-archive` — историческая ветка, не dependency для сборки. Репозиторные gitlinks `corpus/intel80tools` и `examples/zvdb-minz` опциональны, проверять инициализацию отдельно.
- Старые статусные файлы и большая часть `BACKLOG.md` датированы более ранним состоянием. Историческое «PASS на старом checkout» — указатель для repro, не основание закрыть современную задачу. В частности, не переносить старые показатели полноты языков и оптимальности в README без команды на текущем commit.
