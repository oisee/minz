# ADR-0043: Demote VIR from production backend to offline oracle

**Status:** Accepted
**Date:** 2026-08-21
**Supersedes:** the "VIR is the default backend" position in `CLAUDE.md` §5
**Basis:** [Report 117](../../reports/2026-08-21-117-Solver-Architecture-Audit.md),
[Report 119](../../reports/2026-08-21-119-Language-and-Codegen-Audit.md)

---

## Context

`pkg/vir` is an 18,643-line backend that solves instruction selection and register allocation
jointly by generating SMT and shelling out to a `z3` binary. It was the compiler's default
(`--vir` defaulted to `true`) until this was reverted earlier today.

### What we measured

| Corpus | PBQP (now default) | VIR |
|---|---|---|
| `examples/c89` (39 files), Z80 asserts on the emulator | **37 pass / 2 fail** | 33 pass / 6 fail |
| `examples/abap` (30 files), assembles | **28** | **0** |

The repo's own `TestVIR_Assert_GCD` fails: `gcd(12,8)` returns 0. Nobody saw it because `pkg/vir`
takes ~25 minutes and `go test` gives up at 10.

Compile cost is the other half: 21 of 57 Nanz files take over 5 s, three exceed 60 s, and
`op_mul_u8_u8` did not terminate in 11 min 21 s.

### What we already decided, and did not implement

`reports/2026-04-08-Session-Report-EN.md` records two agents independently concluding that Z3
"breaks on any while/for with a parameter-bound loop counter", that it is "a cannon aimed at
sparrows", and resolving: *"Z3 parked as `--vir` flag, PBQP stays production default."*
`DefaultOptions` honoured that. The CLI flag did not. This ADR closes the gap deliberately rather
than by accident.

### The fact that unblocks the decision

**PFCCO — our strongest publishable asset — is not in VIR.** It is `pkg/mir2/contracts.go` (455
lines, greedy DP on the topologically-sorted call graph), it runs on the **default PBQP path**
(`ContractOpt: true` in `DefaultOptions()`, called at `pipeline.go:308` and `:639`), and
`research/abi-paper/FINDINGS.md` documents *that* implementation, citing `contracts.go` line
numbers throughout.

`pkg/vir/pfcco.go` is a separate Z3 reimplementation of the same idea whose encoding is broken:
it emits a bare `(ite …)` at SMT top level, z3 prints `unsupported`, and the bool-return cost term
is silently dropped. Its objective is also sparser than advertised — call-site cost only fires when
the argument happens to be a parameter of the caller.

**So retiring VIR does not touch the paper.**

---

## Decision

**Kill VIR as a backend. Keep the solver as an offline oracle. Do not delete it.**

1. The compiler no longer calls the VIR solver. The `--vir` flag is removed; the `if opt.UseVIR`
   branch leaves `pkg/pipeline`.
2. The solver becomes `cmd/vir-oracle`: given a module, it reports what an optimal allocation
   would be, for comparison against what the production path emitted.
3. `pkg/vir` is **split**. It is two packages wearing one name.

### The split

| Destination | Files | LOC | Why |
|---|---|---|---|
| **Stays as shared infrastructure** | `regalloc_table.go`, `z80.go`, `vir.go`, `mulopt.go`, `mul_table.go`, `enriched_reader.go`, `enriched_index.go`, `peephole_rules.go`, `gpu.go` | ~4,300 | Already imported by `cmd/mzv`, `cmd/mir2asm`, `cmd/gpu-bench` for tables and the machine description — not for Z3. This is also the substrate for Track A |
| **Moves to the oracle** | `pipeline.go` (4,943), `solver.go` (2,233), `bridge.go` (1,467), `cfgsolver.go` (1,278), `isle.go`, `vir_graph.go`, `inliner.go`, `intrinsics.go` | ~12,000 | The backend driver and the SMT encoding |
| **Kept, but quarantined** | `pfcco.go`, `pfcco_test.go` | ~520 | Broken encoding, and duplicates `mir2/contracts.go`. It is Phase 0 of `CodegenModule`, so removing it changes what the oracle computes — do it deliberately, not as part of the extraction. Until then the oracle's convention choices are not trustworthy |

## Why an oracle is worth keeping

This is not sentiment. Track A (retrieval-based codegen) has a hole that only an optimal solver
fills.

The GPU tables are generated by exhaustive search under **a hand-written heuristic cost function**
over a **fixed instruction schedule**. "Provably optimal" is therefore scoped to that model, and
the model is currently validated against itself. An independent SMT formulation that reaches the
same answer is real evidence; agreement between the GPU search and its own cost function is not.

In that role every objection to VIR evaporates:

- **Slow** — irrelevant offline. Minutes per function is fine for a checker run over a sample.
- **Needs an external `z3`** — a research tool may require a research dependency. A *compiler* may
  not.
- **Miscompiles** — an oracle that only reports allocations never emits code.

It also preserves the one idea in there that is genuinely Unison-class: per-instruction location
variables (`lv{vreg}_i{inst}`), which make live-range splitting a decision variable rather than a
post-pass. That is worth being able to point at.

## Alternatives rejected

**Keep it as a flagged backend** (status quo). 18.6K LOC on maintenance producing negative measured
value, and a 25-minute test package that demonstrably hides real failures. This is the option that
let `TestVIR_Assert_GCD` fail unnoticed.

**Delete it outright.** Defensible — git remembers — but it forfeits the independent check Track A
needs, leaving the tables validated only by the heuristic that produced them.

**Fix it to parity first.** A sprint or two to reach where PBQP already is. The roadmap puts solver
work last for exactly this reason.

---

## Consequences

- The compiler has no external-binary dependency on the code path. `z3` becomes a research-tool
  requirement, not a build or runtime one.
- `CLAUDE.md` §5's "-60% vs SDCC", "645/645 functions (100%)" and "non-leaf production" claims are
  retired with the backend. See Report 116 for why they were not supportable anyway.
- `pkg/vir` shrinks to ~4,300 lines of table and machine-description code with a clear job.
- We lose VIR's dual-mode adapter pricing from the shipping compiler. It was implemented and
  unusual; if it proves valuable it should be reimplemented against PBQP, where it can be measured.

## What to fix to make the oracle manageable, observable, understandable

The audits found the solver hard to reason about for reasons independent of whether it ships.
Extraction is the moment to fix them, and an oracle is a much better place to do so than a
backend.

### Manageable

1. **`pipeline.go` is 4,943 lines** — the largest file in the package and the backend driver. Most
   of it is emission and fallback plumbing that the oracle does not need. Extracting the solver
   should shed the majority of it rather than move it.
2. **Split the package** per the table above. Today `mzv` importing a table forces it to depend on
   an SMT backend.
3. **Resolve `pfcco.go`.** Two implementations of one idea, one of them broken, is the most
   expensive kind of duplication. Either fix the encoding (move the `(ite …)` inside the cost sum
   and broaden the call-site term beyond caller-params) or drop Phase 0 and let the oracle consume
   `mir2/contracts.go`'s result like the production path does. The second is probably right: an
   oracle that disagrees with production because it chose different conventions is measuring the
   wrong thing.
4. **`Z3Path` is hardcoded** to `/home/alice/miniconda3/bin/z3` (`lir/z3solve.go:33`, and the same
   pattern in vir). Use `exec.LookPath("z3")` and fail with a clear message.
5. **Run the pre-passes consistently.** `cfgsolver.go:179-180` calls `insertPreTieMoves` and
   `insertSaveMoves` but not `insertSpillReloads` or `coalesceVRegs`, both of which run in
   `solver.go`. Two code paths with different semantics is why multi-block behaviour differs from
   single-block.

### Observable

6. **No hit/miss counters exist anywhere.** The "91% O(1) coverage" figure is static eligibility
   analysis. An oracle whose entire purpose is comparison must count: table hits, misses, solver
   invocations, timeouts, and agreement/disagreement with the production path.
7. **Failures are silent.** Every table-load loop `continue`s on error, so a missing or misparsed
   file yields an empty table and a compiler that quietly does something else.
   `LoadEnrichedBinary` accepts a mismatched header, loads 2,052 of 156,506 records, and
   **returns success**. Validate, and fail loudly.
8. **z3 said `unsupported` and nothing noticed.** `pfcco.go:190`'s malformed term was dropped in
   silence. Treat any non-`sat`/`unsat` output from the solver as an error, and log the SMT script
   on failure.
9. **Emit a machine-readable comparison record** — per function: signature, table hit or miss,
   solver time, chosen locations, cost under the heuristic model, cost under the SMT model,
   agreement flag. That artifact *is* the oracle's product.

### Understandable

10. **Name things after what they do.** "VIR", "Dimension 2", "WFC" describe aspiration rather than
    mechanism; see Report 116. The oracle should say "SMT-based optimal allocator" and mean it.
11. **Write down the cost model in one place.** It currently exists three times — the GPU
    generator's C, the Go table annotator, and the SMT encoding — with no test that they agree.
    Divergence between them is invisible and would invalidate exactly the comparison the oracle
    exists to make.
12. **State the scope of "optimal" everywhere it appears.** Optimal *under this cost function, over
    this fixed schedule, ignoring sub-register aliasing*. The aliasing gap is real: the GPU
    allocator's `check_interference` is index equality, so `B` and `BC` are treated as disjoint.
13. **Give it one worked example end to end** — a function, its SMT, the solution, the emitted
    allocation, and the production path's answer beside it. The package has 26 files and no such
    document.
