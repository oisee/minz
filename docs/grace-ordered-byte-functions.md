# PGO: выбор функций с двумя упорядоченными byte loads

Горячая функция `rd16` в неизменённом `21_hashmap_test.nanz` вычисляла адрес
дважды: `arr[base]`, затем `arr[base+1]`, где `base:u16=idx*2`. Кандидат
сохраняет `base`, вводит один `ptr=arr+base` и читает два отдельных u8:
сначала `ptr`, затем `ptr+1`. Вычисление u16 результата сохраняется.

Умножение u16 на 2 даёт чётный offset от 0 до 65534; поэтому `base+1`
не переполняет логический offset. Переполнение физического адреса остаётся
одинаковым modulo 65536. Порядок двух чтений и частичная ошибка после первого
чтения входят в контракт. Это не замена на один широкий load.

Функции имеют отдельные идентификаторы `minz.function-sites/v1`: отпечаток
полного набора исходных файлов, имя, ABI и структурный отпечаток тела.
Frontend не выдаёт точную привязку целой функции к строке; такая строка
не выдумывается. Изменение любого исходного файла инвалидирует карту.
LoopSiteID не используется для обозначения функции. Карта также сохраняет
отдельный отпечаток происхождения по функции и пути statement: перестановка
привязок двух одинаковых statements не проходит повторную проверку factory.

Opt-in API измеряет все сочетания не более четырёх подходящих функций:
максимум 16 собранных вариантов. Даже не вызванные workload функции входят
в лимит и получают доказательство. LoopProfile используется для проверки
свежести и воспроизведения полного workload; он не объявляет число вызовов
helper. Победитель определяется фактическими T-states или размером бинарника.
При равной стоимости предпочитается меньше изменений.

Перед преобразованием и после компиляции проверяются типы и форма helper,
полный модуль, обычные функции, происхождение statement и связь обычных циклов
с исходником. Подмена policy, неизвестный ID даже со значением false,
оторванное происхождение и устаревший профиль должны отклоняться.
Поддержанные split обычных функций проверяются независимым normalizer;
доказательство не запускает преобразователь для получения ожидаемого AST.

Первые измерения production API на 36 последовательных вызовах исходного
hashmap: **133994 → 126680 T-states**, **984 → 980 байт**. Оба режима выбрали
кандидат. Независимый host сверил результаты, все 82 байта globals и каждый
побайтовый счётчик обращений в raw, postcompile и actual Z80.

Новый production контракт прошёл 131234 raw случая для каждого варианта;
отдельный прототип ранее прошёл 131612 случаев. Домены включают все u16 индексы,
переполнение адресов и частичные ошибки. Независимая машинная проверка
72 вызовов подтверждает последовательность ровно двух чтений low → high,
без дополнительных чтений и изменений RAM вне стека. В Z80 emulator память
оборачивается, поэтому машинная проверка не заявляет ошибки границ raw VM.
Одинаковое исчерпание произвольного лимита pure-expression шагов не заявляется.

Финальный CLI с `--hir-profile-joint --hir-profile-ordered-byte-functions`
и контролируемым workload отдельно проверил оба режима. SHA256 выбранного
бинарника: `31e686b05d328346cd092ee65a310c111de010c53c775d3c3cd8b92ccd016f11`.
Независимый saved-artifact host подтвердил все 36 вызовов обоих кандидатов;
отдельная typed JSON проверка подтвердила полный evidence SHA256 и все бинарники.

Полный parent pipeline прошёл за 280.522 с. HIR / MIR2 / C89 —
20.062 / 5.608 / 5.909 с; Nanz без отдельно измеренного showcase — 1.570 с;
CLI — 20.009 с. В showcase остались те же 31 известное падение, новых нет.
Исходный бинарник baseline побайтово совпадает с предыдущим этапом.
