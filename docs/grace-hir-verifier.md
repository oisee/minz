# HIR verification before Grace and lowering

10 октября 2026. Продолжение [типизированных указателей](grace-typed-pointers.md).

Добавлен `hir.Verify`: некорректный HIR отклоняется до формирования фактов Grace, дампа и lowering. После каждого переписывания Grace проверяет HIR, затем MIR2; при ошибке действие восстанавливает исходный узел или список операторов. Оба production-входа (`CompileHIRWithOptions`, `CompileHIRSteps`) проверяют вход и результат HIR-splitting.

## Где стоит проверка

```text
Source → HIR₀ → Verify HIR
                  ↓
            Grace: candidate rewrite
                  ↓
            Verify HIR → lower → Verify MIR2
                  ↓               ошибка: откат действия
                HIR₁
                  ↓
           split → Verify HIR → lower → MIR2 passes → Z80
```

Результат — более ранняя диагностика и дополнительный барьер для некорректных переписываний. Новый проход не является оптимизацией и не обещает уменьшения T-states или байтов.

## Что проверяется

| Контракт | Примеры отклонения |
|---|---|
| Структура | nil-функция, типизированный nil-узел, отсутствующее обязательное тело, циклическое дерево |
| Метаданные типов | отсутствующий тип, void в бинарной операции, несогласованный известный тип результата вызова |
| Имена | повторные функции/глобальные переменные/параметры; неизвестная переменная в обычной функции; переменная из соседней области |
| Управление | break/continue вне цикла, отсутствующая или повторная метка, повторный case |
| Память | неадресное основание загрузки, отрицательные stride/offset, нецелочисленный индекс |
| Типизированные указатели | доступ u8 через ^u16; подмена типа ссылки на локальный ^u16 |
| Вызовы и возвраты | арность вызова известной функции, длины tuple names/types, арность многозначного возврата |
| Lvalue | попытка записать в литерал или результат произвольного выражения |

Поддержаны существующие неявные преобразования ширины чисел, integer-адреса, raw pointers, разреженные инициализаторы массивов, объявление через `c = ...`, inline asm с именами физических регистров. Это описание текущего HIR, а не новая строгая спецификация языка.

## Реальный пробел, найденный проверкой

```nanz
fun f(n: u8) -> u16 {
    return range(n..0).fold(0, |acc: u16, i: u8| {
        return acc + i
    })
}
```

Раньше вызов fold непосредственно в return имел HIR-тип `void`; lowering самостоятельно выводил тип аккумулятора. Теперь post-parse разрешение типов учитывает сигнатуры поднятых лямбд и записывает результат callback (`u16`) в вызов fold/reduce. Также исправлена область типов при разборе лямбды: её параметры теперь затеняют внешние имена с собственными объявленными типами. Раньше `acc: u16` в теле мог получить `u8`. Тест проверяет тип и независимый ожидаемый результат `f(255) == 32640` на MIR2 VM. Уже существующие range/pipe тесты проверяют и Z80-код.

## Проверки и ограничения

Основные пакеты HIR, MIR2, pipeline и Nanz проходят (`-skip ^TestShowcaseCompileAssemble$`, без ослабления остальных проверок). Отдельный showcase compile/assemble: те же 32 падающих случая, что на предыдущей версии; новых падений нет. Логи находятся в [артефактах](grace-hir-verifier-artifacts/tests.txt).

Это первая версия верификатора, а не доказательство типовой корректности всего HIR. В частности:

1. У поднятых `lambda_*` нет явного списка захватов. Свободные переменные там разрешены; безопасность захвата и встраивания этим проходом не доказана.
2. Intrinsics, вызовы через локальные aliases и косвенные вызовы не имеют полного типизированного контракта в HIR. Для неразрешённого имени вызова проверяются аргументы как узлы, но не существование целевой функции.
3. Raw/integer адреса сохраняют старые правила совместимости. Структурные значения и адреса структур пока недостаточно разделены. Полное соответствие VarRef объявлению, типы всех аргументов вызова и все преобразования не проверяются.
4. Нет доказательства возврата на всех путях, definite assignment при goto, корректности эффектов inline asm, layout всех полей структур или эквивалентности преобразований.
5. Найден отдельный пробел range-fold: текущий `range(0..n).fold` передаёт callback значения n..1, а не 0..n−1. Для сложения при n=5 получается 15 вместо 10. Пробник [до изменений](grace-hir-verifier-artifacts/range-fold-baseline.txt) и [сейчас](grace-hir-verifier-artifacts/range-fold-current.txt) даёт одинаковый результат. Это вопрос lowering итераторов, в этом изменении он не исправлен; тест 16-битного аккумулятора использует явно обратный `range(n..0)`.
6. Проверка структуры не заменяет дифференциальные VM/native тесты. PGO-профиль всё ещё не является доказательством; сборщик профиля и сертификаты PGO остаются отдельной запланированной работой.

Ближайшая задача — исправить порядок и границы forward range-fold. Затем — явные захваты и сигнатуры callable/intrinsic в HIR, чтобы убрать исключения в проверке имён и типов. После этого профиль может выбирать кандидатов Grace, а проверка и fallback — обеспечивать корректность.
