# Z80: u32 spill-память и сохранение через вызов

Исправлены три ошибки production backend, найденные на `zvm.nanz` и сведённые
к независимым небольшим проверкам. Работа основана на `196bb487`.

- Caller spill snapshot принимал только 1/2 байта и отказывал для `u32`.
  Теперь 3/4 байта сохраняются несколькими словами на стеке и восстанавливаются
  в обратном порядке. HL и AF сохраняют уже полученный результат вызова.
- Wide load/store считал spill label регистром: генерировал `LD _spill..., (HL)`
  и неподдерживаемые `LD (DE),L`/`LD L,(BC)`. Более серьёзно, `EXX` переключал
  адресный регистр вместе с верхним словом значения. Теперь адрес фиксируется
  в сохранённом IX; каждый byte проходит через сохранённый A. Работают memory
  spill, main/shadow HL/DE/BC, совпадение пары значения и адреса, spilled pointer.
  Узкий исходник записи расширяется нулями до ширины памяти.
- Живой wide register через CALL сохранялся только в main bank. Теперь дополнительно
  сохраняется его shadow pair; обе половины восстанавливаются после получения
  результата вызова. Это отдельно проверено для HL, DE и BC.

Семантика u32 и EXX: Nanz Language Book v7 §§3.2 и 3.4; прямые адреса §2.15.
Ожидаемые результаты рассчитывает Go `uint32` по модулю 2^32, адресные byte
доступы — по модулю 65536. Эталон не выводится из сравнения VM с Z80.

## Проверки

- 672 случая memory: u24/u32 × 6 адресных homes × 4 value homes × 7 значений ×
  адреса 0x6000/0xffff. У shadow pointers намеренно другие значения; проверены
  все байты, little-endian и переход через конец памяти. Каждая VM и каждый
  assembled Z80 BIN сравниваются с независимым ожидаемым значением.
- 32 случая CALL: spill/HL/DE/BC × 8 значений. Callee намеренно портит обе
  половины caller home, возвращает 0x10003. Результат — `input+0x10003`
  с переполнением. VM исполняет тот же MIR с семантическим callee, Z80 —
  настоящий CALL и восстановление; исходный SP=0xfff0 сохраняется.
- Реальный Nanz `run_u32` через весь production pipeline: mutable global,
  вызов, u32 load/add/store, 4294967294+65539=65537. VM и native RAM совпадают;
  native заканчивает на исходном PC возврата 0x7000 со SP=0xfff2.
- Полный пакет MIR2 PASS; bounded memory-host binding/lifecycle tests PASS.

Дескрипторы memory-host certificate для 3/4-байтных CALL spill остаются явно
неподдерживаемыми: существующий resolver принимает 1/2 байта. Native backend
fix не расширяет сертификат или host runtime неявно.

## Граница ZVM

До исправления ZVM падал в pipeline: `caller spill save: unsupported width 4`,
а валидатор также показывал некорректные wide инструкции. После исправлений
он проходит backend без этих ошибок и достигает assembler, где сверхдлинная
DB строка вызывает `bufio.Scanner: token too long`. Причина данных в исходнике:
`global story: [u8; 131072]`, то есть 128 КиБ при 16-битном Z80 адресном пространстве.
Координатор отдельно добавляет явный отказ для превышения native памяти.

Этот результат **не доказывает native исполнение Zork/ZVM**: программа требует
host file runtime и другой модели адресации больших story. Размер массива не
уменьшался, источник не пропускался, валидатор не ослаблялся. Исключение ZVM
остаётся до решения о целевом memory model, координатор обновляет его причину.

Дополнительно production тест обнаружил потерю scalar global initializer u32
во frontend; координатор исправляет parser отдельно. Здесь исходник задаёт
значение runtime assignment, проверяя именно wide backend.
