# Grace PGO: constant-if вместе с hoist по source loop

`MeasureInvariantSiteRuleVariantSets` пересекает два module-wide выбора constant-if с независимыми скалярными hoist по исходным циклам. Четыре наблюдавшихся допустимых цикла дают максимум32 кандидата. Решение о допустимости берётся из исходного proof; профиль сообщает исполнение и стоимость. Pointer choices здесь остаются original. Текущий pointer proof принимает только точный u8 sum из двух statements, а scalar proof — u16 addition, поэтому эти два распознавателя сейчас выбирают разные формы циклов. Следующий joint поиск должен явно проверить отсутствие пересечения исходных sites и общий cap; при расширении proof для одного цикла потребуется контракт композиции.

Сначала идут constant-if off и все scalar маски, затем constant-if on и те же маски. Baseline all-off выигрывает равенство; победитель — строго минимальные такты workload или размер модуля. Возвращается именно измеренный Steps/Binary. Прежний `MeasureInvariantSiteVariantSets` сохраняет16-кандидатный режим и evidence v1. Новый schema `minz.invariant-site-rule-variant-sets/v2` связывает SHA256 с явными `rule_policy`, `requested_site_policy`, всеми кандидатами и индексом победителя.

Контракт проверок сохранён: preflight свежих независимых HIR, source/workload compatibility, повтор профиля с отказом при поддельных counts/guards; после первого Grace и после компиляции — точное применение каждого запроса и отсутствие оставшихся допустимых выражений. Constant-if может исчерпать бюджет раньше hoist; такой набор вызывает отказ всей операции, а не выдачу непроверенного или частично применённого варианта. Тест со100 ветвлениями подтверждает этот отказ. Переписывания не получают дополнительных разрешений из профиля.

Каждый кандидат исполняется на raw MIR VM и собранном Z80 с возвратами и состоянием после каждого вызова. Opt-in exact access сравнивает число чтений/записей объявленных байтов. Политика проверяется на всех восьми масках двух скалярных циклов, conditional исходниках с4/6параметрами, zero trips, границе32 кандидата/33 fresh modules и превышении cap. Проверяется повторное исполнение retained binary.

На полном неизменном `grace_weighted_checksum.nanz` проходят30 вызовов с длинами0/1/5/16/64/255, независимыми арифметическими результатами, persistent globals/resources и exact byte accesses. Оба режима выбирают hoist-only:1166563T/168B→475239T/116B. Это прежний подтверждённый выигрыш; новый поиск не даёт дополнительного ускорения на этом исходнике. Два scalar helper loops с literal branch дают155625T/131B→45989T/63B, winner mask3; constant-if варианты равны по стоимости и проигрывают раннему кандидату.

CLI: добавьте `--hir-profile-site-rules` к `--hir-profile-joint --hir-profile-invariant-sites --hir-profile-auto DIR --hir-profile-auto-workload FILE`. Новый флаг требует per-site режима, который по-прежнему несовместим с module-wide `--hir-profile-independent-rules`.
