# Fold: сохранение callback и стадий, VM ↔ Z80

10 октября 2026. Продолжение [HIR verifier](grace-hir-verifier.md). Исправления работают в общем production-пути, с HIR Grace и без него.

## Исправление предыдущего вывода

В прошлом отчёте я ошибочно назвал `range(0..5).fold(0, add)` с результатом 15 багом. [Nanz Language Book v7, глава 6](Nanz_Language_Book_v7.md) явно определяет countdown: элементы равны 5,4,3,2,1. Это намеренная семантика, а не обычный полуоткрытый интервал. Она сохранена; тест с callback `acc*3+x` проверяет порядок, а не только сумму. Старый probe с «expected 10» использовал неверный оракул.

Уточнены противоречивые комментарии HIR/lowering/parser. Это правка описания, без изменения границ или порядка range.

## Три реальных исправления

1. **Не терять префикс callback.** `extractReturnExpr` принимал последний return из многооператорного тела. Теперь он извлекает выражение только из тела, полностью состоящего из одного return. Прочие callback вызываются целиком, сохраняя записи, локальные переменные и управление. Fallback сохраняет также арность acc-only callback.
2. **Выполнять map/filter перед fold.** Range-fold пропускал фильтры; memory-fold пропускал все распознанные стадии. Общая сборка тела сохраняет порядок: map вычисляет новое значение, filter условно выполняет оставшийся суффикс цепочки. Отклонённый элемент не вызывает следующие стадии или fold callback. Нет continue, который обходил бы неявный decrement DJNZ.
3. **Сохранять живой A на Z80.** Неконстантная запись байта по глобальному адресу загружала значение в A и уничтожала другое живое значение. Теперь этот fast path сохраняет AF, когда A жив после записи и содержит другое значение, затем восстанавливает AF. Для случаев без такой зависимости сохранение не добавляется.

## Сквозной пример

```nanz
global hits: u8
fun callback(acc: u8, x: u8) -> u8 {
    hits = hits + 1
    return acc + x
}
fun test(n: u8) -> u8 {
    hits = 0
    let sum = range(0..n).fold(0, callback)
    return sum + hits * 16
}
```

При n=5 независимый ответ: сумма 15, hits=5, результат 95 (арифметика u8). База `c1b381ee` возвращала 15 на сырой MIR2 VM: обновление hits было выброшено. После исправления HIR lowering VM возвращала 95, но Z80 ещё возвращал 86; это выявило отдельный дефект записи через A. После обеих правок VM и native возвращают 95.

```text
callback { prefix; return expr }
         ↓
HIR fold lowering: вызов целого callback
         ↓
MIR2: call + load/store effects + DJNZ
         ↓
Z80 direct store: PUSH AF → LD A,value → LD (symbol),A → POP AF
         ↓
независимый оракул = raw MIR2 VM = production Z80 emulator
```

## Измеренные результаты

Все числа ниже — n=5, включая функцию с callback и глобальным счётчиком. Байты включают assembly модуля и сгенерированное хранилище; T-states измерены от входа test до возврата, без bootstrap. Это цена корректного кода, а не ускорение относительно ошибочной базы.

| Случай | База: raw VM | Исправлено: VM и Z80 | Байты | T-states |
|---|---:|---:|---:|---:|
| callback с записью hits | 15 | 95 | 67 | 906 |
| filter → map → fold | 100 | 63 | 106 | 978 |
| map → filter → fold | 100 | 95 | 106 | 1318 |
| два filter с эффектом второго | 15 | 55 | 123 | 1118 |
| filter отклоняет всё, init=7 | 22 | 7 | 36 | 303 |
| memory filter → map → fold | 15 | 63 | 146 | 2000 |

В варианте counter-order результат и код сохранены: 35, 32 байта, 228 T-states. Значения одинаковы с HIR Grace и без него.

## Проверка и границы

Новый тест содержит 10 сценариев: префикс callback, локальная переменная, acc-only callback, порядок счётчика, перестановка стадий, короткое замыкание двух фильтров, пустой range, отбрасывание всех элементов, memory-fold. Для префикса и порядка дополнительно n=0,1,255. Всего **32 варианта**, каждый проверяет сырой MIR2 на VM и production-код на Z80 с независимым ожидаемым ответом. n передаётся параметром, чтобы компилятор не вычислил весь range заранее.

HIR, MIR2, pipeline, Nanz unit tests проходят. В отдельном showcase остаются те же 32 падающих случая; новых нет. [Полный лог](grace-fold-artifacts/tests.txt), [dual-VM и измерения](grace-fold-artifacts/dual-vm-tests.txt), [контроль на базе](grace-fold-artifacts/baseline-tests.txt).

Это исправление корректности общего lowering/backend, а не новые правила Grace. Проверки не доказывают все формы iterator lowering: сложные захваты лямбд, изменение типа элемента в map, широкие счётчики и остальные формы forEach требуют самостоятельного аудита. LLM-less PGO остаётся следующим архитектурным этапом, не реализованным этим изменением.
