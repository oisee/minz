# Карта исполняемого корпуса: точные файлы и границы доказательств

Основание: `ee21cae8`. В корпусе остаются **все 193 точных пути** из `examples/` и `reports/showcase-src/`. Предыдущая карта учитывала только 11 недавно добавленных проверок и пропускала существенные существующие проверки парсера, HashMap и PGO. Исправлена карта, а не сужено обещание корпуса.

Текущий результат — **22 файла с независимым оракулом на VM и собранном Z80**, для перечисленных функций и ограниченных нагрузок. Это не 22 полностью проверенных приложения и не утверждение о поведении всех 193 программ. Генератор сохраняет SHA256 исходника, точные функции, импорт/extern/inline ASM, ожидания исходника, рассмотренные тесты с SHA256 файлов и отдельный индекс ссылок из всех Go-тестов репозитория.

| Статус | Точных путей |
|---|---:|
| Независимое поведение VM/Z80 на названной нагрузке | 22 |
| Нужна независимая исполняемая нагрузка | 112 |
| Нужен аудит исполняемого inline ASM и машины | 32 |
| Нужна реализация достижимого внешнего runtime | 21 |
| Agon eZ80/MOS/VDP | 5 |
| ZVM: host story 128 KiB, отдельная модель памяти | 1 |
| Всего | 193 |

83 файла объявляют `main`, 110 — только вызываемые функции. 69 содержат ожидания/assert. Это структура точек входа, не классификация «можно исключить из native обещания». Все 193 содержат функции, поэтому автоматически назвать оставшиеся файлы библиотеками было бы неправильно. Импортированная библиотека, платформа и интерактивность требуют проверки конкретного пути вызовов. 42 пути имеют ссылки из существующих Go-тестов; ссылка, одинаковое имя файла и PASS сборки не становятся доказательством native поведения.

Точные имена тестов, их SHA256, условия и relation к исходнику — в `catalog.json`. Повторный запуск четырёх больших baseline-тестов прошёл за 4.731 s (`existing-major-reruns.txt`). Восемь остальных рассмотренных тестов, включая parser/HashMap heldout, прошли за 32.925 s (`reconciled-reruns.txt`). Это текущие запуски на базе, а не перенос исторического результата по одному имени.

## Новая крупная область: stateful BufStream

`examples/nanz/30_stream_test.nanz` теперь имеет `TestShowcaseBufStreamNativeCapacityModel`. Оригинальные `bufstream_init` и `bufstream_write_u8` сохраняются. HIR-драйвер задаёт входную память и выполняет 70 записей при каждой ёмкости 0, 1, 3, 63, 64. Независимый оракул проверяет **все 64 байта буфера и 6 байтов дескриптора**, в том числе отбрасывание переполнения, неизменный хвост, pos/cap и реально перемещённый адрес буфера. Байтовая последовательность включает 0x00/0xff. Native выполнение обязано вернуться на исходный PC с восстановленным SP.

Это 350 записей, пять независимых состояний VM/Z80. ASM и BIN каждой ёмкости сохранены. Семантика основана на индексируемых типизированных указателях Book v7 §2.6/§3.3 и описанном BufStream в разделе «Stream Abstraction». Сам файл явно хранит дескриптор `[buf_ptr:2][pos:2][cap:2]` и условие `pos < cap`. Тест проверяет эту inline реализацию; импорт `stdlib/core/stream.nanz`, NullStream и Stdout не выдаются за покрытые.

Уже рассмотренные 11 файлов сохранены: LUT popcount всех 256 байтов, FSM с таблицей переходов, Arena/OOM/reset/сплит и состояние памяти, Lizp crypto, три Lizp ZX экрана целиком, Pascal bubble sort/records/sieve и PLM арифметика. Для Pascal вывод BDOS отделён от проверяемой вычислительной части; для ZX проверена RAM, не ULA или реальное железо.

## CP/M: что именно было исполнено

Исходный `self_lanz_parser.nanz` и derived CString `main` — разные утверждения. Существующий final-e518 compile-only README не является конечным доказательством исполнения. Существующее **фактическое** доказательство находится в `docs/grace-cpm-memory-capture/independent-review/README.md` и его `result.json`/manifest: один сохранённый MZE CP/M capture, COM SHA256 `087a9c7376591a82169b963891493ab6389cf26ebab728ef08a63e7664c73112`, 2574 байта, derived source SHA256 `574cef717965dbe6fcf6937ae35935b7b7e26f2051e49e7862d1826cff76f42d`.

Независимая модель проверила 135 байтов stdout, все 17 узлов (136 байтов), 24 intern байта, 10 globals, status, SP, canaries и неизменную часть COM. Auditor проверяет сохранённое состояние и не запускает CPU повторно. Это эмуляция с существующим BDOS, не реальная CP/M машина; Go BDOS работа исключена из T-states. Карта связывает этот артефакт отдельно и не переносит whole-main PASS на неизменённый исходник или на все нагрузки.

## Что не покрыто и почему это остаётся работой

- Checked tokenizer не доказывает исходные `self_tokenizer.nanz`/`.lizp`; совпадение названия или алгоритма недостаточно.
- Rotozoomer и canvas имеют VM/host rendering-тесты; они не доказывают обычный Z80 вывод.
- Старые «9 showcase» тесты сравнения ASM, синтетические строки с тем же алгоритмом, source asserts и QBE/LLVM host native — отдельные evidence classes. Они не превращаются в независимое выполнение точного Z80 корпуса.
- `sha256.nanz` содержит только bit/arithmetic helpers и несколько простых assertions; полного SHA256 compression/digest там нет. Комментарий про «basic test vectors» не означает выполненные hash-векторы. Нужна реализация и проверка полного хеша, если это заявляется целью.
- ASM/extern/platform строки имеют реальные требования, но допускают будущие проверяемые pure entries. Текущая карта не исключает их навсегда и не считает успешными.
- ZVM story[131072] не помещается в native 16-bit Z80; нужна явная цель/модель памяти, не уменьшение исходника ради сборки.

Следующая содержательная работа — проверять оставшиеся точные крупные программы с полным состоянием, либо реализовывать их явно заявленный runtime/target, а не суммировать synthetic helpers в число «работающих программ».

## Воспроизведение

Из `minzc/`, Go 1.26.8:

```sh
MINZ_SHOWCASE_ORACLE_CATALOG=/absolute/catalog.json go test ./pkg/nanz -run '^TestShowcaseExecutableOracleCatalog$' -count=1 -v
MINZ_SHOWCASE_ORACLE_ARTIFACTS=/absolute/artifacts go test ./pkg/pipeline -run '^TestShowcaseBufStreamNativeCapacityModel$' -count=1 -v
```

`manifest.json` содержит SHA256 всех локальных файлов этого отчёта, кроме самого манифеста. Исторические карты других этапов не перезаписаны.
