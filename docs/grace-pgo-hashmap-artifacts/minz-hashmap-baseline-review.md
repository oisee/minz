# Independent original hashmap baseline review

Read-only source/test/artifact review in `/tmp/minz-hashmap-program-baseline`. Original `examples/nanz/21_hashmap_test.nanz` is byte-identical to saved `source.nanz`. No compiler or source edits, and no redundant machine rerun: an independent Python sequential oracle audits the complete saved evidence. Script/log `/tmp/minz-hashmap-independent-audit.py` and `.txt`.

Terminal independent audit PASS for all 36 persistent calls: results, every global byte's read/write count, complete 82-byte global snapshots, original/precompile/postcompile raw, and actual target invocations all match. Binary SHA256 `aefde17ab12e824e4d790cc7147f0974329faf5dded51f032643eb316d56ba86` binds saved machine bytes and target; 1,013 bytes, sum of invocation costs 138,440 T. This is baseline correctness evidence, not an optimized PGO choice or a universal compiler proof.

The independent oracle performs unsigned16 hash `(key xor ((key+37) mod65536)) &15`, little-endian key/value reads and writes, 16-probe limit, wrapped `(slot+1)&15`, occupancy-before-key read, and count update only on new insertion. Source `map_clear` writes count low/high then all 16 occupancy bytes; it deliberately leaves old keys/values intact. Snapshot checks retain those stale arrays across the second clear/refill. Duplicate insertion overwrites values even when all16 slots are occupied without incrementing count. `map_has` reproduces the source sentinel quirk: a present key storing65535 yields0. This behavior is covered three times; it must not be described as conventional independent presence semantics.

The controlled call sequence exercises empty miss, collisions beginning slot15 and wrapping to0, new insertion, overwrite, 16-slot fill, one seventeenth-key insertion failure, missing lookup in a full map, one overwrite while full, zero/65535 keys/values, sentinel behavior, then clear and refill. Actual observed initial hash slots are only5,11,15. Count remains0..16. Inputs include65535+37 wrap; the low slot mask means some arithmetic differences outside low bits remain observationally masked in this workload.

Limits are concrete: globals start zero and the first call clears them. There is no seeded nonzero initial map_count/map_used state, no count low-byte carry255→256 or65535→0, no full16 hash-start-slot distribution, no arbitrary poisoned occupancy bytes, and no direct rd16/wr16/hash16 call oracle. The eight existing source assertion functions remain in the unchanged program, but this baseline workload invokes only map_clear/map_put/map_get/map_has with AssertMode:none. Do not claim those eight actualZ80 entry assertions were independently run here.

Go host `rd` evaluates the low-byte read then high-byte read; `wr` stores low then high, matching the exact source expression/statements. The saved traffic evidence aggregates accesses per byte, so it cannot prove ordered native low/high event sequences or trap order. There are no out-of-bounds cases in the 16-slot global allocation. Stack/code-fetch/bootstrap/initialization/snapshot traffic is outside the profiled declared-global accesses. Complete read/write counters prove the observed workload traffic totals, not every possible evaluation order.

No concrete mismatch in the saved baseline was found. A next-stage optimization should retain unchanged-source and full-machine evidence and add focused seed/carry/hash-distribution cases only where its touched contract requires them. Global-array or zero-fill profitability is not established by this baseline cost alone.
