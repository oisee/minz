# Структура в регистрах: что доказано для C и что требуется от Nanz

16 октября 2026 года. G2 из [плана](c89-optimization/objective.md).

Маленькая C-структура уже передаётся и возвращается как несколько скалярных
значений, когда проверены все границы использования. Это реальная смена HIR/MIR
контракта, не только удаление инструкций после генерации. typed Nanz-структуры
пока не получают автоматически этот C-specific проход.

## Что делает рабочий C-проход

[HIR admission](../minzc/pkg/hir/c_aggregate_promote.go) и
[scalarization](../minzc/pkg/hir/c_aggregate_scalar.go) проверяют CValueABI,
локальное определение функции, известные прямые вызовы и отсутствие использования
адреса функции/косвенного контракта. Тип должен иметь до четырёх простых скалярных
полей и до четырёх байтов хранения: без nested structs, arrays, union/overlap,
volatile и неизвестного layout. Ranged/qualified формы, которые этот узкий
predicate не понимает, сохраняют memory ABI.

Возврат объекта читает **текущие поля** в точке return. Он не повторяет
initializer, поскольку объект мог измениться, а initializer мог иметь эффекты.
Caller получает tuple и материализует прежний объект, когда тот остаётся
наблюдаемым. Если локальный объект не escape и используется только по допустимым
полям, эти поля становятся скалярами; иначе сохраняется storage. Большие C-возвраты
используют caller-owned buffer, с проверкой времени жизни отдельных результатов.

C-параметр по значению имеет собственную копию. Скаляризация меняет представление
этой копии, сохраняя её локальные изменения. Уже материализованный aggregate
аргумент нужен для текущего narrow admission: произвольная функция, возвращающая
объект внутри сложного выражения аргументов, не получает обещание такого ABI.
Внешние, косвенные, volatile и адресно-наблюдаемые границы удерживают memory ABI.

Проверки представлены [ABI/семантическими тестами](../minzc/pkg/c89/aggregate_scalarization_contract_test.go),
[временем жизни](../minzc/pkg/c89/aggregate_lifetime_native_test.go),
[передачей четырёх байтов](../minzc/pkg/c89/aggregate_widths_native_test.go),
[межмодульным linking](../minzc/pkg/c89/aggregate_import_native_test.go) и
[стоимостью полного caller/callee](../minzc/pkg/c89/aggregate_transfer_cost_test.go).
ABI-тест проверяет действительно несколько параметров/возвратов и отсутствие
лишней Alloca; совпадение результата само по себе этого не доказывает.

## Почему одного флага недостаточно для Nanz

В двух [замороженных исходниках](../minzc/pkg/nanz/testdata/aggregate_abi/manifest.json)
caller создаёт Pair, вызывает touch(p), изменяющую hi, затем читает свой p.hi.
C90 §6.7.1 требует параметр-копию; Nanz Book v7 §4.1/4.2 описывает layout/методы,
но не обещает такую же C-copy семантику typed параметра.

При x=7 оба touch возвращают 8. Затем C caller читает своё прежнее hi=7,
а Nanz caller видит hi=8. При x=255 touch возвращает 0; C caller всё ещё видит
255, Nanz caller видит 0. Это наблюдение текущей реализации, не новая спецификация.

[Raw/final MIR и native ASM](c89-aggregate-abi-audit/) подтвердили каждый x=0..255
в default/Grace/Size: **1536 native вызовов и 3072 raw/final VM вызова**,
входная глобальная переменная и PC/SP сохранены. Все 256 C-ожиданий отдельно
подтверждены [GCC-host](c89-aggregate-abi-audit/host-oracle.json).
SHA исходников проверяется до запуска.

**Эти два исходника ведут себя по-разному, поэтому их размеры/такты не являются
честным C-vs-Nanz benchmark.** Они проверяют границу семантики.
В основном struct_roundtrip параметры читаются без такой наблюдаемой записи;
его отдельные C/Nanz/tuple варианты остаются в полной benchmark-матрице.

Для безопасного Nanz-переноса нужны самостоятельные факты:

- Параметр: отсутствие наблюдаемых записей через объект или согласованное
  сохранение всех таких записей; отсутствие alias, который меняет читаемые поля.
- Чтения полей: scalarization не поднимает их через вызов/глобальный эффект,
  способный изменить объект, и не меняет порядок вычисления выражений.
- Возврат: caller не наблюдает адрес/идентичность и время жизни прежнего объекта;
  все его использования допускают tuple либо явную материализацию.
- Literal/генератор: выражения полей вычисляются в исходном порядке один раз,
  прежде чем значения переставляются в порядок tuple-контракта.
- Call graph: все внутренние участники переписаны вместе; внешний и indirect ABI
  остаётся прежним или имеет явный adapter.

Это проверенная возможность дальнейшего расширения, а не повод выставить
CValueABI всем Nanz-функциям. Общая оптимизация C/Nanz и измеренная польза уже
подтверждены; полная универсальная scalarization Nanz относится к дальнейшему
развитию языка/backend.

## Исправленная граница четырёх байтов

Аудит воспроизвёл ошибку narrow admission: у bool один value bit, а хранится он
в целом байте. Предыдущий Width()/8 считал его нулём. Поэтому u16 + три bool
(пять байтов) ошибочно считался допустимым четырёхбайтовым агрегатом.

Теперь используются storage bytes. Граничный тест сначала падал на пятибайтовом
случае и прошёл после исправления: четыре bool и u16 + два bool допускаются,
u16 + три bool отвергается. Это исправление условия допуска; miscompile такого
C89-исходника не заявляется — исходник для него здесь не предъявлен.
[Тест](../minzc/pkg/hir/aggregate_bool_storage_test.go).

Полные HIR/C89/Nanz пакеты PASS (30,472 / 63,986 / 26,320 s);
[протокол](c89-aggregate-abi-audit/core.log). После добавления проверки frozen SHA
направленные admission/native тесты тоже PASS:
[протокол](c89-aggregate-abi-audit/directed.log),
[манифест артефактов](c89-aggregate-abi-audit/manifest.json).
Оптимизация Nanz для общих readonly aggregate функций пока не включена;
подмены её измеренной пользой C promotion нет.
