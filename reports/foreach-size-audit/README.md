# forEach: почему Grace добавляет четыре байта

Точный исходник reports/showcase-src/2026-03-10/ex6_foreach.nanz собран во всех восьми сочетаниях HIR Grace, MIR Grace и Size. ContractOpt включён во всех случаях. Без MIR Grace модуль57B; с MIR Grace61B независимо от двух остальных флагов. source/ASM/BIN/MIR и reproduce.go сохранены; matrix.txt содержит фактические размеры собранного BIN.

Разница находится в max_chain: empty-block-elim удаляет пустой if_then3 и перенаправляет условное ребро сразу к if_join4 с аргументом. Поведение сохраняется, но меняются vreg/coalescing и homes: load был в A при живом максимуме в B, стал в B при живом максимуме в A. Backend сохраняет A через E для сравнения, добавляет копии на entry/exit/backedge. Один условный переход исчезает, но итоговый BIN увеличивается на4байта.

Это конкретный контрпример к предположению «меньше MIR-блоков → меньше Z80-кода». HIR-инварианты и Size-флаг не являются причиной. Полный original iterator тест уже прошёл forEach во всехтрёхрежимах с независимыми VM/native оракулами; живой pipeline350149ad продолжает mapInPlace. Эта матрица проверяет сборочные продукты, не заменяет семантический тест.

Не введён специальный запрет empty-block-elim для max_chain: это форма backend cost regression, которую следует решать выбором проверенного физического кандидата или улучшением назначения/сравнения. Общий selector не должен предполагать прибыльность CFG simplification по числу блоков. Чистая Speed-цель сохраняется без штрафа за байты; такты в этой матрице не измерены.
