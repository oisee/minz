# Языки, которым есть что делать на Z80

> Примечание при публикации: примеры исследованы на локальном снимке `77f8ed19`. Перед push обнаружились более новые изменения master до `c633c9d8`, включая исправления frontend/QBE и перевод VIR из backend в офлайн-оракул. Они здесь заново не проверялись; конкретные результаты компиляции ниже относятся к указанному локальному снимку.

**Дата:** 2026-09-16  
**Автор:** Codex  
**Контекст:** рабочее дерево MinZ на основе `77f8ed19`, включая локальные изменения компилятора.

Мне больше всего нравятся Nanz, Frill и C — по разным причинам. Nanz лучше всего выражает собственный характер проекта. Frill показывает, как приятно описывать вычисления композициями маленьких функций. C приносит настоящие задачи, на которых качество компилятора становится измеримым. ABAP добавляет совершенно другой мир: формы, отчёты и таблицы. А Lanz и Lizp позволяют посмотреть на ту же машину через структурные выражения.

Это рассказ о выразительности и удачных задачах для языков, а не сертификат готовности всех примеров. Состояние backend и обнаруженные ошибки разобраны в [отдельном аудите](2026-09-16-Compiler-State-Audit.md). Здесь исходники взяты из репозитория; свежую проверку, проектный замысел и иллюстративный ассемблер я различаю явно.

## 1. Nanz: язык, который замечает устройство машины

Главная привлекательность Nanz для меня — возможность сообщить компилятору намерение, которое имеет конкретный смысл на Z80: диапазон аргумента, способ обработки ошибки, структуру состояния. При этом указатели и байтовая арифметика остаются видимыми.

### Цикл, который можно выполнить до запуска программы

Из [04_lut_popcount.nanz](../examples/nanz/04_lut_popcount.nanz):

```nanz
fun popcount(x: u8<0..255>) -> u8 {
    var n: u8 = 0
    var v: u8 = x
    while v != 0 {
        n = n + (v & 1)
        v = v >> 1
    }
    return n
}
```

В исходнике виден алгоритм подсчёта установленных битов. Аннотация задаёт небольшой конечный набор входов: в синтаксисе Nanz верхняя граница включена, так что здесь 256 значений. LUTGen умеет вычислить подходящую функцию через MIR2 VM и заменить тело обращением к таблице.

На Z80 это особенно красиво: можно обменять 256 байт таблицы на устранение цикла в каждом вызове. Для таблицы, выровненной на 256 байт, и аргумента в A естественная реализация выглядит так:

```asm
; Иллюстрация при заданных выравнивании и ABI,
; не свежий дамп этого примера.
LD HL, popcount_lut
LD L, A
LD A, (HL)
RET
```

Важен выбор: таблица занимает память, а машинный цикл экономит память ценой времени. Сам исходный алгоритм остаётся понятным. Такой подход полезен для преобразования яркости, малых нелинейных функций, битовых масок и игровой математики. Ограничение диапазона само по себе не доказывает чистоту произвольной функции: применимость преобразования должен проверять компилятор.

### Ошибка, помещающаяся в carry flag

Из [15_error_enforcement.nanz](../examples/nanz/15_error_enforcement.nanz):

```nanz
fun safe_div?(a: u8, b: u8) -> u8 {
    if b == 0 { @error(1) }
    return a / b
}

fun compute(a: u8, b: u8) -> u8 {
    var x: u8 = safe_div?(a, b)
    @propagate
    var y: u8 = safe_add?(x, 5)
    @propagate
    return y
}
```

Определение `safe_add?` есть в полном исходнике. Замысел ABI: carry сообщает об ошибке, A содержит её код; распространение ошибки выражается через `RET C`. Здесь языковая конструкция напрямую использует удобную инструкцию процессора. Суффикс `?` также позволяет парсеру требовать явной обработки вызова.

Это хороший кандидат для небольшого файлового API, парсера команд или работы с устройством. Но корректность зависит от сохранения и очистки флага на всех путях; наличие красивой инструкции ещё не доказывает правильность всей реализации.

**Зачем существует Nanz:** чтобы писать прикладной код для маленькой машины с понятными типами и выразительными конструкциями, сохраняя возможность управлять ценой представления данных.

## 2. Frill: композиция, которая исчезает в трёх инструкциях

### Самый убедительный маленький пример

Из [fun/pipes.frl](../fun/pipes.frl):

```frill
let double (x : u8) : u8 = x + x
let inc (x : u8) : u8 = x + 1

let pipe_dbl_inc (x : u8) : u8 = x |> double |> inc

assert pipe_dbl_inc 5 == 11
```

Этот файл заново скомпилирован при подготовке отчёта. В полученном Z80-коде действительно есть:

```asm
pipe_dbl_inc:
    ADD A, A
    INC A
    RET
```

Вот хорошее оправдание функционального frontend: автор собирает преобразование из именованных частей, а горячий путь не содержит вызовов этих частей или промежуточных объектов. Это наблюдение относится к данной функции, а не обещание такой же цены любой функциональной конструкции.

### Геометрия как функция от координат

Из [examples/frill/graphics.frl](../examples/frill/graphics.frl):

```frill
let sierpinski (x : u8) (y : u8) =
  if (x & y) == 0 then 1 else 0

let xor_tex (x : u8) (y : u8) = (x ^ y) % 8

let abs_diff (a : u8) (b : u8) =
  if a > b then a - b else b - a
```

Треугольник Серпинского здесь рождается из побитового AND. Цветная XOR-текстура — из XOR и ограничения палитры. У Z80 есть подходящие дешёвые побитовые операции: функция описывает рисунок без необходимости хранить готовое изображение.

Отдельный вывод пикселей или атрибутов всё равно нужен. В полном файле есть canvas-вызовы; их наличие не означает, что это уже автономная Spectrum-программа. Особенно убедителен здесь именно вычислительный слой: маленькие функции узора можно отдельно проверять, комбинировать и встраивать в платформенный renderer.

**Зачем существует Frill:** чтобы строить узоры, преобразования байтов и небольшие вычислительные конвейеры из выразительных функций, позволяя общему backend убирать композиционный overhead.

## 3. C: красота настоящего бинарного формата

У C в этом проекте есть более сильное оправдание, чем привычность синтаксиса: существующий код, форматы данных и возможность независимого сравнения результатов.

### Двенадцать бит на запись

Из [fatfs_lowlevel.c](../examples/c89/fatfs_lowlevel.c), где `BYTE` — `unsigned char`, а `WORD` — `unsigned short`:

```c
WORD ld_word(const BYTE* ptr) {
    WORD rv;
    rv = ptr[1];
    rv = (WORD)(rv << 8) | ptr[0];
    return rv;
}

WORD read_fat12(const BYTE* fat, WORD clst) {
    WORD ofs = clst + (clst >> 1);
    WORD val = ld_word(fat + ofs);
    if (clst & 1) {
        val = val >> 4;
    } else {
        val = val & 0x0FFF;
    }
    return val;
}
```

Смещение `clst + (clst >> 1)` отражает упаковку двух 12-битных записей в три байта. Дальше выбирается нужная половина. Это компактное описание реального дискового формата, а не искусственный пример на сложение.

Для Z80 задача естественная: работа с байтами, парами регистров, указателями и масками. Отсутствие аппаратного умножения не мешает вычислению смещения через сдвиг и сложение. При этом такая программа быстро обнаруживает ошибки расширения типов, порядка байтов и распределения регистров.

Полный FatFS не объявляется здесь рабочим на Z80. [Предыдущий отчёт о блокерах](2026-04-06-Claude-FatFS-Precision-Blockers.md) и свежий аудит объясняют, почему это ещё проверочная цель. Пример показывает ценность задачи и языка; качество конечного кода нужно заслужить тестами.

**Зачем существует C frontend:** чтобы общий backend обслуживал реальные библиотеки и форматы, а результат можно было проверять относительно других реализаций. Хорошая поддержка C улучшает условия жизни и Nanz, и Frill.

## 4. ABAP: маленькая машина как терминал деловой системы

ABAP на Z80 сначала смешит, а потом предлагает вполне понятную задачу: экран, пользователь, табличные записи и отчёт. Для терминального интерфейса CP/M такой мир не выглядит чужим.

### Выборка и табличное представление

Фрагмент из [makt_search_cpm.abap](../examples/abap/makt_search_cpm.abap):

```abap
REPORT zmakt_search.

START-OF-SELECTION.
  WRITE '  Material Text Search (MAKT)'.

  SELECT matnr maktx FROM makt INTO TABLE @DATA(lt_makt).

  cl_salv_table=>factory( lt_makt ).

END-OF-SELECTION.
  WRITE '  ABAP Open SQL on Z80 CP/M'.
```

Полный файл содержит и директивы инициализации таблицы. Нравится то, что исходник сразу говорит о задаче: взять коды и описания материалов, показать таблицу. Именно такая предметная выразительность и оправдывает отдельный frontend.

Граница исполнения принципиальна: SQLite в описанном проектом варианте работает через сервис хоста, а не целиком внутри Z80. На ретромашину приходится скомпилированная прикладная часть и взаимодействие с доступным окружением. Для самостоятельного железа понадобится соответствующая реализация этого интерфейса.

Здесь нет свежего подтверждения полного запуска: ABAP-проверки предыдущего аудита остановились на отсутствующей зависимости парсера. И не стоит использовать [старый sqlite_demo.abap](../examples/abap/sqlite_demo.abap) как доказательство работы базы: его `sqlite_run` и `sqlite_select` лишь делают `WRITE pv_sql`.

**Зачем существует ABAP frontend:** чтобы исследовать компактные формы и отчёты на ретротерминале и проверить, способен ли общий IR обслуживать язык, выросший из совершенно другой предметной области.

## 5. Lanz: маленький язык, на котором удобно объяснять компилятор

Из [assert_test.lanz](../examples/lizp/assert_test.lanz):

```lisp
(fun double ((x u8)) u8
  (return (+ x x)))

(fun max_byte ((a u8) (b u8)) u8
  (if (> a b) (return a) (return b)))

(assert double 127 == 254)
(assert max_byte 10 20 == 20)
```

Здесь видна структура: функция, типы, операция, ветвление, возврат. Для исследования backend это достоинство. Маленький исходник удобно генерировать, сокращать до воспроизводителя и сопоставлять с HIR/MIR2 и ассемблером.

На Z80 роль особенно полезна: можно изучать, как один аргумент попадает в A, как сравнение управляет возвратом, где требуется перемещение регистра. Lanz позволяет оставлять языковую оболочку минимальной, сохраняя типизацию и общий pipeline.

**Зачем существует Lanz:** как текстовый вход для экспериментов, генераторов и регрессионных примеров. Для этой роли ему не требуется конкурировать с Nanz за каждую прикладную программу.

## 6. Lizp: выражения Лиспа доходят до экранной памяти

Lanz и Lizp не стоит смешивать. У Lizp есть более высокоуровневые формы вроде `defun`, `let` и `cond`; в примерах при этом явно присутствуют машинные типы. Называть эту реализацию полным универсальным Scheme было бы слишком сильным утверждением.

### Цветная сетка Spectrum

Из [zx_checkerboard.lizp](../examples/lizp/zx_checkerboard.lizp):

```lisp
(defun attr-addr ((col u8) (row u8)) -> u16
  (return (+ #x5800 (+ (* (cast row u16) 32) (cast col u16)))))

(defun make-attr ((paper u8) (ink u8)) -> u8
  (return (| (<< paper 3) ink)))
```

Первое выражение адресует ячейку атрибутов Spectrum: базовый адрес плюс строка из 32 ячеек и номер столбца. Второе собирает цвет фона и чернил. В полном примере циклы раскрашивают 24 × 32 ячейки; формула узора строится из сдвигов, сложения и маски.

Это уже узнаваемая задача конкретного компьютера. S-выражения вполне способны быть оболочкой для адресной арифметики и побитовой графики. Однако inline-asm примитив записи в полном исходнике также зависит от правильного ABI; в рамках этого отчёта вся программа заново не исполнялась.

**Зачем существует Lizp:** чтобы пользоваться структурными выражениями и формами Лиспа в маленьких графических и вычислительных программах, сохраняя явные ширины чисел и доступ к машине.

## Что именно проверено при подготовке

Источники всех приведённых фрагментов прочитаны непосредственно в репозитории. Для Frill дополнительно выполнено:

```sh
# Из корня репозитория, бинарник собран во время аудита:
timeout 60s /tmp/minz-audit-mz fun/pipes.frl -o /tmp/minz-language-pipes.a80
```

Команда успешно завершилась, а тело `pipe_dbl_inc` сверено с полученным `.a80`. Это подтверждение конкретного результата компиляции; физический Z80 в этой проверке не участвовал. Ассемблерный пример LUT выше помечен как иллюстрация, остальные большие программы показаны по исходникам, без обещания свежей сквозной проверки.

## За что я бы держался

| Язык | Его сильная роль в MinZ | Пример, который хорошо её выражает |
|---|---|---|
| Nanz | Прикладной язык с информацией для оптимизации под машину | Диапазон → таблица; ошибка → carry |
| Frill | Композиция небольших вычислений | `x |> double |> inc` → три инструкции |
| C | Реальные библиотеки и независимая проверка семантики | Чтение упакованной FAT12-записи |
| ABAP | Предметный язык форм, выборок и отчётов | Open SQL → табличное представление |
| Lanz | Компактный структурный вход в общий pipeline | Типизированная функция плюс assert |
| Lizp | Лиспоподобное описание машинных вычислений | Адреса и цвета атрибутов Spectrum |

Pascal, PL/M и ObjC тоже заслуживают своих подборок. Здесь я сознательно развил предыдущий разговор о фаворитах, добавив Lizp как полезный контраст с Lanz; это не рейтинг всех frontend по полноте реализации.

Мой выбор для следующей небольшой Z80-программы — Nanz. Для самого короткого и убедительного показа красоты компиляции — Frill с тремя инструкциями. Для проверки, насколько компилятор уже выдерживает реальную работу, — C с бинарными форматами. У остальных есть собственные задачи, и именно наличие таких задач делает многоязычность проекта содержательной.
