## От картинки к программе

Обычная рисовалка читает байты картинки из массива. Compiled sprite превращает известную картинку в последовательность инструкций: «запиши 17, сдвинь указатель, запиши 34…». Значения рисунка уже входят в код. Наш Nanz-генератор делает это во время компиляции, а полученная программа выполняется на настоящих инструкциях Z80.

```nanz
import hw.sprite_chain

@sprite_chain("actor") {
    destination "zx_bitmap_bytes" 0x4000
    region 4 56 4 2
    row "00000000" "11223344"
    row "00000000" "55667788"
    via "compiled"
}
```

Это две строки по четыре **байта**, то есть рисунок шириной 32 пикселя и высотой 2 scanlines. Координата x тоже в байтах. Каждая `row` содержит две hex-строки: keep-mask и рисунок. Здесь маски нулевые, поэтому запись непрозрачная.

`actor` — имя создаваемой runtime-функции. `@sprite_chain` — метафункция на самом Nanz из [stdlib/hw/sprite_chain.nanz](../stdlib/hw/sprite_chain.nanz). Она проверяет описание, декодирует hex, вычисляет начальные экранные адреса и через `emit` выпускает функцию и её helpers. Генератор выполняется на compile-time MIR2 VM; в готовом BIN остаются инструкции и данные, нужные самой программе.

В отличие от прежнего фиксированного `@sprite`, каждая строка получает собственный изменяемый адрес и переход продолжения. Смысл первого фрагмента можно прочитать так:

```asm
actor_chain_row_0:
    LD HL, 16612       ; 0x40e4: первый байт строки (x=4, y=56)
    LD (HL), 17
    INC HL
    LD (HL), 34
    INC HL
    LD (HL), 51
    INC HL
    LD (HL), 68
actor_chain_row_0_next:
    JP actor_chain_row_1
```

Адрес строки на Spectrum переставлен по битам y, поэтому следующий scanline не обязательно находится через 32 байта. Генератор знает эту раскладку. Известное при сборке вычисляется один раз; при перемещении новые адреса подготавливает runtime-код.

## Перемещение меняет два байта, рисунок остаётся прежним

Компилятор также получает обычные функции-сеттеры. Setter адреса строки записывает новое слово в immediate после opcode `LD HL,nn`:

```asm
actor_set_row_0:
    LD (actor_chain_row_0+1), HL
    RET
```

Никакие пиксельные инструкции не пересобираются. Меняются два байта адреса, которые Z80 прочитает при следующем исполнении строки. Это физический self-modifying code: инструкция получает новые операнды в RAM.

На Nanz можно определить собственное адресное преобразование:

```nanz
fun screen_address(x: u16, y: u16) -> u16 {
    return 0x4000 + ((y & 192) << 5)
                  + ((y & 7) << 8)
                  + ((y & 56) << 2) + x
}

fun move_actor(x: u16, y: u16) -> void {
    actor_set_row_0(screen_address(x, y))
    actor_set_row_1(screen_address(x, y + 1))
}
```

Для этой картинки вызывающий код должен обеспечить x ≤ 28 и y ≤ 190. Сеттер принимает сырой адрес; runtime clipping и проверку новых координат он не добавляет. Начальный descriptor проверяется при компиляции, дальнейшее владение RAM и границы — ответственность вызывающего кода.

В статическом положении можно много раз вызывать `actor()` без повторного патчинга. Если положение меняется каждый кадр, нужно считать стоимость обоих действий: **move + draw**.

## Порядок строк тоже становится данными

Каждая секция заканчивается патчируемым `JP`. Setter следующей строки меняет его operand. Helpers возвращают адреса секций, поэтому можно построить цепочку из Nanz:

```nanz
fun reverse_actor_rows() -> void {
    actor_set_entry(actor_row_1_address())
    actor_set_next_1(actor_row_0_address())
    actor_set_next_0(actor_done_address())
}
```

```mermaid
flowchart LR
    E[Вход actor] --> R1[Строка 1]
    R1 --> R0[Строка 0]
    R0 --> D[done: восстановить регистры и RET]
```

В исходном descriptor цепочка идёт 0 → 1 → done. После этих трёх патчей она идёт 1 → 0 → done. Адрес назначения каждой строки при этом остаётся её собственным: перестановка **порядка исполнения** не переставляет изображение автоматически. Чтобы обменять строки картинки местами, меняются их destination-addresses.

Можно пропустить вторую строку:

```nanz
actor_set_entry(actor_row_0_address())
actor_set_next_0(actor_done_address())
```

Или сделать пустую цепочку: `actor_set_entry(actor_done_address())`.

Цепочка должна завершаться в `done` этого же экземпляра. Сеттеры не анализируют динамический граф: цикл даст бесконечное исполнение, чужая секция завершения нарушит контракт. Входить нужно через `actor()`, который сохраняет регистры; `actor_row_0_address()` не предназначен для отдельного CALL строки.

Есть тонкость генерации: peephole обычно удаляет JP на соседнюю инструкцию. Но такой переход нельзя удалять, если его operand затем патчит setter. Поэтому библиотека выпускает **`DB 195 / DW target`** — точные байты JP с символическим адресом. Сборщик получает тот же машинный переход, а текстовый peephole сохраняет его место. Native-тест наблюдает PC при входе в каждую строку и подтверждает фактическую последовательность.

## Маска специализируется до исполнения

Операция каждого байта задана явно:

```text
new = (old & keep_mask) | graphics
```

Например:

```nanz
@sprite_chain("masked") {
    destination "linear" 0x6000 3 1 3
    region 0 0 3 1
    row "ff00f0" "007f05"
    via "compiled"
}
```

Первый байт прозрачен: `ff/00` не требует чтения или записи. Второй записывает `0x7f` напрямую. Третий оставляет старшие биты фона и добавляет младшие:

```asm
    LD A, (HL)
    AND 240
    OR 5
    LD (HL), A
```

Фон остаётся живой памятью. Тест меняет его на всех 256 byte-значениях и повторно патчит **один и тот же** экземпляр кода, проверяя работу после предыдущего вызова.

## PUSH: временно превратить стек в пишущую головку

Непрозрачная картинка допускает другой примитив:

```nanz
@sprite_chain("fast_actor") {
    destination "zx_bitmap_bytes" 0x4000
    region 4 56 4 2
    row "00000000" "11223344"
    row "00000000" "55667788"
    via "push"
    irq "disabled"
}
```

Теперь setter строки принимает **end + 1**, а не первый адрес:

```nanz
fast_actor_set_row_0(screen_address(4, 56) + 4)
fast_actor_set_row_1(screen_address(4, 57) + 4)
```

Строка рисуется примерно так:

```asm
row_0:
    LD SP, 16616
    LD DE, 0x4433
    PUSH DE
    LD DE, 0x2211
    PUSH DE
    JP row_1
```

PUSH уменьшает SP и записывает word так, что младший байт оказывается по младшему адресу. Поэтому данные выпущены справа налево: в экран попадут ровно `11 22 33 44`.

`LD DE,nn` стоит 10 T, `PUSH DE` — 11 T: пара байтов записывается за 21 T после установки SP. Для обычных записей две `LD (HL),n` и промежуточный `INC HL` стоят 26 T; переходы между парами, подготовка и сохранение состояния также входят в общую цену.

Перед рисованием ядро сохраняет AF/BC/DE/HL на **обычном** стеке. Затем записывает текущий SP в immediate своей restore-инструкции:

```asm
    PUSH AF
    PUSH BC
    PUSH DE
    PUSH HL
    LD (restore+1), SP
    ; ... строки рисуют через экранный SP ...
restore:
    LD SP, 0           ; здесь уже записан сохранённый normal SP
    POP HL
    POP DE
    POP BC
    POP AF
    RET
```

Это второй вид SMC в том же ядре: изменяемый адрес восстановления стека. На последнем шаге RET опять читает обычный адрес возврата, а не пиксели экрана.

Между строками используется JP. `LD BC,next / PUSH BC / RET` при экранном SP записал бы адрес продолжения в экран и стоил бы 31 T вместо 10 T для JP. Возможность перемешивать строки сохраняется патчированием JP.

## Прерывания — часть API

PUSH использует SP как экранный указатель. Принятый IRQ или NMI тоже использует стек и может испортить экран или возврат. Поэтому этот вариант требует отключённых maskable IRQ на всём интервале исполнения; NMI и reentry не поддержаны.

`irq "disabled"` — обязательное описание контракта. **Сам генератор не выпускает DI/EI.** Это делает вызывающий код, который знает состояние машины:

```nanz
fun paint_with_irqs_enabled_on_exit() -> void {
    asm z80 (clob) { DI }
    fast_actor_set_row_0(screen_address(4, 56) + 4)
    fast_actor_set_row_1(screen_address(4, 57) + 4)
    fast_actor()
    asm z80 (clob) { EI }
}
```

Такой wrapper намеренно включает IRQ на выходе. Он не сохраняет произвольное исходное состояние IFF. Реальное демо использует именно этот режим, затем `EI / HALT` для pacing через ROM.

Compiled-вариант сохраняет обычный SP и не меняет IFF, но патчируемый код всё равно требует согласования: не исполнять экземпляр одновременно с неполной двухбайтовой записью, не вызывать его рекурсивно и не менять его из IRQ. Код, рисунок и доступный восьмибайтовый save-frame должны лежать в непересекающихся областях owned RAM.

## Что показало честное сравнение

Мы сравнили восемь непрозрачных строк: pointer-вариант хранит динамические адреса в data и рисует специализированными обычными Nanz stores; новые варианты патчат immediate. Все вычисляют те же ZX-адреса из runtime x/y. Natural links настроены при сборке; перестановка цепочки в эту таблицу не включена.

| Ширина строки | Вариант | Move T | Draw T | Сумма T | Весь модуль, B |
|---|---|---:|---:|---:|---:|
| 4 B | Pointer | 3884 | 602 | 4486 | 867 |
| 4 B | Compiled | 3859 | 728 | 4587 | 945 |
| 4 B | PUSH | 4091 | 630 | 4721 | 976 |
| 8 B | Pointer | 3884 | 1114 | 4998 | 963 |
| 8 B | PUSH | 4091 | 966 | 5057 | 1040 |
| 16 B | Pointer | 3884 | 2138 | 6022 | 1155 |
| 16 B | Compiled | 3859 | 2264 | 6123 | 1233 |
| 16 B | PUSH | 4091 | 1638 | 5729 | 1168 |

Это ordinary mode при x=4/y=56. Восемь строк по 16 байтов — 128×8 пикселей. PUSH сокращает сам draw на **23,4%**, полную сумму — примерно на **4,9%**. На маленьких строках полная цена проигрывает. Compiled-цепочка сохраняет регистры и выполняет отдельные переходы: гибкость стоит инструкций.

81 сравнение охватило три ширины, три стратегии, три режима и три позиции. T-states включают тела position/draw и RET; внешний CALL, DI/EI и физические IRQ/ULA исключены. Размер — весь измерительный модуль с helpers, не только рисунок. Автоматического selector нет: выбор остаётся явным, а повторное рисование неподвижного изображения амортизирует move.

## Что именно проверено и где поиграть

- 108 native-сценариев проверили позиции, порядок, subsets, пустую цепочку, RAM и регистры/PC/SP. Трасса PC подтверждает порядок секций.
- 768 masked-вызовов повторно патчили код на разных фонах; 17 ошибочных descriptors/names отвергнуты.
- Полный Spectrum actual main прошёл **64 completed screens × 6 сборок**, с 48K ROM, IM1 IRQ и ULA contention. В каждом прогоне приняты 189 ROM IRQ, проверены экран, draw PC/SP и регистры через IRQ. PUSH входит с IFF выключенным и сохраняет это состояние до возврата.
- На чистом main `201146cf` вся chain-серия завершилась PASS за 4,487 с; launcher снова отработал 100 video frames.

Это эмуляторная проверка реального машинного кода. Физический Spectrum, NMI и tear-free presentation остаются вне доказательства. Video frames и завершённые рисунки — разные события; периодический screenshot может увидеть очередную отрисовку посередине.

```sh
scripts/play_zx_sprite_chain.sh
scripts/play_zx_sprite_chain.sh --push
```

Для окна нужны SDL и display. Windowless: добавить после выбора примитива `--headless --frames 100 --screenshot build/sprite.png`.
