## Что меняется

В MIR встречалась пара: чтение байта во временный регистр и немедленное
копирование в регистр, предпочтительный для следующего потребителя.
Теперь исходное чтение сразу определяет результат копирования. Аллокатор
получает предпочтение потребителя и может обойтись без пересылки.

В execute() примера abs_diff:

```asm
; прежде
LD HL, v_a
LD C, (HL)
LD A, C

; теперь
LD A, (v_a)
```

Тело abs_diff остаётся прежним. [Полный ASM](c89-byte-load-fusion/program.a80),
[raw MIR](c89-byte-load-fusion/raw.mir), [final MIR](c89-byte-load-fusion/final.mir).
Следующий резерв — прямые 16-битные записи из DE/BC вместо адресации через HL;
в приведённые результаты он не включён.

## Почему сохраняется поведение

[Проход](../minzc/pkg/mir2/fuse_byte_load_move.go) принимает только соседние
Load/Move одного байтового типа. У результата чтения должен быть ровно один
потребитель во всей функции; оба результата должны иметь единственное
определение, включая параметры блоков и дополнительные результаты вызовов.
Жёсткие ограничения регистров, raw ASM, fallible и flag-return функции не допускаются.

Чтение не перемещается, не дублируется и не устраняется: его volatile-признак,
позиция, указатель и метаданные сохраняются. Поэтому преобразование допустимо
и для volatile-чтения; оно удаляет только ненаблюдаемое копирование значения.
Написанный тест проверяет все 256 значений и точное число чтений. Отдельные
проверки отказывают при общих потребителях, переопределениях, несовпадающих
типах, переходе между блоками и неподдерживаемых контрактах.

Полные пакеты MIR2, C89, HIR и Nanz прошли: 83,467 / 55,318 / 32,061 /
27,545 секунды соответственно. Все 432 проверки быстрого pipeline прошли
в трёх независимых процессах: [статусы](c89-byte-load-fusion/fast-statuses.json).
После совмещения с main дерево исходников компилятора совпадает с измеренным
checkpoint 6e9e662d; сужение арифметики уже интегрировано через PR #175.
Полный глубокий pipeline не заявлен как PASS.
