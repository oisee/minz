# C89 и идиоматичный Nanz против SDCC 4.2/4.5 и sccz80

16 октября 2026 года. Этот отчёт расширяет [одинаковый C baseline](../2026-10-16-c89-identical-c-benchmark.md).
**SDCC 4.5 поддерживает наш struct-by-value пример; MinZ C выигрывает в нём.
В пяти других одинаковых C-примерах SDCC быстрее и компактнее.** Nanz улучшает
несколько строк; существующий Grace дополнительно ускоряет Nanz gcd.

## Сравнение

Ячейка — занятые байты кода и данных / сумма T-states всей нагрузки данной строки.
Измеряются execute(), внутренние вызовы, helper routines, запись результата и RET.
Внешний синтетический вызов исключён одинаково. Это голый Z80 без ULA/BDOS/startup.

| Пример | MinZ C | Nanz | Nanz + Grace | SDCC 4.2 speed | SDCC 4.5 speed | sccz80 O3 |
|---|---:|---:|---:|---:|---:|---:|
| abs_diff | 82 / 553 558 | 38 / 305 750 | 38 / 305 750 | 34 / 264 286 | 33 / 258 142 | 87 / 696 320 |
| gcd | 127 / 17 003 692 | 62 / 5 003 118 | 56 / 3 116 165 | 57 / 4 249 984 | 56 / 4 243 840 | 168 / 28 596 874 |
| sum_array | 360 / 19 897 856 | 320 / 8 316 876 | 320 / 8 316 876 | 326 / 9 798 656 | 316 / 7 433 216 | 375 / 27 157 248 |
| copy_bytes | 250 / 1 669 590 | 215 / 1 044 550 | 215 / 1 044 550 | 215 / 822 770 | 212 / 683 930 | 230 / 1 474 590 |
| fat12_decode | 187 / 37 856 | 188 / 38 112 | 188 / 38 112 | 159 / 27 392 | 150 / 25 152 | 207 / 57 952 |
| struct_roundtrip | 90 / 985 088 | 159 / 1 974 272 | 159 / 1 974 272 | Не собирается | 152 / 1 826 816 | Не собирается |

Здесь показаны speed-профили SDCC. Все size-профили, MinZ OptSize и прочие
результаты сохранены в [полной таблице](baseline/summary.json); проигрыши не удалены.
MinZ OptSize без Grace не меняет результаты. MinZ C+Grace меняет только gcd:
17 003 692 → 16 842 712 T при тех же 127 байтах. Nanz OptSize совпадает с default;
Nanz+Grace меняет только gcd: 62 → 56 байт и 5 003 118 → 3 116 165 T.

Сумма Nanz по foreach быстрее SDCC 4.2, но уступает SDCC 4.5 speed. Nanz+Grace gcd
быстрее обеих speed-версий SDCC при том же размере, что SDCC 4.5 speed (56 байт).
Это результаты этих исходников/нагрузок, не общий рейтинг компиляторов.

## Структура и tuple — два сохранённых варианта

В строке struct_roundtrip выше используется настоящая Nanz-структура. Отдельный
[идиоматичный tuple-вариант](../../research/c89-benchmark/nanz-tuple/struct_roundtrip.nanz)
возвращает те же два значения и выполняет тот же расчёт: **77 байт / 669 696 T**
во всех трёх режимах MinZ, против **159 / 1 974 272** у Nanz-структуры.
Он не подставлен вместо более дорогой структуры и не назван одинаковым C.

SDCC 4.5 speed исполняет исходный C с передачей/возвратом структуры по значению:
152 байта / 1 826 816 T. MinZ C: 90 / 985 088, около −40,8% байт и −46,1% тактов.
В MinZ это уже существующее разложение маленькой C-структуры на скалярный ABI;
новая оптимизация в ходе baseline не добавлялась. Обычная Nanz-структура пока
не получает тот же C-specific promotion. Это отдельная подцель [G2](objective.md).

SDCC 4.2 и sccz80 этот неизменённый C с агрегатами не собирают. Вывод старого
отчёта относится только к этим версиям, не к актуальному SDCC вообще.

## Что одинаково, что различается

[C-файлы](../../research/c89-benchmark/cases/) буквально одинаковы для MinZ,
SDCC 4.2, SDCC 4.5 и sccz80, с прежними SHA256. [Nanz-файлы](../../research/c89-benchmark/nanz-cases/)
— отдельные эквивалентные алгоритмы: явные u8/u16, while для gcd/copy,
foreach по указательному диапазону для суммы. Число входов каждой строки неизменно:
2048 / 2048 / 512 / 130 / 64 / 2048. Нет hand ASM, SMC, специализации по входам
или новой таблицы. Tuple ABI добавлен отдельно после наблюдения структурного
результата, с собственным исходником и manifest. Ранние ошибки написания Nanz
(semicolon и return с продолжением после скобок) сохранены как syntax probes;
их исправление не меняло production-компилятор или алгоритм.

Настройки compiler профилей объявлены до итогового запуска. Для обоих SDCC:
-mz80 --std-c89, отдельно --opt-code-size/--opt-code-speed, без CRT0.
--max-allocs-per-node оставлен штатным; это не поиск сильнейшей конфигурации SDCC.
MinZ: обычный PBQP и greedy contract optimization; отдельно default/OptSize/Grace.
Нет checked-local tables, joint PFCCO или PGO. sccz80: штатный zcc -O3 и официальный
архив compiler helpers, без переписанных вручную вспомогательных функций.

[SDCC 4.5.0 #15242](baseline/sdcc45-build-info.json) собран из официального release
архива, без изменения исходников; локальные Boost/zlib/bison/flex/m4 нужны только
для сборки инструмента. [Версии и SHA](baseline/toolchains.json),
[инструкция стенда](../../research/c89-benchmark/README.md) сохраняют воспроизводимость.
Production MinZ совпадает с main caa049f9/5929c812; baseline runner commit 9d3e4c9a.

## Проверки и ограничения

69 сборок: **66 PASS**, три явных aggregate compile errors у старых инструментов.
**75 350 native-вызовов** проверяют результат, входы/заданную память/хвост copy и PC/SP.
MinZ C/Nanz/tuple также проходят **94 488 raw/final MIR VM-вызовов**. Полная нагрузка
имеет одинаковый SHA между языками, режимами и версиями. Независимый GCC-компилятор
на тех же C-файлах подтвердил все **6850** ожиданий: [host oracle](baseline/host-oracle.json).

Байты включают helper routines, globals и compiler-owned DATA/BSS, даже когда SDCC
не хранит её в HEX. Перекрытия считаются один раз, пустые адресные промежутки
исключены. Например, SDCC 4.5 struct-return buffer учитывается в размере.
Это не COM-размер и не peak stack. Весь 64-КБ след, INT и экранный луч здесь
не проверяются. Все raw артефакты, команды и наблюдения сохранены локально
в grace-reports/2026-10-16/c89-nanz-sdcc45/full-final с SHA256 manifest.
