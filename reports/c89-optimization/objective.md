# Цель: проверенная польза оптимизаций C89 и Nanz на Z80

Начата 16 октября 2026 года после завершения practical C89 admission (PR #171).

1. Заморозить одинаковый C и отдельный идиоматичный Nanz на общих алгоритмах.
   Воспроизвести весь набор с SDCC 4.2.0, SDCC 4.5.0 и sccz80, сохранив все
   режимы и неудачные сборки. Для Nanz tuple ABI публиковать отдельный вариант,
   сохраняя структурный исходник даже если он хуже.
2. Проверить результат, заданную память и PC/SP на Z80; MinZ также на raw/final
   MIR VM. Проверить численный/памятный оракул независимым host C-компилятором.
3. Изолировать подтверждённые причины лишнего кода и применить безопасные
   обычные MIR или Grace-преобразования. Не менять исходный baseline ради победы.
4. Получить воспроизводимый выигрыш минимум в двух разных семействах задач,
   подтвердить его на отложенных входах и дополнительных исходниках, с
   регрессионными проверками границ семантики, памяти и ABI.
5. Интегрировать проверенные изменения и отчёт в main. Разделять пользу языка,
   ABI и оптимизатора; не требовать победы над SDCC в каждой строке.

Стенд не измеряет ULA contention и полный RAM trace. Сужение C-promotions должно
опираться на доказанные диапазоны, а не на изменение правил C89. Общее сравнение
не подменяет прежние VIR/Z3 эксперименты: тот backend и старые исходники требуют
отдельного воспроизведения.

Baseline интегрирован через PR #173; byte compare — #174; byte arithmetic —
#175; byte loads — #176; C output contracts — #177; целый CFG abs_diff — #178.
Полный текущий benchmark и повтор старых C-обещаний интегрированы в PR #179/#180;
прямые word stores, их взаимодействие с PFCCO и G2 bool-storage fix объединены в #181.
G2 проверен [отдельным аудитом](../2026-10-16-c89-nanz-aggregate-abi-audit.md): C promotion
работает с проверенными условиями; текущая Nanz shared-object семантика требует
самостоятельного допуска, а не общего CValueABI. Исправлена bool-storage граница.
[Заключительный аудит](../2026-10-16-c89-optimization-completion-audit.md) подтверждает
измеримые требования; интеграция принимается только после MERGED #181 и проверки
фактического main на идентичность проверенному compiler tree. Универсальный typed-Nanz promotion
не объявлен работающим и не заменяет доказательства C-прохода.

## Подцели, уточнённые с Alice

### G1. Честный baseline

Одинаковый C: MinZ / SDCC 4.2 / SDCC 4.5 / sccz80. Отдельно идиоматичный Nanz,
сохраняя struct и tuple как разные варианты. Все исходники и входы фиксированы;
ошибки и проигрыши сохраняются. Полная матрица завершена: 69 сборок, 66 PASS,
75 350 native-вызовов и 94 488 raw/final MIR VM-вызовов; host C oracle 6850 PASS.
SDCC 4.5 поддерживает tested struct-by-value, в отличие от 4.2.
[Полный отчёт](baseline.md) интегрирован в main через PR #173.

### G2. Безопасная структура ↔ скалярный tuple ABI

Не реализовывать заново уже работающую C promotion. Проверить и зафиксировать
условия её допуска: маленькие скалярные поля (сейчас до четырёх байт), известные
прямые вызовы, порядок вычислений/копирования, отсутствие несовместимых адресных,
volatile и косвенных ABI-наблюдений. Небезопасные формы сохраняют memory ABI.
Проверить возможность распространить доказанный механизм на typed Nanz-структуры,
не подменяя возвращаемый указатель возвращаемым значением. PFCCO выбирает
расположение скалярных слотов после легального изменения представления.

### G3. Выходной указатель → возвращаемое значение

Реальный C outparam admission интегрирован в main через PR #177.
[Отчёт](../2026-10-16-c89-output-contracts.md) содержит три исходника и отказные формы.
Исследовать существующий узкий `findOutParamFunctions`/`rewriteOutParamFunc` и
допустить реальные исходники C через проверяемые факты. Одного «нет чтения через
out» недостаточно. Доказать область всех вызовов, отсутствие escape/наблюдаемого
aliasing/volatile/inline-ASM-наблюдений, корректность на каждом пути и сохранение
момента/порядка существенных эффектов. Переписать caller вместе с callee: сначала
получить вычисленное значение, затем материализовать исходное назначение, если оно
наблюдаемо. Не удалять обычные глобальные эффекты функции под словом «чистая».
Публиковать отдельно допущенные, отвергнутые и уже существующие случаи.

### G4. Доказанное сужение C-promotions

Приведения C к int остаются семантически правильными. Сужать только эквивалентные
операции при доказанном диапазоне или последующей truncation. Учитывать signed,
unsigned, переполнение, сравнения и различие битовых/арифметических сдвигов.
Проверить независимыми граничными и полными маленькими доменами на VM и Z80.

### G5. Польза Grace и обычных проходов на циклах/адресации

Сначала измерить существующие проходы на неизменённом baseline, затем добавлять
или обобщать правила по фактам. Адресные инварианты, byte compare и безопасный
pointer walk — кандидаты, а не заранее объявленные победители. Отдельно измерять
ABI-трансферы и цену call sites. Для каждого изменения дать размер и T-states.

### G6. Heldout и интеграция

Подтвердить новые выигрыши хотя бы в двух разных семействах задач на отложенных
входах и дополнительных исходниках. Повторить исходный baseline, не выбирая
удачные строки. Интегрировать изменения и итоговый отчёт в main через необходимые
проверки. Цель не закрывается одним выигрышным микропримером или только VM PASS.

Порядок: G1 → аудит G2/G3 и первый G4 → G5 → G6. G2/G3 не блокируют независимое
сужение арифметики; после фиксации baseline их можно вести независимо. Общие
факты о диапазонах, эффектах, escape и ABI должны переиспользоваться проходами.
