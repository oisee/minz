## 2. E2E Examples (all verified via MZE real Z80 emulator)

### 2.1 fibonacci — recursive, 16-bit result in HL

```asm
; generated by MIR2 Z80 codegen

fibonacci:
    CP 1
    JP C, .fibonacci_base
    JP Z, .fibonacci_base
.fibonacci_loop_init:
    LD HL, 0
    LD DE, 1
    LD B, 2
.fibonacci_loop_head:
    CP B
    JP C, .fibonacci_trmp0
.fibonacci_loop_body:
    ADD HL, DE
    INC B
    EX DE, HL
    JP .fibonacci_loop_head
.fibonacci_exit:
    RET
.fibonacci_base:
    LD L, A
    LD H, 0
    RET
.fibonacci_trmp0:
    LD H, D
    LD L, E
    JP .fibonacci_exit
```

Results: fib(1)=1, fib(2)=1, fib(3)=2, fib(5)=5, fib(8)=21, fib(10)=55 ✓

Key techniques: loop with 3 live regs (A=n, HL=prev, DE=curr, B=i), parallel-copy
trampoline for HL↔DE at loop exit, EX DE,HL for swap-in-place.

### 2.2 double_sum — liveness across CALL

```asm
; double(a: u8) -> u8
double:
    ADD A, A
    RET

; double_sum(a: u8, b: u8) -> u8  =  2a + 2b
double_sum:
    CALL double        ; A = 2a; b is in C (ClassGeneral — survives CALL)
    LD D, A            ; spill 2a to D
    LD A, C            ; load b
    CALL double        ; A = 2b
    ADD A, D           ; A = 2a + 2b
    RET
```

Results: double_sum(1,2)=6, double_sum(3,4)=14, double_sum(63,64)=254 ✓

Key technique: b allocated to ClassGeneral (C register) which survives the first
CALL; 2a manually spilled to D before second CALL. The allocator did this
automatically via interference graph: `b` doesn't interfere with `2a` after the
first call, so they can share C and D without coordination.

### 2.4 sum_array — DJNZ peephole

Two equivalent builds of the same function. The peephole is applied at codegen time
to the manual loop — no change to MIR2 IR needed.

**Before peephole** (manual loop):
```asm
sum_array:
    LD A, 0
    LD C, A
.sum_array_loop_head:
    LD A, B            ; load counter
    AND A              ; test B==0
    JP Z, .exit
.sum_array_loop_body:
    LD A, (HL)
    ADD A, C
    LD C, A
    INC HL
    DEC B              ; manual decrement  (← peephole target)
    JP NZ, .sum_array_loop_body   ; (← peephole target)
.sum_array_exit:
    LD A, C
    RET
```

**After peephole** (DJNZ):
```asm
sum_array:
    LD A, 0
    LD C, A
.sum_array_loop_head:
    LD A, B
    AND A
    JP Z, .sum_array_exit
.sum_array_loop_body:
    LD A, (HL)
    ADD A, C
    LD C, A
    INC HL
    DJNZ .sum_array_loop_body    ; ← replaces DEC B + JP NZ
.sum_array_exit:
    LD A, C
    RET
```

T-state saving: `DEC B (4T) + JP NZ (10T) = 14T` → `DJNZ (13T if taken, 8T if not)`.
For a loop of N iterations: saves `(N-1) × 1T` at the taken branches, and gains
`1T` at the final not-taken branch = negligible, but **removes one instruction** from
the hot path and from the binary.

The bigger win is **explicit TermDJNZ** (Phase 3c):

```asm
sum_array_djnz:
    LD A, 0
    LD C, A
    LD A, B            ; 0-check before entering do-while
    AND A
    JP Z, .sum_array_djnz_exit
.sum_array_djnz_loop_body:
    LD A, (HL)
    ADD A, C
    LD C, A
    INC HL
    DJNZ .sum_array_djnz_loop_body  ; do-while: no per-iteration loop_head check
.sum_array_djnz_exit:
    LD A, C
    RET
```

Eliminates the `loop_head` block entirely (saves `LD A,B + AND A + JP` = 14T per
iteration in the body). Correct output: [10,20,30,40,50]→150, [255,1]→0 (u8 wrap) ✓

## 3. Cost Table Architecture — How It Works

The cost table is the bridge between the target-neutral MIR2 IR and the
target-specific register allocator. It's the key to portability.

### 3.1 Interface (in `pkg/mir2/regs.go`)

```go
type CostTable interface {
    Cost(cls RegClass, loc PhysLoc) int
    Locs() []PhysLoc
}
```

That's it. Two methods. The allocator calls nothing else from the backend.

`RegClass` is target-neutral (ClassAcc, ClassCounter, ClassPointer…). `PhysLoc`
is target-specific but opaque to the allocator — it's just a key in the cost matrix.

### 3.2 What the Allocator Does With It

```
Phase 1: collectRegInfo(f)  →  map[Reg]{Ty, RegClass}
Phase 2: BuildInterferenceGraph(f, lr)  →  adj map[Reg]RegSet
Phase 3: Greedy coloring:
    for each Reg (sorted by interference degree ↓):
        forbidden = {PhysLoc of all neighbors already colored}
        candidates = CostTable.Locs() \ forbidden
        pick argmin over candidates: CostTable.Cost(reg.Cls, loc)
        if candidates empty: spill to fresh LocMem slot
```

The cost table is consulted in Phase 3 only. Phases 1 and 2 are completely
target-neutral. This means the interference graph can be reused as-is for any
backend — only the cost function changes.

### 3.3 Z80 Cost Table (4 tiers, all T-state based)

```
Tier 0 — primary regs (0–4T):
  ClassAcc     → A=0, B/C/D/E/H/L=4T, HL=4T, ...
  ClassCounter → B=0, other 8-bit=4T, ...
  ClassGeneral → C/D/E/H/L=0, A/B=2T (penalised so Acc/Counter win)
  ClassPointer → HL=0, DE=4T, BC=6T, ...
  ClassIndex   → DE=0, HL=4T, BC=6T, ...

Tier 1 — IX/IY (+4T DD/FD prefix overhead per instruction):
  ClassIX/IY   → IX/IY=0, other pair=+8T, ...

Tier 2 — shadow regs (EXX overhead ~8T per region):
  ClassShadow  → B'/C'/D'/E'/H'/L'=0, primary=+8T, ...

Tier 3 — stack slot (PUSH 11T + POP 10T = 21T):
  ClassStack   → LocStack=0, LocMem=+4T, ...

Tier 4 — memory $F0xx (LD (nn),r 13T + LD r,(nn) 13T = 26T):
  ClassMem     → LocMem=0, LocStack=+4T, ...
```

Cost source: `pkg/z80timing/` — SSOT for all Z80 T-state constants, table-driven
`Base[256]`, `CBBase`, `EDBase`, `DDBase`. All cost values are derived constants,
not magic numbers.

## 4. PBQP: What, Why, and Pre-Requisites

### 4.1 What PBQP Is

PBQP = Partitioned Boolean Quadratic Problem. In register allocation context it's
used to optimise decisions that have **pairwise interaction costs** — where the best
choice for A depends on what you chose for B.

Greedy allocation (what we use today) assigns each virtual register independently,
considering only interference (hard constraint) and unary cost (soft preference).
PBQP additionally handles **edge costs**: "if A is in register X and B is in register Y,
the cost at every call site between them is Z".

### 4.2 Three PBQP Applications for MIR2

#### 5b — Function Contract Optimisation (interprocedural)

**Problem**: Right now each function's calling convention (which register carries
each param/return) is decided independently. `double_sum` puts `b` in C because
C is the cheapest ClassGeneral slot available. But if `double` could accept its
argument in C instead of A, we'd eliminate the `LD A, C` before each call.

**PBQP formulation**:
- **Node**: each function in the call graph
- **Variable per node**: the register class chosen for each param/return slot
- **Edge (call site)**: cost matrix = "if caller uses ClassX for arg0 and callee
  expects ClassY, the call site pays `moveCost(X→Y) × callFrequency`"
- **Objective**: minimise total register traffic across all call sites

**What we need**:
- Call graph (✅ available from Phase 3d — `m.Funcs` with OpCall links)
- Contract representation that allows the allocator to *choose* the class,
  not just respect a fixed contract (currently contracts are fixed at IR build time)
- Call frequency weights (can start with static count; later: profiler data)

**What we gain**:
- Eliminate adapter moves at hot call sites (`LD A, C` before CALL)
- Co-optimise leaf chains: `caller → double_sum → double` in one pass
- Enables the `isLess` pattern from Phase 2 ABI but generalised to all functions

**Current state**: The `Contract` struct already has `Params[].Class` and
`Returns[].Class`. What's missing is an allocator mode that treats these as
*variables to optimise* rather than *fixed constraints*.

#### 5c — SoA256 Page Assignment

**Problem**: In SoA256 layout `[N]Struct{f0,f1,f2}` → three separate arrays at
aligned 256-byte pages. If f0 and f1 are co-accessed (e.g. `x[i].f0 + x[i].f1`),
they should be on consecutive pages so we can use `INC H` (4T) instead of
`LD H, page2` (10T).

**PBQP formulation**:
- **Node**: each field column array
- **Variable**: page offset (0, 1, 2, ...)
- **Edge cost**: `INC H` (4T) if pages consecutive, `LD H, imm` (10T) if not
- **Edge weight**: co-access frequency

**What we need**:
- SoA256 codegen for `INC H` / `INC L` (✅ `OpPtrBump` with stride=-1/256)
- Access frequency data (static analysis or profiler)
- Verifier: `Len≤256`, global-only, `Align=256` constraints (stub in place)

#### 5d — Bank Switching (128K targets)

**Problem**: ZX Spectrum 128K / MegaROM has 8 RAM banks + 4 ROM banks. Calling a
function in a different bank requires a bank-switch syscall (~50T overhead). Functions
called together should be in the same bank.

**PBQP formulation**:
- **Node**: code block or data segment
- **Variable**: bank number (0–7)
- **Edge**: inter-block call/reference — cost 0 if same bank, 50T if not
- **Objective**: minimise total bank switches weighted by execution frequency

**What we need**:
- Call graph (✅)
- Code size estimation per function (approximate from assembly output)
- Bank capacity constraints (16KB per bank)
- 128K target backend (not yet implemented)

### 4.3 Pre-Requisites Summary

| Application | Hard pre-req | Optional improvement |
|-------------|-------------|---------------------|
| 5b contracts | Mutable Contract class fields | Call frequency weights |
| 5c SoA256 pages | Access frequency data | Profiler integration |
| 5d bank switching | Code size estimation | 128K backend |
| All | PBQP solver | — |

The only universal pre-req is a PBQP solver. For N functions/arrays/segments with
K choices each, PBQP is NP-hard in general but tractable for the sizes we have:
- 5b: typically 5–20 functions, 2–4 params each → trivially small
- 5c: typically 2–8 fields per struct → trivially small
- 5d: typically 20–100 code blocks, 8 banks → small; can use Fiduccia-Mattheyses

For these sizes, **brute-force enumeration works**:
- 5b with 10 functions × 4 slots × 5 class choices = 5^40 ... too big
- But: independent subproblems (leaf functions have no edges) + dynamic programming
  on the call tree → O(K^depth) where depth is typically 3–5
- 5c: 8 fields × 8 pages = 8^8 = 16M cases → brute force in <1 second

## 5. Cost Table Portability for Other Architectures

The `CostTable` interface is already loosely coupled. Implementing a new backend
requires only:

1. A `[]PhysLoc` listing all physical locations
2. A `Cost(cls RegClass, loc PhysLoc) int` function
3. A `<target>codegen.go` that maps `PhysLoc.Name` strings to instruction emission

The `RegClass` values are target-neutral by design. Here's how they map:

### 5.1 eZ80 (Agon Light 2)

eZ80 is backward-compatible with Z80. The Z80 cost table works as-is.
Additional considerations:
- 24-bit address mode: `ClassPointer` should prefer HL in 24-bit mode (cost 0)
- `LDIR.L` instruction for 24-bit block transfers
- Shadow registers: eZ80 has same EXX/EX AF,AF' as Z80
- **Cost table delta**: add LocReg entries for `HLU`/`DEU`/`BCU` (upper 8 bits of 24-bit pairs)

```go
type EZ80CostTable struct{}
func (EZ80CostTable) Locs() []PhysLoc { return append(Z80PhysLocs, ez80ExtraLocs...) }
func (EZ80CostTable) Cost(cls RegClass, loc PhysLoc) int {
    // Delegate most to Z80CostTable, override 24-bit pointer cost
}
```

### 5.2 6502 / 65C02

6502 has 3 registers: A (accumulator), X, Y (index). Much more constrained.

```
ClassAcc      → A = 0     (only reg that can do ALU)
ClassCounter  → X or Y = 0  (DEX/DEY for counting; no DJNZ equivalent)
ClassGeneral  → X or Y = 4T (TAX/TXA 2T + TAY/TYA 2T)
ClassPointer  → zero-page (u8 addr in ZP, indirect via (zp,X)/(zp),Y)
ClassMem      → absolute address (3B/4T load, 3B/4T store)
```

Stack is only 256 bytes, software-managed. No 16-bit regs.
ClassIndex/ClassPair/ClassIX/ClassShadow → InfCost.

The cost table would be much sparser (most class/loc combinations are InfCost),
but the interface works identically.

### 5.3 SM83 (Game Boy)

SM83 is a Z80 subset. Key differences:
- No `EX DE,HL` (remove EX DE,HL from parallel copy; use register-move sequence)
- No undocumented IXY halves (ClassIXY8 → InfCost for all locs)
- No shadow registers (ClassShadow, ClassAccShadow → InfCost)
- No `OUT`/`IN` instructions (use memory-mapped I/O instead)
- `ADD SP, e` exists; `LD HL, SP+e` exists → useful for frame locals

```go
type SM83CostTable struct{}
func (SM83CostTable) Locs() []PhysLoc {
    // Z80PhysLocs minus IX/IY/IXY8/shadow
    return sm83Locs
}
func (SM83CostTable) Cost(cls RegClass, loc PhysLoc) int {
    // Same as Z80 except IXY8/Shadow → InfCost; IX/IY → InfCost
}
```

The codegen would also need to omit `EX DE,HL` from parallel copy resolution
(use `LD tmp, D; LD D, H; LD H, tmp` sequence instead).

### 5.4 PBQP + Multiple Targets

PBQP is target-neutral by construction: the edge cost matrices are populated by
calling `CostTable.Cost()` on both endpoints. A hypothetical brute-force PBQP
solver for 5b would look like:

```go
type PBQPSolver struct {
    Funcs      []*Func
    CallGraph  map[*Func][]*Func   // caller → callees
    CostTable  CostTable
    ClassOpts  []RegClass           // classes to try for each param slot
}

func (s *PBQPSolver) Solve() map[*Func][]RegClass {
    // For each leaf function: pick min-cost class independently
    // For call edges: iterate all (callerClass, calleeClass) pairs,
    //   accumulate edge cost = moveCost(caller→callee) × callFreq
    // DP up the call tree
}
```

The solver doesn't call any codegen functions — it only uses `CostTable.Cost()`.
This means the same solver runs identically for Z80, SM83, 6502, or any future target.
Only the `CostTable` implementation changes.

## 6. Current Bottleneck and Phase 5 Priority

The current allocator is greedy: it assigns registers independently. For our
current example suite (5–10 functions, 3–5 live ranges each), greedy is optimal
or near-optimal. PBQP gains are measurable only when:

- Functions have constrained register windows (high register pressure at call sites)
- The call graph has hot edges (called many times in tight loops)
- Struct layouts have multiple co-accessed field pairs

**Recommended Phase 5 order**:
1. **5b** first — most immediate gain; applies to all programs; mutable contracts
   are a small allocator change
2. **5c** second — applies only to SoA256 programs; needs profiler or static analysis
3. **5d** last — requires 128K backend which doesn't exist yet
