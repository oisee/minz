# Второй потребитель структурного emit: hw.copy

Pointer-ветка `hw.copy` теперь строит HIR напрямую. Единственный новый
примитив — `hir_load(pointer)`: чтение байта из типизированного указателя.
Остальное использует API первого потребителя hw.fill: блоки, объявления,
цикл, присваивания и store. LDIR-ветка продолжает пользоваться текстовым emit.

## Измерения против сохранённого текстового генератора

| Вход | Байты | Такты Z80 |
|---|---|---|
| Две строки по 4 байта с разными strides | 53 → 41 | 637 → 597 |
| Непрерывные 256 байт | 48 → 30 | 45 708 → 30 559 |
| Linear → ZX, строки 7/8 | 53 → 41 | 765 → 725 |

Обычный режим, Grace Speed и Grace Size дают одинаковые результаты.
Каждый вариант разбирается заново; учитывается весь собранный код функции
и исполнение до исходного возвратного PC с восстановленным SP.
Это локальные результаты этих входов, не доказательство пользы во всех копиях.

## Ограничение текущего allocator

Порядок объявлений влияет на назначения указателей. При объявлении source
первым он получал HL, destination — DE: byte store требовал PUSH/POP AF для
сохранения живого счётчика. Первые маленькие замеры замедлялись на 10–12%.
Объявление destination первым даёт HL для записи, DE для чтения и убирает
регрессию в трёх замерах. В коде это решение объяснено комментарием.

Это подтверждённый рабочий выбор генератора, но зависимость от порядка —
отдельная задача для PBQP/выбора машинных кандидатов. Структурный emit сам
не решает распределение регистров и не обещает оптимальный результат.

Матрица HardwareCopy сравнивает всю память с независимым оракулом раскладки
на raw/final MIR VM и собранном Z80. Она включает границы, экранные строки,
пустые области и 255/256 байт. Отдельный native-тест сохраняет динамическое
значение через два вызова генератора. Финальный повтор с новым порядком
объявлений выполняется; до его PASS интеграция не заявляется.
