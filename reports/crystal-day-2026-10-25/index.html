Crystal на Z80:
память, meta
и генераторы.

За сегодня у нас появился работающий путь от настоящего Crystal frontend до Z80 — с arena, borrowed views, общей библиотекой буферов и ленивым обходом. А несколько ошибок, найденных по дороге, превратились в исправления общего компилятора.

Это отчёт о проверенном системном subset. Полный Crystal runtime и stdlib сюда не перенесены.

01 · Язык

Это всё ещё узнаваемый Crystal.

Остаются def … end, выражения, методы, @fields, inference, overloads и macros. Типы и специализации разрешает сам Crystal. Наш адаптер получает уже типизированную программу и переводит поддержанные конструкции в общий HIR; Go-код задаёт представление памяти для target. Сам Crystal compiler написан на Crystal и self-hosted; сейчас его frontend работает отдельным native-процессом и передаёт typed wire в Go compiler. Это ещё не встраиваемая Go-библиотека frontend.

Так Ruby-подобный синтаксис встречается с явной памятью маленькой машины. Struct копируется как значение; указатель продолжает ссылаться на общие bytes. Никакого обязательного GC в этом target-профиле нет: память даёт вызывающая сторона или arena. Вызовы pointerof, разрядности и wrapping operators пока заметны — удобство системного языка ещё предстоит довести.

В прикладном buffer/ring-коде marker-функции уже спрятаны за обычными методами. Native Crystal выполняет fallback, а target вызывает ту же Nanz-библиотеку mem.bytes, которую импортирует Nanz.

Что работает

Маленький, но содержательный профиль

Unsigned byte/word данные, ограниченный signed scalar путь, structs, typed pointers, StaticArray storage, local Slice, методы, циклы, immediate blocks, value-copy и общая backing memory.

Native macros и monomorphization сочетаются с Nanz meta VM. В раннем scalar эксперименте 19 специализаций объединялись в 18 функций по точному совпадению тел.

Граница

Поддержка проверяется по операциям

Heap classes, полная stdlib, произвольные Iterator objects, aggregate returns, yield feedback/send и полный exception cleanup не поддержаны этим bridge.

Есть отдельный raise/rescue → Nanz CY/error probe. Он не доказывает полноценный Crystal unwinding. Команда основного compiler пока не получила универсальный режим .cr: это исследовательский frontend в отдельной ветке.

Фрагмент выполненного ring_early · first/second получены через ring.segments

  reads = 0_u8
  sum = 0_u16
  count = 0_u8
  ring_values(first.to_unsafe, first.size, second.to_unsafe, second.size, pointerof(reads)) do |value|
    sum = sum &+ value.to_u16
    count = count &+ 1_u8
    break if count == 2_u8
  end

Ruby всё ещё прекрасен. Теперь у этой выразительности появилась проверенная дорога к памяти и инструкциям Z80.

02 · Память

Один buffer API для двух frontend.

ТипZ80Смысл
Borrowed View4 BPointer + length. Собственный descriptor, общие bytes.
Bounded Buffer6 BPointer + length + capacity. Проверяемый append.
Ring FIFO8 BPointer + head + length + capacity. Очередь без allocation и division.

На проверенном native host Crystal Slice занимает 16 байт; target view — 4. Host layout не копируется. Для MetaArena поле marker находится на offset 20 у host и на offset 7 у Z80, но чтение возвращает одинаковое значение. Nanz meta-генератор получает именно target offset, sizeof и pointer width.

View копирует pointer/length и разделяет backing memory. После clear буфера старое view сохраняет длину и видит новые записи в те же bytes. Это не продление lifetime: backing allocation должна оставаться живой. Bounds checks и borrow checker решают разные задачи; автоматического borrow checker у нас пока нет.

Ring отдаёт читаемую очередь двумя непрерывными views. Это позволяет обходить wrap без копирования и без нового вида iterator в MIR.

Физическая память

storage · head = 1

312

После pop и push байты лежат в таком порядке.

Логический FIFO

first + second

12+3

Два borrowed диапазона дают очередь 1, 2, 3.

В примере consumer берёт первые два элемента и останавливается. Counter подтверждает ровно два чтения: второй сегмент не затрагивается. Ring пока последовательный — channel protocol, scheduler и синхронизация с IRQ остаются отдельными задачами.

03 · Ленивость

Yield превращается в frame и next.

Обычные Crystal-методы с односторонним yield подключены к существующим HIR YieldStmt и GenForStmt. Общий lowering строит структуру состояния и функцию next(frame, out) → bool. В frame лежат continuation tag, параметры и значения, которым действительно нужно пережить suspension.

Это даёт независимые экземпляры, early stop, next, nonlocal return и конечное потребление бесконечного producer. Для filter + take(2) тесты проверяют число чтений и порядок эффектов, а не только сумму результата.

Финальная веха дня — более точный общий liveness analysis. Временное значение, которое заново вычисляется после resume, больше не обязано жить в frame. При этом сохраняются значения, нужные на loop back edge, после continue и в разных ветках.

Двухсегментный Ring producer

До · 53 байта
После · 13 байт

Размер generator state, а не всей stack/RAM программы. Output, обычные locals и сохранение регистров учитываются отдельно.

Тот же проход полезен Nanz

Отдельный Nanz regression уменьшил frame двухфазного ANF-примера с 8 до 3 байт. Обе MIR2 VM и Z80 сохраняют результат.

Бесконечный counter: 6 → 3 B.
Byte stream остаётся 33 B, RLE — 47 B: здесь адресные выражения пока включают прежний консервативный анализ.

Для address-taking и ещё не моделируемых конструкций остаётся прежний консервативный анализ. Минимальность всех frames не заявляется.

04 · Общая архитектура

Crystal обогатил весь compiler.

Native CrystalParse, normalize, macros, type inference, specialization
Typed adapterЯвно допущенные операции, target layout, library bindings
Общий HIRNanz meta, structs, borrowed views, foreach, generator expansion
MIR2 → Z80Оптимизации, register allocation, assembly и emulator checks

HIR/MIR2, Nanz iterator chains и generator lowering существовали до этой работы. Сегодня Crystal стал ещё одним реальным потребителем этой основы. Появились общая форма addressable borrowed view, библиотека Buffer/Ring и мост к тем же функциям из двух языков.

Macro ↔ meta тоже уже соединены: Crystal делает native macro expansion, а opt-in протокол запускает настоящий Nanz meta VM, который строит HIR. Проверены repeat-генерация и layout-aware byte reader. Универсальный MetaContext и произвольная compile-time reflection ещё не готовы.

Найденная проблемаЧто изменилось в общем compiler
Explicit return не завершал некоторые generatorsSticky DONE и false при завершении; последующие pulls сохраняют output.
Frontend мог передать derived frame, а dump падалОбщий dump принимает ещё не выведенный frame layout.
Адресация поля затирала carry сравненияPending predicate сохраняется до flag-clobbering ADD/INC. Native regression раньше превращал 1 < 2 в false.
В frame попадали заново вычисляемые временные значенияCFG liveness с definition kills уменьшает state для Crystal и Nanz.
Forward EQU мог дать неверный CALLИсправлена сходимость assembler passes; сохранены регрессионные проверки.

Shared byte API использует обычные structs, field loads/stores, pointers и calls. Новые MIR coroutine или ring-buffer opcodes не понадобились. Nanz пока стирает semantic pointee для ^Struct params в публичном HIR; bridge восстанавливает роли self/output по явному контракту API, а не действует как универсальный linker типов.

05 · Машинный код

Иногда прекрасный. Иногда ещё тяжёлый.

Чтение target-поля на offset 7 · 4 инструкции

meta_layout_byte_8_7:
    LD HL, 7
    ADD HL, DE
    LD A, (HL)
    RET

Shared ByteBuffer.clear · 8 инструкций

ByteBuffer_clear:
    LD DE, 0
    INC HL
    INC HL
    LD (HL), E     ; lo
    INC HL
    LD (HL), D     ; hi
    DEC HL
    RET

В этих местах хорошо видна архитектура: target offset стал обычной арифметикой адреса, clear — записями нулевой длины. Но checked try_push в сохранённом листинге занимает 92 инструкций: загрузки полей и сохранение регистров пока дороги.

Это статические инструкции листинга, не executed instruction count, binary size или cycles. Уменьшенный frame даёт измеримое сокращение state; обещать идеальный ASM или ускорение всей программы по этому числу было бы преждевременно.

В этих Crystal-корпусах сравниваются native Crystal, raw MIR2, optimized MIR2 и собранный Z80 в эмуляторе. Для последней liveness-вехи заново выполнены generator и ring корпуса, общие Nanz regressions и независимые FIFO-трассы. Исторические размеры остальных корпусов относятся к сохранённым receipts соответствующих итераций.

Отдельно Go FIFO model проверяет 10 трасс, 3224 операции и 2578 наблюдаемых queue bytes на каждом target engine. Проверяются status, head/length/capacity, порядок сегментов, все backing bytes и canaries. Есть отрицательные контроли типов, schema, неподдержанных операций и проверка file identity через symlink.

Наборы не складываются в процент покрытия языка. Runtime исходного Z80 железа, весь Crystal stdlib и оптимальность кода этими проверками не доказаны.

07 · Применимость

Что у нас теперь есть — и куда это ведёт.

Получился перспективный системный subset Crystal: выразительный frontend над общей низкоуровневой моделью памяти. Для музыкального pipeline уже видны полезные формы: view как окно над событиями, generator как последовательная выдача, ring как очередь или история. Autosiril целиком пока не портирован: его dynamic collections, строки, IO, библиотеки и точность timing потребуют отдельной проверки с Ruby-oracle.

Есть и рабочий host-путь: существующий MIR2→Go backend уже проверен на 1792 scalar/meta наборах Crystal. Это generated Go из нашего IR; сам Crystal compiler в Go не переписан, records и exceptions на Go этим корпусом не подтверждены.

Ближайшие технические направления

Удобство и общие контракты

Более широкий typed buffer/slice API, сохранение pointee metadata, удобные fallible методы, подключение стандартных iteration adapters и уменьшение лишних загрузок/сохранений в ASM.

Macro/meta API стоит довести до обычных typed queries и handles. Lifetime arena/view должен оставаться явным; библиотечные bounds checks не заменяют анализ заимствований.

Идеи из других экосистем

HIR как место встречи

Rust даёт ориентир для compile-time ownership/lifetimes — полезно и на Z80 без runtime borrow checker. JVM-языки напоминают о цене wide integers и сохранении semantic analysis. BEAM — о явных сообщениях, tagged outcomes и backpressure.

Эти frontend и runtimes здесь ещё не реализованы. ANTLR имеет штатный Go target, tree-sitter генерирует C parser; ABAPiti остаётся отдельным compiler/IR, а не готовым адаптером к MinZ HIR.

Главный результат дня — не только новый синтаксис на Z80. У двух frontend появилась общая проверенная память, а реальная программа помогла улучшить общий compiler.
