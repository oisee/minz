# Nanz + C для системного кода Z80

Цель Alice: импортировать C-модули прямо из Nanz, исправить семантику
целочисленных типов и доступа к железу, собрать работающий дисковый пример
с FAT12, проверить его на VM и Z80, интегрировать результат в main
с примерами и документацией.

Исходный main: 8fd39fbe. Работа: feat/system-c-z80. Цель остаётся активной
до выполнения всех пунктов ниже; работающий импорт сам по себе её не закрывает.

## Проверяемые требования

1. Обычный Nanz import находит .c и компилирует его через общий HIR.
   Проверить локальные #include, алиасы, функции, глобальные данные,
   структуры, внутренние вызовы, несколько модулей и диагностику ошибок.
   Исполнение Nanz → C и C → Nanz проверяется на native Z80 и raw/final VM.
2. Z80-модель C: 8-битные char, 16-битные int/short/указатели,
   32-битные long. Проверить знак, продвижения, приведения, переполнение
   unsigned, sizeof, layout, загрузки/записи и начальные значения.
   Неподдержанные конструкции получают явную ошибку, а не подмену типа.
3. Доступ к железу: volatile чтения/записи сохраняют число и порядок событий
   через оптимизации; совместимость с ASM и контрактами прерываний.
   Проверить на наблюдаемом устройстве, включая PC/SP и живые значения.
4. Рабочий дисковый пример: Nanz-приложение использует C-модуль FAT12
   и интерфейс блочного устройства. Проверить реальные данные образа диска,
   mount, каталог, чтение файла и обработку ошибок; если пример записывает,
   сверять итоговый образ независимым host-инструментом.
   Встроенный массив с заранее известным ответом не заменяет дисковый пример.
5. Для каждого сквозного сценария — независимый оракул поведения, native Z80
   и raw/final VM, реальные ASM/BIN и границы памяти. Успешный разбор C
   или успешная сборка сами по себе не доказывают корректность.
6. Примеры и документация явно отделяют поддержанные возможности C89/C99
   от оставшихся ограничений. Обязательные CI проверки проходят; изменения
   слиты в main, итоговая инструкция запуска воспроизводима.

## Порядок

Импорт и глобальные данные → типы/32-битный путь → volatile/устройства →
FAT12 дисковый пример → проверка корпуса и main. Уже имеющиеся возможности
C99 развиваются по требованиям реального примера. Полная совместимость
C11/C23 и многозадачная ОС не подменяют эту цель и остаются следующим этапом.

## Найденные исходные пробелы

- .c отсутствовал в поиске Nanz import.
- unsigned long plus1(65535) возвращал 0 вместо 65536: тип терял 16 бит.
- Глобальная структура {2,513} теряла значение второго поля.
- Исходный код и тесты C уже используют общий backend; для прямой зависимости
  Nanz → C интеграционные тесты C вынесены в внешний Go test-пакет,
  сохранив их случаи и оракулы.

## Открытая семантическая проба

На checkpoint enum проверено: `*pick() += 2` повторяет вызов pick; pre/post
increment и значение assignment expression тоже вычисляют адрес повторно.
Raw VM и native Z80 воспроизводили ошибку. Исправление и сквозные оракулы
описаны в [lvalue evaluation](lvalue-evaluation.md); итоговые общие проверки
и аудит остальных требований продолжаются.

## Финальный стык и аппаратное наблюдение

[Source API](source-api.md) закрывает standalone C CLI → C/Nanz и изоляцию
file-static символов: исходная двухмодульная проба возвращала 26 вместо 28
на VM и Z80. [Local volatile](local-volatile.md) добавляет реальные byte traces
локальных объектов в пределах их времени жизни, включая оба состояния INT.
Все требования выше остаются критериями окончания: текущие отчёты не заменяют
обязательные CI, merge и воспроизводимый запуск на main.
