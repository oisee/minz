# Автоматическая композиция shape-таблиц

13 октября 2026. Подготовка проверяемых назначений без ручного выбора границ.

Раньше клиент должен был перечислить индексы операций, разделяющие функцию
на фрагменты. `ComposeCheckedAutomatically` находит разбиения по размерам
записей исходного пула и существующим move/RET-мостикам. Проверка достижимости
конца отсекает неполные разбиения; глубина ограничена восемью фрагментами.
Число полных разбиений и поиск назначений для каждого ограничены явно заданным
лимитом до 1024. Превышение лимита отменяет подготовку целиком, не отдавая
частичный результат.

`pipeline.ComposeCheckedLocalTables` применяет это к модулю после обычных
MIR/PBQP/PFCCO/Grace проходов. Неподдерживаемые функции (например, caller с CALL)
получают пояснение и остаются на обычном backend. Для leaf-функций строится
точная таблица текущего MIR/ABI; её можно сохранить и подать обычному
`--checked-local-table` selector. Внешний solver не запускается.

Размеры записей задают предложения, а не доказательство совпадения семантики.
Каждый фрагмент и полная функция заново проходят проверку инструкций,
живых значений, scratch, физических aliases и настоящего ABI. Разбиения
не изменяют исходный MIR. Старый ручной API сохраняется.

На weighted с вызывающей функцией автоматически найденное разбиение
воспроизводит 44→20 байт и 238→142 такта caller. Матрица PFCCO greedy/PBQP
× Grace off/on прошла по 256 native-входов. Один исходный пул add5 повторно
проверен на +19/-11/XOR90: caller сохраняет такты 76/76/69; XOR остаётся
на PBQP. Автоматизация не даёт дополнительного ускорения поверх ранее
проверенных назначений, но устраняет ручной выбор каждой границы.

Проверяются пределы, атомарность, подделка подготовленного MIR, огромный
размер записи и неподдерживаемые режимы. CFG, новые пересылки для смены
назначения одного SSA-значения и общий оптимальный поиск ещё впереди.
