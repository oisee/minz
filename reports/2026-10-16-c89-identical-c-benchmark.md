# C89 на Z80: одинаковый исходник, настоящие такты, без старых overclaim

16 октября 2026 года. **На пяти общих примерах SDCC быстрее и компактнее MinZ.**
MinZ правильно исполняет все шесть примеров, включая передачу и возврат маленькой
структуры; выбранные версии SDCC и sccz80 последний исходник не собирают. Это
различие возможностей, а не доказательство превосходства нашего оптимизатора.

C89 practical-good-enough уже интегрирован в main через
[PR #171](https://github.com/oisee/minz/pull/171), main `caa049f9`.
[Аудит допуска](c89-good-enough/completion-audit.md) относится к корректности и
практическому покрытию. Этот новый benchmark отдельно проверяет качество кода.

## Что именно сравнивали

Для каждого инструмента используется **буквально один и тот же C-файл**: никаких
вариантов Nanz, переписанного алгоритма или отдельного ABI-обхода для конкурента.
Шесть [исходников](../research/c89-benchmark/cases/) и их
[SHA256](../research/c89-benchmark/cases/manifest.json) зафиксированы коммитом
`068f3dc6` до измерения. Это небольшие исследовательские функции, не случайная
выборка всех программ и не полный FAT12-драйвер.

| Пример | Нагрузка | Что проверяется |
|---|---|---|
| abs_diff | 2048 пар: все x=0..255, восемь граничных y | Модуль разности |
| gcd | Те же 2048 пар | Евклид вычитаниями, в том числе нули |
| sum_array | Два массива, все длины 0..255: 512 вызовов | 16-битная сумма |
| copy_bytes | Два массива, все длины 0..64: 130 вызовов | Скопированный префикс и неизменный хвост |
| fat12_decode | Два массива, номера кластеров 0..31: 64 вызова | Распакованная 12-битная запись |
| struct_roundtrip | 2048 пар | Factory → структура по значению → consumer → живые значения caller |

Всего 6850 входов на полный набор. Массивы детерминированы; полные значения
сохранены в `workload.json`. SHA нагрузки одинаков между компиляторами и режимами.
Входы не передаются оптимизаторам и не используются для PGO.

Инструменты:

- MinZ: измерительный коммит `ae0feed5`; production-код совпадает с main `caa049f9`.
  Обычный PBQP и greedy contract optimization включены. Три режима:
  default, `OptSize` отдельно, HIR+MIR Grace отдельно. Это не поиск лучшего профиля.
- SDCC **4.2.0 #13081**, пакет Ubuntu `4.2.0+dfsg-1`: `-mz80 --std-c89`,
  отдельно `--opt-code-size` и `--opt-code-speed`. Это доступная установленная
  версия, **не утверждение о последнем SDCC в 2026 году**.
- z88dk/sccz80 **1-83383009-20261016**: `zcc +z80 -clib=classic -compiler=sccz80 -O3 -S`,
  затем обычный z80asm и официальный архив вспомогательных процедур компилятора.
  Это sccz80, отдельный компилятор; не SDCC внутри z88dk.

Точные ревизии, команды и хеш архива находятся в
[toolchains.json](c89-good-enough/identical-c-benchmark/toolchains.json).
Стенд: [инструкция](../research/c89-benchmark/README.md),
[driver](../research/c89-benchmark/run.py), [runner](../research/c89-benchmark/measure.go).

## Результаты на одинаковой нагрузке

Каждая ячейка — **занятые байты / сумма T-states всех вызовов из строки**.
Время включает `execute()`, внутренние CALL, helper routines, запись результата
и RET. Синтетический внешний вызов не входит в замер у всех инструментов.

| C-пример | MinZ default | SDCC size | SDCC speed | sccz80 O3 |
|---|---:|---:|---:|---:|
| abs_diff | 82 / 553 558 | 34 / 264 286 | 34 / 264 286 | 87 / 696 320 |
| gcd | 127 / 17 003 692 | 55 / 4 398 206 | 57 / 4 249 984 | 168 / 28 596 874 |
| sum_array | 360 / 19 897 856 | 325 / 9 929 216 | 326 / 9 798 656 | 375 / 27 157 248 |
| copy_bytes | 250 / 1 669 590 | 214 / 831 090 | 215 / 822 770 | 230 / 1 474 590 |
| fat12_decode | 187 / 37 856 | 149 / 29 184 | 159 / 27 392 | 207 / 57 952 |
| struct_roundtrip | 90 / 985 088 | Не собирается | Не собирается | Не собирается |

MinZ `OptSize` даёт те же байты и такты во всех шести строках. Grace меняет только
`gcd`: 17 003 692 → **16 842 712 T**, около −0,95%, при тех же 127 байтах.
Другие пять строк совпадают с default. Весь набор режимов, включая неудачные
сборки, опубликован в [summary.json](c89-good-enough/identical-c-benchmark/summary.json).
Ни один проигрывающий пример не исключён из таблицы.

На этих пяти общих исходниках MinZ default расходует от **1,30 до 3,87 раза**
больше тактов, чем SDCC size. Против sccz80 у MinZ быстрее четыре примера;
`copy_bytes` у sccz80 быстрее и меньше. Объявлять «MinZ быстрее C-компиляторов»
по этому набору нельзя. Суммарный рейтинг разных задач не вводим: произвольные
веса входов сильно влияли бы на такой рейтинг.

## Что значит «байты» и «проверено»

Размер включает занятые байты образа, связанные helper routines и глобальные/
компиляторские области данных; совпадающие адреса считаются один раз. Незаполненная
DATA SDCC включена, хотя отсутствует в Intel HEX. Фиксированные промежутки между
секциями исключены. Это **не размер COM, не длина HEX и не пик использования стека**.
Например, из 360 байт MinZ sum_array 259 — одинаковые для всех входной массив,
длина и результат; собственно образ вне этих глобалов занимает 101 байт.

Все успешные сборки выполняются на одном Z80-эмуляторе с новой памятью и явными
входами для каждого вызова. Проверены результат, заданные глобальные данные,
неизменные входы, хвост копируемого буфера и возвращение на исходный адрес с
правильным SP. **34 956 native-вызовов — PASS**. У MinZ дополнительно
**41 100 raw/final MIR VM-вызовов — PASS**.

Независимый [host replay](../research/c89-benchmark/check_host.py) компилирует эти
же C-файлы GCC с `-std=c89 -pedantic-errors -O2` и сверяет все **6850 входов** с
численными и памятьными ожиданиями: [PASS](c89-good-enough/identical-c-benchmark/host-oracle.json).
Это проверка ожиданий, а не сопоставление host ABI с Z80 ABI.

Стенд не проверяет весь 64-КБ след памяти, прерывания или ULA contention. Здесь
нет libc, BDOS, экранного драйвера и startup. Это голый Z80, а не скорость игры
на Spectrum. Проверка хешей связывает внешний образ с сохранённой сборкой;
подменённый хеш образа отвергается до выполнения с нулём измеренных вызовов.

## Структуры: честная граница сравнения

`struct_roundtrip.c` не переписан под out-pointer. SDCC сообщает
`Function cannot return aggregate` и `cannot pass structure ... as function argument`.
sccz80 предупреждает о преобразовании возвращаемой структуры в указатель и
останавливает сборку на вызывающем коде. Диагностики сохранены:
[SDCC](c89-good-enough/identical-c-benchmark/sdcc/struct_roundtrip/build.log),
[sccz80](c89-good-enough/identical-c-benchmark/sccz80/struct_roundtrip/build.log).

MinZ раскладывает маленькую структуру на скалярные ABI-значения и проходит все
2048 входов в каждом из трёх режимов. Это полезная возможность языка C89. Для
сравнения производительности с конкурентами можно позже добавить **отдельный
одинаковый для всех** C-файл с явным out-pointer. Его нельзя подставлять только
в колонку конкурента и объявлять тем же исходником.

## Что исправлять следующим

Первый конкретный кандидат — доказанное сужение операций после integer promotions.
В C два `unsigned char` расширяются до `int`, и это правильно. Но их диапазон
0..255 позволяет сравнить их байтовой беззнаковой инструкцией, а вычитание перед
возвратом `unsigned char` выполнять по модулю 256.

В [MinZ abs_diff ASM](c89-good-enough/identical-c-benchmark/minz/abs_diff/program.a80)
остались расширения, 16-битные вычитания и ветви для знакового overflow.
[SDCC ASM](c89-good-enough/identical-c-benchmark/sdcc/abs_diff/program.asm)
использует байтовые SUB и короткий переход. В sum_array также видны дорогие
сравнение расширенного индекса и сохранения регистров на каждой итерации.
Это подтверждённые примеры лишнего кода; полный вклад каждого приёма ещё не
изолирован отдельным A/B-замером.

Следующий практический этап: сужать только доказанные диапазоны, проверять границы,
затем повторить **этот замороженный набор** и добавить независимые heldout-задачи.
Идиоматичный Nanz можно сравнивать отдельной колонкой на том же алгоритме, но
основная колонка одинакового C должна сохраниться.
