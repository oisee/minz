# Красиво на Nanz, близко к Z80: декларативные массивы и compile-time специализация

12 октября 2026 года. [Полный разбор Astra](2026-10-12-130-nanz-hardware-arrays-astra.md) · [Antique Toy](https://github.com/oisee/antique-toy) · [Общее состояние компилятора](2026-10-11-092-grace-vm-z80-status.md).

Идея: описывать представление памяти, порядок обхода и операцию над целой областью. Метафункции заранее подготавливают адреса и постоянные данные; методы конкретных типов выражают runtime-операции; backend выбирает проверенное исполнение. Так можно получить удобный библиотечный API без объектов интерфейсов и таблиц виртуальных вызовов в бинарнике. Скорость требует отдельного измерения: выразительный синтаксис сам по себе не убирает все пересылки, вызовы и проверки.

Отчёт публикуется в `main`, но исследовательский код ниже относится к checkpoint [`7061db0b`](https://github.com/oisee/minz/tree/7061db0b). Примеры будущего API обозначены как проекты; они пока не компилируются.

## Что уже работает

- `fun @name` исполняется при компиляции на MIR2 VM. `emit` выдаёт Nanz, который снова разбирается: объявления массивов, функции, операторы и явный ASM. Можно импортировать генераторы и раскрывать их внутри функции.
- Методы конкретного типа и UFCS разрешаются в прямые вызовы. [Typed printing](https://github.com/oisee/minz/blob/7061db0b/stdlib/text/README.md) использует `CText`, `Dec8`, `Dec16` и `BufWriter`; проверка требует конкретных CALL и отсутствия непрямого dispatch.
- Структурные интерфейсы сейчас задают набор имён методов. При интерфейсном параметре parser выбирает единственного подходящего реализатора; несколько реализаций дают ошибку неоднозначности. Это ограниченный статический dispatch, а не универсальная мономорфизация одной generic-функции для любого числа типов.
- Генерация LUT и внутреннее выравнивание массивов уже существуют. Общий пользовательский `@align(256)` ещё нужно добавить и проверить по итоговым адресам.

Старая система MinZ generic/CTIE и текущий Nanz → HIR → MIR2 путь различаются. Наличие реализации в старом semantic-пакете не доказывает доступность того же поведения в Nanz. Для новых библиотек опираемся на проверенные возможности текущего frontend.

## Как это может выглядеть

Следующий синтаксис — **проект направления API**:

```nanz
screen.bytes().walk(storage).fill(0)
attrs.rect(4, 3, 20, 16).walk(rows).fill(0x47)
dst.walk(rows).copy_from(src)
screen.bits().walk(addresses(dots)).or_from(font_bits)
```

`view`, layout и статические размеры не должны создавать выделение памяти во время исполнения. Размещение может быть фиксированным, как `0x4000`, либо символическим; окончательный адрес символа устанавливает assembler, а не compile-time VM.

| Составляющая | Что описывает | Примеры |
|---|---|---|
| Представление | Координаты → адрес и битовое поле | Linear, stride, ZX bitmap, packed bits, mask/data |
| Обход | Порядок чтений и записей | По памяти, по строкам, обратно, tiles, поток адресов |
| Операция | Результат над данными | Fill, copy, move, XOR, masked copy, выборка и упаковка |
| Исполнение | Конкретный машинный примитив | Цикл, LDIR, LDI-группа, compiled stores, разрешённый PUSH |

Один layout обслуживает множество операций. Один подготовленный обход подходит для сферы, dotfield, текстуры или спрайта. Это позволяет переносить строительные блоки Antique Toy в библиотеку, а не писать отдельный генератор каждого эффекта.

Полный ZX bitmap занимает непрерывные 6144 байта: заливка в физическом порядке проста. Копирование картинки из линейного raster-буфера требует перестановки адресов строк. Перекрывающийся `move` и цепочка переносов при scrolling требуют правильного направления; их нельзя свободно переставлять, как одноцветную заливку.

## Интерфейсы и метафункции помогают друг другу

Для первой версии достаточно конкретных типов представлений и существующих генераторов. Например, отдельные `LinearBytes` и `ZXBitmapBytes` могут иметь одноимённые методы; вызов на конкретном receiver разрешается при компиляции. Метафункция знает размеры и layout и создаёт нужный специализированный helper. Динамические данные и координаты остаются runtime-значениями.

Позже можно добавить специализацию generic-функции по конкретному типу layout: один алгоритм, отдельные реализации для linear и ZX. Это требует настоящей проверки многореализационного dispatch, кэширования специализаций и сохранения типовых контрактов; текущего правила «единственный implementor» недостаточно.

Метаданные layout дают backend факты: неизменяемая база, stride, размер области, выравнивание, допустимые записи. Тогда адресный hoist, подбор регистров и варианты развёртки могут опираться на доказанные условия. PFCCO/PBQP и проверенные shape-таблицы остаются кандидатами для машинного выбора; описание layout само по себе не гарантирует их применимость или выигрыш.

Метафункции можно сохранить как удобный интерфейс подготовки, а типизированные операции — как проверяемую runtime-часть. Это достижимый путь к декларативному и гибкому API с малой накладной стоимостью.

## Перегрузка операторов: полезна, но не заменяет интерфейс обхода

В текущем Nanz есть перегрузка операторов через функцию с именем символа:

```nanz
fun +(a: Vec2, b: Vec2) -> Vec2 {
    return Vec2{ x: a.x + b.x, y: a.y + b.y }
}
```

Выражение `a + b` разрешается при разборе в вызов зарегистрированной функции. Существуют также перегрузки для точных пар scalar-типов, например расширяющее умножение. Это отдельный механизм от interface dispatch.

Интерфейс сейчас ожидает имена методов-идентификаторов, поэтому операторное требование `interface Plusable { + }` и метод `. +` не являются реализованным API. `interface Addable { add }` может описывать обычный именованный метод, но автоматически связать его с `+` compiler пока не умеет. Проект trait-бounds и полноценной специализации по реализатору требует отдельной работы.

Операторы подходят для чистых значений: векторов, fixed-point координат, смещений, цветовых значений. Для заполнения, копирования и маскированных записей предпочтительны явные методы: они показывают изменение памяти и позволяют выразить overlap, порядок обхода и разрешённые эффекты. Первую библиотеку layout/fill/copy можно сделать без операторных traits; затем реальный пример определит, нужен ли такой синтаксис.

## Ротозумер уже подтверждает направление

32×48 здесь означает цветовые половинки 8×4: PAPER сверху, INK снизу, общий BRIGHT. Bitmap фиксирован, меняются 768 атрибутов. Это не 1536 полностью независимых цветных пикселей.

| Сохранённый вариант | Размер бинарника | Такты frame 0 |
|---|---:|---:|
| Обычный Nanz | 1291 байт | 2 451 932 T |
| Мета-таблицы и развёрнутая Nanz-строка | 10 447 байт | 1 885 669 T |
| Мета-таблицы и генерируемая ASM-группа из четырёх ячеек | 1616 байт | 312 363 T |

Последний вариант примерно в 7,85 раза быстрее первого. Таблицы и ядро генерируют настоящие метафункции на Nanz; текстура остаётся изменяемой при исполнении. Проверены 32 кадра для ordinary, Grace Size и Grace Speed, все атрибуты, bitmap и возврат с восстановленным SP. Это результат собранного Z80 в эмуляторе; ULA contention, IRQ и полный ROM-loop не входят в измерение. ASM-ядро не имеет VM-оракула: независимая модель сравнивается с native-памятью.

## Первый полезный инкремент

Библиотечная `@fill` со статическими размерами, `u8`, linear/ZX layouts и проверкой границ. Формат метаблока уже поддерживается; самой функции ещё нет:

```nanz
// ПРОЕКТ БИБЛИОТЕКИ
@fill() {
    layout "linear" 0x5800 32 24 32
    region 4 3 20 16
    traversal "rows"
    value 0x47
}
```

Сначала обычные stores и циклы с точным набором разрешённых адресов. Затем copy, mapped-row copy и mask на том же расчёте областей. После этого — выбор LDIR/LDI и специализация спрайтов. Стековые потоки и SMC добавляются после появления проверяемых SP/IFF и patch-site контрактов.

Приёмка: нулевая и единичная длина, границы страниц и строк ZX 7/8 и 63/64, всё содержимое и защитные байты, точные PC/SP, законные Z80-кодировки, размеры и такты. `LDIR` с BC=0 переносит 65 536 байт; безусловное `DI … EI` меняет состояние caller; `clob all` не описывает владение SP или памятью. Эти условия должны быть явными.

Для этого нового IR не требуется. Первый шаг реализуется библиотекой и текущим parser; дополнительные метаданные нужны там, где они дают новую проверяемую гарантию.
