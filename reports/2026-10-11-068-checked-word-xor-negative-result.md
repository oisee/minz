# Проверка word XOR для таблиц: отрицательный результат на настоящем HashMap

Изменять production descriptor ради этого примера не стали. Проверяли неизменённый `examples/nanz/21_hashmap_test.nanz` на базе `85773cf6`: `hash16(key) = key xor (key + 37)`. Обычный MIR2 backend уже выдаёт 11 байт и 55 T, включая `RET`; весь модуль — 981 байт. ABI реального caller: аргумент DE, результат HL.

Обычная CLI генерация таблицы отклоняет hash16: отсутствует word XOR pattern. Эксперимент добавил девять tied вариантов HL/DE/BC, но с ним генератор предложил небезопасный `add_de_nn`, перезаписывающий живой BC. Независимое admission правильно отказало. Выбранного табличного кода нет, 981 → 981 байт. Для безопасной реализации именно folded цепочки понадобилось бы копирование исходного key и отдельное сложение с константой: например `LD H,D; LD L,E; LD BC,37; ADD HL,BC; XOR обеих половинок; RET` — 13 байт / 63 T. Это хуже уже имеющихся `LD HL,37; ADD HL,DE; XOR обеих половинок; RET` — 11 байт / 55 T. Это сравнение конкретных последовательностей, не доказательство глобального оптимума.

Экспериментальный patch и тест сохранены вне Go-build. Девять XOR templates используют шесть инструкций, **24 T / 6 байт**, явно портят A и F, связывают destination с первым операндом; IX/IY не допускаются. Для каждого pattern проверены 65 536 входов на настоящем Z80 emulator: второй операнд получен независимой перестановкой `x*40503+137` по модулю 65536; для совпадающих пар проверено `x xor x`. Это 589 824 проверок, **не** все 2³² пары аргументов. Проверены фактические такты, размер, сохранность rhs, IX/IY и SP. Admission отклоняет живые A, F, H/L aliases и отдельный BC clobber у сложения.

Активный регрессионный тест проверяет исходный hash16 для **всех 65 536 ключей** на VM и Z80 с независимым `uint16(x) xor uint16(x+37)` оракулом. Language Book v7 §3.1 определяет ширину u16, Nanz Language Book §2.8 — битовый XOR. Модульное сложение здесь явно задано как Z80 width oracle: книгу нельзя цитировать как полную формальную спецификацию overflow.

Восемь существующих вызывающих функций проверены на VM и Z80 вместе с реальными calls, register moves/saves и глобальной памятью HashMap. Все вернули 1, SP восстановлен. Такты от входа функции до возврата: put/get 3688, missing 1955, overwrite 4764, two keys 5842, has 4229, count 5015, zero key 3704, many 17876. Это один конкретный corpus example, не общий gate всего компилятора.

Обычная CLI: сборка baseline PASS; генерация возвращает явный `no checked local entries admitted`; применение пустой таблицы PASS и сохраняет ASM побайтно. Производственный API способен сохранить пустую таблицу для диагностического fallback; CLI генерация её не публикует как полезный результат.

Артефакты: `reports/artifacts/checked-word-xor/` — точный исходник, ASM/BIN, текущая пустая таблица, CLI команды/логи, экспериментальный patch/test/native log, SHA256 manifest. Команды воспроизведения ниже запускаются из корня checkout после сборки minzc:

```sh
minzc examples/nanz/21_hashmap_test.nanz --Osize --asserts none -o baseline.a80
minzc examples/nanz/21_hashmap_test.nanz --Osize --asserts none \
  --generate-checked-local-table table.json --checked-local-solver /path/to/z3
# Здесь ожидается отказ: нет admitted entries.
```

Focused native+generation tests PASS 0.291s. Повтор с существующим положительным function-pointer table control PASS 0.775s. Полный pipeline в этой ветке не запускали. Следующий исследовательский вопрос — таблицы для маленьких функций с реальными calls: сначала границы ABI/live values и measured benefit; CFG admission этим экспериментом не расширено.
