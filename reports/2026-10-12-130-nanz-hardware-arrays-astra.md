Я бы развивал Nanz вокруг **представления памяти + порядка обхода + операции над данными**. Это даст общий язык для массивов, экранных областей, текстур, масок и спрайтов. Первый полезный шаг — библиотечная метафункция заливки статической области; существующего пути Nanz → HIR → MIR2 → Z80 для неё достаточно.

Файлы не изменял, агентов не запускал. Прочитал указанные главы, реализацию метафункций и rotozoomer; измерения ниже включают повторное исполнение сохранённого бинарника.

**Что уже существует.** Здесь важно опираться именно на `pkg/nanz`, а не на старый пакет `pkg/metafunction`.

- `fun @name` исполняется при компиляции на MIR2 VM. `emit()` выдаёт текст Nanz, который повторно разбирается. Можно генерировать глобальные массивы, функции и функции с `asm`. Это уже используется в rotozoomer. [Реализация](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/nanz/meta.go#L3).
- Метафункции импортируются; раскрытие внутри функции разбирается в лексическом окружении вызывающего кода. Это позволяет сгенерированным операторам обращаться к локальным переменным. [Разбор раскрытия](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/nanz/parse.go#L3276).
- Вход пока преимущественно текстовый. В действующем пути даже аргументы вызова, записанные числовыми литералами, сначала превращаются в строки в памяти VM. Числа из декларативного блока отдельно доступны через `node_arg_int`. Поэтому `@f(42)` нельзя считать готовым интерфейсом типизированных compile-time аргументов. [Передача аргументов](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/nanz/parse.go#L6155).
- Уже есть распознавание и объединение цепочек `map/filter/forEach`, включая мутацию элементов. Это полезная основа для операций над целыми массивами. [Lowering](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/hir/lower.go#L3083).
- Есть `LUTGen`: вычисление таблицы для подходящей функции с ограниченным диапазоном аргумента. Результат `u16` раскладывается на таблицы младших и старших байтов; при 256 элементах устанавливается `ArrayTy.Align = 256`. Генератор Z80 уже выдаёт `ALIGN`. Общего пользовательского `@align(256)` в просмотренном синтаксисе Nanz нет. [LUTGen](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/mir2/lutgen.go#L3).
- Есть `@smc` у параметров, именованные patch slots и генерируемые функции изменения immediate. Но общий `OpPatch` в Z80 codegen всё ещё содержит TODO. Это отдельные работающие механизмы, а не законченная система безопасной произвольной SMC. [Патчи](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/mir2/z80codegen_inst.go#L1328).

У `AsmStmt` и `AsmExtra` есть входы, выходы и register clobbers. Проверяемых контрактов временного владения SP, состояния IFF и диапазонов изменяемого кода в этих структурах нет. `clob all` таких гарантий не даёт. [Структура ASM](https://github.com/oisee/minz/blob/7061db0b/minzc/pkg/hir/hir.go#L336).

**Предлагаемый интерфейс должен описывать результат и сохранять контроль над исполнением.** Весь следующий синтаксис — проект, сейчас он не реализован:

```nanz
// ПРОЕКТ
comptime let screen = surface(0x4000, zx.bitmap());
comptime let attrs  = surface(0x5800, linear<u8>(32, 24, stride: 32));

buffer.view().walk(forward).fill(0);
buffer.view().walk(forward).map_in_place(|v| v ^ 0x80);
words.view().walk(forward).fill(0x1234);

screen.bytes().walk(storage).fill(0);
screen.bytes().walk(rows).generate(
    |x, y| if (y & 4) == 0 { 0 } else { 255 }
);

attrs.rect(4, 3, 20, 16).walk(rows).fill(0x47);
dst.walk(rows).copy_from(src);          // области не пересекаются
dst.walk(rows).move_from(src);          // сохраняет исходные значения
```

Здесь:

- **Layout** определяет отображение координат в адрес и битовое поле: linear, strided, ZX bitmap, packed bits, interleaved mask/data.
- **Traversal** определяет последовательность посещений: физический порядок, визуальные строки, обратный порядок, столбцы, tiles, таблица адресов.
- **Operation** определяет чтения и записи: fill, copy, masked copy, XOR, преобразование, упаковка, свёртка.

`view()` не должен означать выделение памяти. Статические размеры и layout исчезают после специализации; динамический указатель остаётся обычным параметром. Для `u16.fill(0x1234)` сохраняется семантика элементов, включая порядок байтов.

`screen.bytes()` имеет координаты 32×192, а битовое представление — 256×192. Такое различие предотвращает смешение байтов, пикселей и атрибутных ячеек.

Порядок обхода — часть контракта. Одноцветную заливку можно переставлять; перекрывающееся перемещение, carry-цепочку и обращения к volatile-памяти — только при доказанной эквивалентности. Например, сдвиг изображения влево через `RL` требует прохода байтов строки справа налево и отдельного начального carry для каждой строки.

**Таблицы адресов стоит сделать полноценным библиотечным инструментом.**

```nanz
// ПРОЕКТ
comptime let row_addr = @table(
    y in 0..192 => screen.bytes().address(0, y)
);

comptime let dots = @table(
    p in trajectory => screen.bits().location(p.x, p.y)
);

screen.bits().walk(addresses(dots)).or_from(font_bits);
```

Для ZX байтовый адрес:

```text
base + ((y & 0xC0) << 5)
     + ((y & 0x07) << 8)
     + ((y & 0x38) << 2)
     + x_byte
```

Таблица 192 адресов занимает 384 байта. Представление выбирается под потребителя:

- последовательные little-endian слова удобны для `POP HL`;
- отдельные `lo[]`/`hi[]` удобны для индексирования;
- постоянные адреса можно встроить в инструкции;
- регулярный обход иногда выгоднее таблицы: достаточно `INC H` и известных переходов.

Для произвольной битовой траектории одного адреса недостаточно: нужен также номер бита или маска. Если фаза движения известна лишь во время исполнения, compile-time генерация должна выдавать набор фаз либо заготовку для обновления таблицы; динамические координаты сами собой константами не становятся.

Выравнивание нужно выразить явно:

```nanz
// ПРОЕКТ
@align(256)
global texture: [u8; 256] = [...];
```

Начальная реализация может использовать уже существующий `ArrayTy.Align`. Гарантия должна проверяться по итоговому размещению, с учётом padding. Для адресов символов нужны обычные assembler fixups: метафункция не знает окончательных адресов размещаемых объектов.

Само выравнивание не разрешает любую замену `INC HL` на `INC L`. Последний всегда оборачивает только младший байт. Это правильно для кольца размером 256 или доказанно ограниченного участка; вертикальное оборачивание текстуры требует отдельного решения.

**Маски и compiled sprites естественно получаются специализацией одной операции.**

```nanz
// ПРОЕКТ
screen.bytes().rect(xb, y, w, h)
      .walk(rows)
      .masked_copy_from(graphics, keep_mask);

comptime let draw_ship = @compile_sprite(
    ship,
    layout: zx.bitmap(),
    blend: masked,
    x_shifts: 0..8
);
draw_ship(x, y);
```

Семантика маски должна быть однозначной:

```text
dst = (old_dst & keep_mask) | graphics
```

Тогда генератор может выбрать:

| Известные данные | Генерируемое действие |
|---|---|
| `mask=255`, `graphics=0` | Пропустить запись |
| `mask=0` | Записать непрозрачный байт |
| Смешанная маска | Прочитать, AND, OR, записать |
| Последовательность непрозрачных байтов | Выбрать обычные stores, пары или допустимый PUSH |

Это даёт compiled sprite без отдельного языка спрайтов. Но специализация по `x & 7` не решает переходы строк ZX: нужно учитывать начальное `y`, границы знакомест и третей, clipping. Вариантами остаются таблица строк, общий переход или несколько специализированных случаев.

Сохранение и восстановление фона — обычные копирования между разными layouts. Для перекрывающихся спрайтов порядок сохранения/рисования/восстановления должен быть согласован; его нельзя вывести только из прямоугольников.

**PUSH/POP и LDI должны быть явными стратегиями с проверяемыми предпосылками.**

```nanz
// ПРОЕКТ
dst.walk(forward).copy_from(src, via: z80.ldi_chain(16));

requires interrupts_off
fun clear_fast() {
    screen.bytes().walk(storage_reverse)
          .fill(0, via: z80.push_words);
}
```

Для `LDI` необходимо учитывать расход `HL`, `DE`, `BC` и флагов. Нельзя одновременно использовать `B` как независимый счётчик строк: `LDI` уменьшает весь `BC`. Развёртка группами требует обработки остатка; нулевая длина не должна превращаться в `LDIR` с `BC=0`. Вход в суффикс цепочки возможен без SMC, но требует проверки границ и стоимости вычисления точки входа.

Для стековых потоков нужны более строгие условия:

- **SP один.** POP из источника и PUSH в назначение требуют переключения SP и пакетирования через регистры. Сумма 10+11 T за пару не является полной ценой копирования.
- При `SP=end` инструкция `PUSH HL` оставляет `L` по `end−2`, `H` по `end−1`. Для двух соседних экранных байтов слева должен оказаться `L`. В тексте главы 16 это местами описано наоборот. [Zilog, PUSH](https://www.zilog.com/docs/z80/UM0080.pdf#page=129).
- Пока SP занят потоком, запрещены обычные CALL/RET, стековые spills и сохранения регистров через стек. Начало и конец такого участка должны быть неделимы для codegen.
- Исходный SP восстанавливается до выхода и разрешения прерываний. Сохранять его можно в отдельное слово RAM; SMC для этого необязательна.
- Безусловное `DI … EI` меняет состояние вызывающего кода. Первый вариант лучше ограничить контрактом «вход и выход с прерываниями выключенными». Универсальное сохранение состояния нельзя объявлять решённым коротким шаблоном `LD A,I; DI`: руководство отмечает особенность P/V при прерывании этой инструкции. DI также не блокирует NMI. [Zilog, LD A,I и interrupts](https://www.zilog.com/docs/z80/UM0080.pdf).

RET-chain — отдельное владение SP как потоком адресов переходов. Смешивать его с PUSH-потоком назначения без явного переключения нельзя.

SMC тоже должна быть видна в исходнике:

```nanz
// ПРОЕКТ
@smc(writes: [step_u.imm16, step_v.imm16], reentrant: false)
fun prepare_steps(u: u16, v: u16) {
    patch(step_u, u);
    patch(step_v, v);
}
```

Нужны известные patch sites, writable-размещение, точная ширина записи и правило, исключающее исполнение частично обновлённого операнда. Варианты immediate, opcode patch и генерации нового кода имеют разные контракты. Стоимость подготовки включается в стоимость кадра.

**Фиксированные адреса не создают новых инструкций Z80.** Для записи константного байта допустимы, например:

```asm
LD A, 0x47
LD (0x5800), A
```

или:

```asm
LD HL, 0x5800
LD (HL), 0x47
```

`LD (nn),n` отсутствует. Соседние stores могут переиспользовать A или указатель; выбор зависит от всей последовательности. `LD (nn),HL` записывает два байта и требует подходящей семантики. [Таблица инструкций Zilog](https://www.zilog.com/docs/z80/UM0080.pdf).

**Для текущего rotozoomer эта модель подходит непосредственно.** В [source.nanz](https://github.com/oisee/minz/blob/7061db0b/reports/zx-rotozoomer-kernel/source.nanz#L81) уже разделены подготовка восьми таблиц и генерация четырёх повторений ASM-ядра. Текстура 16×16 копируется на `0xC000`; bitmap фиксирован; 768 атрибутов кодируют 1536 выборок PAPER/INK с общим BRIGHT.

Будущий surface-интерфейс должен выражать именно парную упаковку цветов. Две половины ячейки нельзя трактовать как полностью независимые цветные пиксели. Также нужно сохранить текущую арифметику: `row_step = 2 * trunc(step/2)` для нечётных значений отличается от `step`.

Перспективные эксперименты — распределение регистров, число развёрнутых ячеек, размещение текстуры и, отдельно, явно разрешённое патчирование шагов. Обещать ускорение только от более красивого синтаксиса оснований нет.

Повторное исполнение сохранённого бинарника дало **312 363 T на всех 32 кадрах**. Проверены все 768 атрибутов, 6144 байта bitmap и восстановление SP. Это стоимость `draw_frame` с возвратом, без внешнего CALL, одноразовой инициализации, IRQ и ULA contention; она совпала с [сохранённым результатом](https://github.com/oisee/minz/blob/7061db0b/reports/zx-rotozoomer-kernel/native/ordinary/result.json). При 3,5 МГц это около 89 мс вычисления, а не измеренная частота кадров полного `main`.

Дополнительно измерил конкретные машинные последовательности для 256 байт:

| Последовательность | Код, байт | T, включая подготовку и RET |
|---|---:|---:|
| Заливка: store + `INC HL` + `DJNZ` | 12 | 6685 |
| Заливка: полная развёртка stores | 517 | 3349 |
| Заливка: первый байт + `LDIR` | 14 | 5400 |
| Заливка: 128 PUSH, сохранение/восстановление SP в RAM | 143 | 1478 |
| Копирование через `LDIR` | 12 | 5411 |
| Копирование через 256 `LDI` | 522 | 4136 |

Обёртка исключена; IFF уже выключен; память вне экранной области. Проверены содержимое, соседние защитные байты и SP; источник копирования был непостоянным. Это измерения через имеющийся `mze-f9d06718`, без записи файлов. Установленный в PATH старый `mze` возвращал нулевой счётчик циклов, поэтому его показания отброшены.

Книжные числа не следует переносить в cost model: в главе 6 база 101 T не согласуется с приведённым набором инструкций; в главе 7 оценка около 10 T на атрибутную ячейку не покрывает даже отдельные чтение и запись. А утверждение главы 17 о плавном сдвиге всего изображения изменением только крайних колонок не задаёт корректной операции над всем экраном.

**Первый небольшой инкремент я выбрал бы такой:** новая библиотечная `@fill` на уже существующем формате метаблоков.

```nanz
// ПРОЕКТ БИБЛИОТЕКИ: формат блока уже поддерживается,
// сама метафункция @fill пока отсутствует.
@fill() {
    layout "linear" 0x5800 32 24 32
    region 4 3 20 16
    traversal "rows"
    value 0x47
}

@fill() {
    layout "zx_bitmap_bytes" 0x4000
    region 0 0 32 192
    traversal "storage"
    value 0
}
```

Первый выпуск: только статические размеры, `u8`, два layout, проверка границ и обычные stores/циклы. Он уже полезен для очистки массивов, атрибутных панелей и bitmap-областей. Контракт — точный набор изменённых адресов, без изменения IFF и заимствования SP.

Приёмка: нулевая и единичная длина, границы страниц, строки 7/8 и 63/64, сравнение всей области и окружающей памяти, легальность машинных кодировок, размер и измеренные T. Затем тот же расчёт областей используется для copy, mask и таблиц адресов.

Для этого **новый IR не нужен**. Дескрипторы могут оставаться compile-time структурами библиотеки или frontend и раскрываться в существующие объявления, циклы и `AsmStmt`. Расширение метаданных оправдано там, где появляется новая проверяемая гарантия — alignment, SP/IFF или разрешённые записи SMC. Отдельный «surface IR» стоит рассматривать только после появления конкретной оптимизации, которую существующий путь действительно не может выразить.
