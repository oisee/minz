Как MIDI из Autosiril
добрался до Z80

Начали с вопроса «а можно фронтенд Crystal прикрутить к нашему HIR?». Пришли к общим буферам, ленивым генераторам и MIDI-декодеру, который принимает музыку по байту. Разберём, что уже работает, какой код получается и где здесь дискета TR-DOS.

Музыка оказалась хорошим испытанием компилятора

Можно написать красивый пример с двумя числами, скомпилировать его и радоваться. С MIDI так не получается. В настоящем файле смешаны длины разных разрядностей, последовательности переменной длины, состояние running status, несколько дорожек, текстовые метаданные и системные сообщения.

Время события может давно выйти за 65 535 ticks, хотя сам процессор восьмибитный. Пакет может оборваться на середине длины. А потребитель вправе сказать: «Я ещё не разобрал предыдущее событие, подожди».

Поэтому мы взяли chronos.mid, flim.mid, imrav.mid и tottoro_example.mid из Autosiril и написали потоковый SMF-декодер на Nanz. Его результат сравнили с Ruby midilib 4.0.2. Затем тот же Nanz прошёл через общий HIR до машинного Z80.

Что именно доказано: совпали события, времена и байты payload. Z80 исполнялся в эмуляторе. Сам декодер пока не открывает TR-DOS-файл и не играет звук; дисковый ввод и музыкальный исполнитель — отдельные следующие слои.

Как сюда попал Crystal

Crystal сохраняет узнаваемую Ruby-интонацию: def … end, методы, поля, выражения и блоки. При этом его компилятор написан на Crystal и уже self-hosted — это прямо описано в официальной инструкции по сборке.

В нашем эксперименте мы используем настоящий семантический фронтенд Crystal: он разбирает программу, разрешает типы, overloads и специализации. Исследовательский exporter передаёт выбранные типизированные конструкции в Go-часть компилятора. Там они получают целевой layout и превращаются в HIR.

Это пока ограниченный мост с явным протоколом markers и bindings. Полный Crystal runtime и произвольная stdlib через него не проходят. Зато структуры, arena/pointer-приёмы, borrowed views и часть итерации уже связаны с общей инфраструктурой.

Crystal frontend→Typed export→Go bridge→HIR←Nanz frontend + meta
HIR→MIR2 + оптимизации→Z80

Именно общий нижний слой оказался самым интересным. ByteView, ограниченный ByteBuffer и кольцевой ByteRing можно использовать из разных frontend. На этой базе новый MIDI-декодер написан непосредственно на Nanz. Подключение его удобного API к Crystal bridge ещё предстоит.

Ленивые генераторы тоже уже существуют в общем HIR: состояние хранится в отдельном frame, а потребитель вызывает next. В предыдущей вехе улучшение liveness уменьшило один ring frame с 53 до 13 байт, frame бесконечного счётчика — с 6 до 3. Это размер frame, а не полная оценка RAM или стека приложения.

Маленький подарок от Erlang: поля в битах

В Erlang есть выразительный синтаксис построения и разбора бинарных значений. Для нашего первого шага оказалось достаточно небольшой Nanz meta-функции: описываем поля, получаем структуру и конкретные маски со сдвигами.

import stream.bit_fields
@bit_fields("Header") {
 bits "kind" 3
 bits "flags" 5
}
fun kind(raw:u8)->u8 {
 var out:Header
 Header_decode(u16(raw),&out)
 return out.kind
}

Это работающий код из приложенного probe. Meta-функция исполняется в MIR2 meta VM во время компиляции. На Z80 не попадают ни парсер описания полей, ни строковые имена. Генерируется Header_decode, который раскладывает слово в два байтовых поля.

Имена полей здесь намеренно записаны строками — так устроен текущий block DSL. Поддерживаются до восьми полей, каждое шириной 1–8 бит; общая ширина схемы 8 или 16 бит. В тесте есть и поле, пересекающее границу байта.

Поток — это состояние плюс договор

Главная сложность начинается там, где очередного байта пока нет. Нельзя предполагать, что длина, событие или payload целиком лежат в памяти. Автомат запоминает, что именно он ждёт, и продолжает с этого места при следующем вызове.

SMF-декодер читает заголовок файла, затем заголовки дорожек и события. В цикле события он собирает delta-time, выбирает тип сообщения, принимает данные и выдаёт один готовый результат. Running status позволяет опустить повторяющийся channel status; он сохраняется между подходящими сообщениями и сбрасывается на meta/SysEx.

УПРОЩЁННЫЙ ЦИКЛ СОБЫТИЯ · ЗАГОЛОВКИ ФАЙЛА И ДОРОЖЕК ОПУЩЕНЫ

MORE означает, что байт принят, но событие ещё не собрано. EVENT выдаёт результат. Пока потребитель не вызвал ack(), следующие попытки подачи возвращают BLOCKED с нулевым потреблением.

Это backpressure в очень конкретном виде: одна занятая выходная ячейка. Планировщика и параллельных процессов для такого договора не требуется. Chunk API сообщает точное число принятых байтов: остаток входного блока остаётся у вызывающего кода.

Пустой chunk не означает конец файла. Для EOF есть отдельный finish(). Если поток оборван посреди сообщения, ошибка остаётся sticky до повторной инициализации. Если событие готово, его сначала нужно забрать и подтвердить.

Вот настоящий потребитель на Nanz

В midi_notes.nanz вызывающий код предоставляет 64-байтный payload-буфер, инициализирует декодер и подаёт байты. Ниже — реальная функция из этого примера. Старший байт результата feed_byte содержит consumed, младший — status.

fun midi_byte(byte:u8) -> u8 {
    let result:u16 = parser.feed_byte(byte,&message)
    let status:u8 = u8(result & 255)
    if status == SmfStatus.EVENT {
        let kind:u8 = message.status & 240
        if kind == 144 {
            if message.data2 != 0 { note_ons = note_ons + 1 }
            else { note_offs = note_offs + 1 }
        }
        if kind == 128 { note_offs = note_offs + 1 }
        last_tick = message.tick
        parser.ack()
    }
    return status
}
fun midi_finish() -> u8 { return parser.finish() }

Обрати внимание на NoteOn с нулевой velocity: на проводе это сохраняется как исходный NoteOn, а потребитель считает его NoteOff. Oracle для проверки тоже снимает исходные сообщения до нормализации. Иначе два корректных парсера могли бы казаться различными из-за разных представлений одного музыкального действия.

Данные события простые и пригодные для обычного HIR:

struct MidiEvent {
track:u16, tick:u32, delta:u32, status:u8,
    data1:u8, data2:u8, meta:u8, length:u32
}

tick — абсолютное время внутри дорожки, delta — приращение. Файловые длины и время остаются u32. Тесты доходят до 0xFFFFFFFF ticks и отдельно проверяют отказ при следующем переполнении.

Насколько маленькая память нужна

Сам декодер не выделяет память. Его состояние, событие и буфер предоставляет владелец. Выходной payload копируется в этот буфер и живёт до подтверждения; после ack() сохранённый borrowed view использовать как прежнее событие уже нельзя.

132 байта — состояние SmfDecoder (44), MidiEvent (18), дескриптор ByteBuffer (6) и payload примера (64). Счётчики потребителя, входной сектор, стек и compiler spills прибавляются отдельно.

В дифференциальном harness payload больше — 512 байт, входной chunk — 256 байт. Весь этот harness вместе со статическими данными и вспомогательными функциями собирается в 10 005 байт. Эта цифра не является минимальным размером MIDI-плеера.

Самый большой payload в выбранных четырёх файлах — 44 байта. Для произвольного MIDI это не гарантия: длинный текст или SysEx может быть значительно больше. Сейчас такие события отвергаются до записи payload, если не помещаются в заданную вместимость. Потоковая выдача огромного payload по частям ещё не реализована.

Каждый файл прошёл через сырой MIR2 VM, оптимизированный MIR2 VM и собранный Z80 в эмуляторе. Получилось 86 172 сравнения событий. После каждого готового события во всех трёх движках дополнительно проверяется заблокированная подача до ack().

Независимый oracle — парсер из Ruby midilib, а не переписанная на другом языке копия Nanz-алгоритма. MIDI-ассеты не копируются в репозиторий: сохранены SHA-256, команды и результаты; corpus test получает путь через AUTOSIRIL_MIDI_DIR.

Есть и синтетические проверки: 49 повреждённых/обрезанных SMF-входов на каждый движок, chunk sizes 1…256, защитные байты вокруг payload. Общий пакетный автомат проверен на всех 128 разбиениях небольшого потока и всех восьми позициях головы кольцевого буфера. 557 результатов битовых схем также проверены в трёх исполнениях.

Он обычный, читаемый и пока местами расточительный. Ниже — реальный сгенерированный Header_decode из маленького probe выше. Полный исходник, HIR, MIR2 и ASM приложены к статье.

Видно пять пар SRL D / RR E: helper принимает 16-битное слово и сдвигает пару регистров. Затем идут AND 7, AND 31 и записи полей. Это не виртуальная машина языка на Z80 — это сами маски, сдвиги, загрузки и переходы.

Но для строго восьмибитного входа можно было бы мечтать о более коротком пути с байтовыми сдвигами. В текущем probe промежуточный ABI остаётся u16; показанный результат не следует выдавать за идеальный ручной ASM. Следующий полезный эксперимент — измерить пользу отдельного 8-битного helper или специализации ширины. Измерений скорости здесь пока нет.

Так он может открыть файл на TR-DOS?

Существующие части позволяют спроектировать такой путь, но полного MIDI-прогона с TRD сейчас ещё нет. Декодер уже умеет принимать последовательные порции байтов. В другом участке репозитория уже есть чтение секторов через TR-DOS API traps MZX и пример, который разбирает каталог настоящего TRD-образа и читает CSV в гостевом Z80-коде.

Это пример ABAP CSV → ALV на Spectrum. Там поиск имени, разбор каталога и работа с содержимым выполняются в госте, а MZX предоставляет границу секторного I/O. Отдельные Scorpion-адаптеры тоже прямо помечены как проверка API traps, без обещания совместимости с физическим TR-DOS ROM.

Дисковому адаптеру потребуется хранить текущий сектор, позицию в нём и оставшееся число байтов файла. При готовом событии он сохраняет непрочитанный остаток сектора. В последнем секторе нужно остановиться по длине файла из каталога: padding нельзя выдавать декодеру как продолжение MIDI.

// План соединения, псевдокод — пока не готовый Nanz API.
file = trd_find("IMRAV")
while file.remaining > 0:
    chunk = read_next_sector(file)   // максимум 256 байт
    while chunk.has_remaining:
        status = decoder.feed(chunk.remaining, event, report)
        chunk.advance(report.consumed)
        if status == EVENT:
            consume(event)
            decoder.ack()
        if status == ERROR:
            fail(decoder.error)
decoder.finish()

Для настоящей дискеты на физической машине добавится проверка ROM ABI, workspace, переключения памяти и обработки ошибок диска. Успех через MZX traps не заменяет такую проверку. При этом сам MIDI-автомат от способа получения байтов не зависит: файл, последовательный порт или заранее подготовленный массив могут иметь разные transport adapters.

Что здесь от OTP — и что получает весь compiler

OTP относится к экосистеме Erlang и используется также Elixir. Среди его стандартных behaviours есть gen_server, gen_statem и supervisor. Для нас особенно интересен явный автомат состояний: отдельно состояние, событие, данные и правило перехода.

В эксперименте мы взяли этот инженерный приём. Никаких BEAM-процессов, supervision tree или scheduler на Z80 пока не добавляли. Предсказуемая пауза, sticky fault и явный reset уже полезны для двоичного протокола даже в одном синхронном цикле.

Компилятор тоже получил пользу. Этот пример обнаружил потерю метаданных у локальных ^Struct, потерю элементов импортированных простых enum и пропущенную зависимость &local при HIR-разбиении функций. Исправления общие: они помогают Nanz-программам вне MIDI. Для scalar cells и массивов небезопасное разбиение теперь отвергается, пока нет корректной передачи адресной идентичности.

Новое поведение большей частью выражено через уже существующий HIR: структуры, память, циклы и вызовы. Мы расширили проверенную применимость общего слоя и библиотеки, а не добавили в IR особую инструкцию «декодировать MIDI».

Следующие три проверяемые вехи

TRD → SMF. Соединить каталог и секторное чтение MZX с chunk API. Сравнить события и доказать, что непрочитанные остатки сектора не теряются.

SMF → общий музыкальный timeline. Декодер сейчас выдаёт события в порядке дорожек файла. Плееру нужно объединение по времени и учёт tempo map.

Timeline → звук. Подключить конкретный исполнитель: MIDI-выход, AY или другой синтезатор. Тогда можно будет говорить о проигрывании музыки, а не только о её правильном чтении.

Уже сейчас у нас есть небольшой системный язык, который описывает состояние двоичного потока человеческим кодом и опускается до обычного Z80. А ещё — общий слой памяти и итерации, пригодный для разных frontend. Для идеи, начавшейся с «а Crystal сюда уложится?», это вполне музыкальное продолжение.
