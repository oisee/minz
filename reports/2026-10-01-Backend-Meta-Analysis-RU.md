# Метаанализ backend-компонентов: совместимость, синтез блоками, нужен ли 4-й пайплайн

**Дата/база:** 2026-10-01, `main` на `c84079f7` (после PR #53). **Метод:** три независимых чтения кода (production PFCCO/PBQP/Z80Codegen; LIR/ISLE/WFC; VIR/таблицы/rewrite), ручная перепроверка ключевых утверждений, эмпирический прогон на Z80-эмуляторе через `--asserts z80`, независимая архитектурная критика (Fable) с проверкой корневой причины по коду. Продолжение [отчёта о портфеле](2026-10-01-Backend-Portfolio-Synthesis-RU.md) и [handover](../docs/project/HANDOVER-2026-10-01-BACKEND-PORTFOLIO.md).

## Вердикт в трёх строках

1. Компоненты **не совместимы по принципу «подключи и работай»**: четыре пространства имён локаций, три независимые модели ISA, и ни одна не описывает полностью aliases + tied accumulator + flags + call clobbers.
2. Недостающая четвёртая часть — **не пайплайн, а судья**: дифференциальная проверка «MIR2 VM как спецификация ↔ собранный Z80 на эмуляторе», per-function, исчерпывающе для ≤16 бит входа. Без него «выбрать лучший из трёх» бессмысленно — сегодня `gcd` неправилен на всех трёх путях.
3. Новый 4-й backend сейчас **преждевременен**. Найденный дефект production — модельный (tie аккумулятора не в аллокаторе, блок-локальная liveness в codegen), и дешевле чинить модель внутри production, затем постепенно отделять isel от emit. Слияние LIR+VIR в «pattern backend» — только если судья покажет, что этого недостаточно.

## Новый факт: production PBQP выдаёт wrong code на `gcd`

```nanz
fun gcd(a: u8, b: u8) -> u8 {
    while a != b { if a > b { a = a - b } else { b = b - a } }
    return a
}
```

| Путь | `gcd(12,8)` | `gcd(1,3)` | `gcd(100,75)` |
|---|---|---|---|
| MIR2 VM | 4 ✅ | 1 ✅ | 25 ✅ |
| **PBQP (production, default)** | 4 ✅ | **2 ❌** | **50 ❌** |
| LIR/WFC (`--lir`) | 0 ❌ | 0 ❌ | 0 ❌ |
| VIR (по аудиту 2026-08-21) | 0 ❌ | — | — |

Воспроизводится и из Nanz, и из C. На сетке 14×14 граничных значений production проходит `gcd` в 67/170 случаях; семь соседних функций (`absdiff`, `max`, `min`, циклы со счётчиком, умножение сложением, обмен через временную) проходят все 1 274 прогона — дефект узкий, не «всё сломано». [Августовский аудит](2026-08-21-117-Solver-Architecture-Audit.md) проверял только `(12,8)`: там сначала выполняется ветка `then` (`a=4`), затем один раз `else`, и порча `a` случайно совпадает с верным ответом `4`, поэтому PBQP сочли правильным.

**Корень (проверено по коду).** MIR2 корректен: `%r8 = sub %r4, %r3`, `%r3` жив после. PBQP кладёт `a`=`%r3` в A, `b`=`%r4` в C. В `genBinOp` (`minzc/pkg/mir2/z80codegen.go:3905`) ветка `rhs == "A" && lhs != "A"` выдаёт `NEG; ADD A,C` **без** проверки, жив ли A; соседняя ветка (~3930) такую проверку делает. Но и она слаба: `isVregLiveAfter` смотрит только на инструкции текущего блока и его терминатор — значение, живое в следующих блоках без block-параметра, считается мёртвым. `ComputeLiveness`/`LiveOut` существуют, но codegen их не читает. Ограничение «результат ALU пишется в A» не выражено в PBQP: оно аппроксимируется рёбрами интерференции, class hints и несколькими самостоятельными fixup'ами в codegen.

**Вывод:** баг локальный, причина структурная. Это главный аргумент для решения ниже.

## Инвентарь: что каждый компонент на самом деле моделирует

| | Production (PFCCO→PBQP→Z80Codegen) | LIR (ISLE→isel→WFC) | VIR (table/Z3→PIR) | GPU tables |
|---|---|---|---|---|
| Статус | default | `--lir`, opt-in | offline `vir-oracle` | данные для VIR |
| Локация | `PhysLoc{Kind,Name string,Offset}` | `LocSet uint64`, 37 locs | `LocSet uint64`, 41 loc | 15 locs, свой индекс |
| isel относительно regalloc | **после**, слит с emit (~9k строк) | **до** (greedy pattern) | **совместно** | — (только allocation) |
| Aliases (B↔BC) | hard-coded, **нет IX↔IXH/IXL** | `Loc.Alias` не заполнен — **нет** | hard-coded `pairAliases` | в генераторе |
| Tied accumulator | **не моделируется**, fixups | неявно через `{A}` | явный `TiedDstSrc` (38 паттернов) | в генераторе |
| Flags | `LocFlag` для 1-битных значений | одна loc `F` | loc `F`, без def/use | — |
| Call clobbers | в codegen, не в аллокаторе | `Pattern.Clobbers` | `Pattern.Clobbers` | — |
| Мутирует `*mir2.Module` | `ApplyContracts`, `PreallocCoalesce` | нет | **да** (Grace/FuseAbsDiff/Inline) | — |
| Глобальное состояние | только read-only таблицы | `UseZ3`, `UseLIRContracts`, правила | env `VIR_*`, singletons | — |
| Главная дыра | tie/liveness fixups (gcd) | **молчаливо выбрасывает** `OpNeg/OpNot/Push/Pop/SMC/Asm/Alloca` и прямой вызов без модуля (`translateCall`, `bridge.go:993`); после 4 неудачных попыток валидации **выдаёт ASM с warning**; теряет dataflow block-args | мутации, Z3-PFCCO сломан (ADR-0043) | 6v без надёжного индекса |

Отдельно: две несвязанные реализации ISLE (`pkg/lir/isle` живая; `pkg/rewrite/isle` без импортёров), Grace-правила в production только по `--grace` (default off), `rules/*.grace|*.isle` не загружаются кодом. Собственная VM LIR абстрактна (без aliasing, грубые флаги) — её «convergence» не говорит о Z80.

## Карта швов: где компоненты действительно стыкуются

| Шов | Состояние | Что даёт |
|---|---|---|
| MIR2 + `Contract` | **общий** для всех | единственная реальная общая граница |
| `AllocResult` → `Z80Codegen` | существует; `Allocate` (greedy) уже взаимозаменяем с PBQP | можно подставить другой аллокатор, **но** codegen переопределяет локации (`physOverride`) — оптимальность чужого аллокатора не переносится |
| PBQP → LIR hints | `pbqpToLIRHints` по имени | мягкие подсказки, ABI не фиксирует |
| LIR loc ↔ VIR loc | индексы 0–32 **совпадают**, VIR добавляет `stk0–3` | слияние описаний машины почти бесплатно |
| GPU ↔ VIR | `gpuToZ80Loc`/`z80ToGPULoc` | работает для 8-бит ≤6 vreg; MEM0→-1 не обработан |
| `PhysLoc` ↔ VIR/LIR index | **нет** (только косвенно через имя) | нужен адаптер для любой подстановки таблиц в production |
| Per-function fallback | сплайсинг **текста** ASM | не годится как интерфейс портфеля |
| ISA-модель | **три копии**, расходятся | корень несовместимости |

## Ответы на вопросы

### Могут ли пути работать одновременно и выбирать лучший?

Технически — да (отдельные процессы, иммутабельный вход). Практически — сегодня нечего выбирать: на `gcd` проигрывают все три, а LIR вдобавок сообщает «all compiled». Выбор «лучшего» требует, чтобы каждый кандидат прошёл одного и того же **судью**; тогда правило простое: *среди кандидатов, прошедших судью, взять дешёвый по bytes/T-states; иначе production; иначе ошибка*. Метрики «948/948», «97.9%», «645/645» в CLAUDE.md измеряют завершение пайплайна, а не корректность, и должны быть сняты так же, как ранее сняты VIR-claims.

### Как они могут помогать друг другу (синтез блоками)?

Ранжировано по ценности/усилию. Каждый пункт независимо полезен и проверяем судьёй.

| # | Блок | Откуда → куда | Усилие | Ценность |
|---|---|---|---|---|
| S0 | **Судья**: MIR2 VM ↔ Z80 per function, ABI из Contract/Alloc, исчерпывающе по области определения u8×u8 (до 65 536 входов; для `gcd` — `a,b ≥ 1`, т.к. при ровно одном нуле цикл не завершается и в исходнике), граничная сетка + случайные для шире; бюджет тактов (зависание = FAIL); сброс RAM между входами (SMC); post-state globals; canary-регистры для clobbers; два отрицательных контроля | расширение `production_dual_run_test.go` и `RunAssertsZ80` | дни | **максимальная** |
| S1 | Production: одна `saveAccIfLive`, опирающаяся на `LivenessResult`; NEG-трюк запрещён при живом rhs; `pickScratch8` учитывает live-out | внутри `z80codegen.go` | дни | чинит единственный backend, которым пользуются |
| S2 | LIR честный: молчаливые drop и emit-anyway → ошибка → PBQP fallback | `lir/bridge.go`, `lir/pipeline.go` | часы | без этого LIR-метрики ложны |
| S3 | Единая Z80 ISA spec: из описаний VIR+LIR (индексы совпадают) с aliases, ties, flags def/use, clobbers; адаптер к `PhysLoc`; property-тесты; PBQP alias-check сверяется с ней (закрыть IX-halves) | новый маленький пакет | неделя | фундамент всего остального |
| S4 | Tie аккумулятора как стоимость/ограничение PBQP (а не аппроксимация интерференцией) | `pbqp.go` | неделя | убирает класс багов, а не экземпляр |
| S5 | GPU mul8/mul16 таблицы на уровне MIR2/production codegen вместо текстовой замены в VIR | `vir/mulopt` → mir2 pass | дни | реальный выигрыш тактов (×3: 26T vs ~200T) |
| S6 | ISLE-алгебра LIR (`mul→shift/add`, identities) → MIR2 pass; `load16_le` требует intrinsic | `lir/combine.go` → mir2 | дни | малая, но безопасная |
| S7 | Superoptimizer-доказанные peephole (500 GPU-правил) поверх production | text/MIR | дни | ортогонально, безопасно при судье |
| S8 | Таблицы как точный аллокатор островов ≤6 vreg → `AllocResult` | VIR → production | средне | **низкая**, пока codegen переопределяет локации |

### Нужен ли 4-й пайплайн?

Рассмотрены четыре варианта:

| Вариант | Суть | Оценка |
|---|---|---|
| A. «Судья + закалка production» | S0+S1+S4 | **делать первым**; не новый пайплайн, а 4-я «нога» — проверка |
| B. Production потребляет поток выбранных инструкций | разделить isel (паттерны с явными tie/alias из S3) и emit внутри production, переиспользуя 9k строк emit-знаний | **правильная долгосрочная форма**; инкрементальный рефакторинг, по семействам операций, под судьёй |
| C. Слияние LIR+VIR в pattern-backend | isel-first по общей spec, PBQP по ограниченным доменам, WFC как pruning, таблицы для островов, Z3 offline | только если B упрётся; оба исходника дальше от корректности, чем production |
| D. E-graph/equality saturation над MIR2 с Z80-извлечением | красиво | без доверенной cost-модели (S3) извлечение бессмысленно; последним |

**Ответ:** «нужно ли» — нет, не как отдельная ветка рядом с тремя. Синтез стоит делать **внутрь production** блоками S0–S7, а форма «4-го пайплайна» появится естественно как вариант B: production с отделённым isel и общей ISA spec. Это и есть гармонизация — ISLE, таблицы и VIR-описание машины перестают быть отдельными backend'ами и становятся *поставщиками правил, данных и проверок* для одного пути.

```text
                       ┌──────── S3: единая Z80 ISA spec (aliases/ties/flags/clobbers) ───────┐
                       │                    ↑ из описаний VIR+LIR                              │
HIR → MIR2 ─ S6 ISLE-алгебра ─ S5 mul-таблицы ─ PFCCO ─ PBQP(+S4 tie) ─ isel(B) ─ emit ─ S7 peephole ─ ASM
        │                                                                                        │
        └──────────────── S0 СУДЬЯ: MIR2 VM ≡ Z80 emulator per function ─────────────────────────┘
VIR/Z3, таблицы ≤6v:   offline — генераторы кандидатов и контрпримеров, проходят того же судью
```

## Что удалить или поместить в карантин

- LIR: пути молчаливого drop и emit-anyway; собственная VM как «доказательство» сходимости.
- VIR Z3-PFCCO (сломанное SMT-кодирование, ADR-0043).
- `pkg/rewrite/isle` (нет импортёров) — либо сделать единственным ISLE, либо удалить; `rules/*.grace|*.isle`, которые никто не грузит.
- Метрики завершения пайплайна в CLAUDE.md §4 и таблице метрик, подаваемые как корректность.

Сохранить: `ValidateZ80Asm` (сделать фатальным), описания машины VIR/LIR + `TiedDstSrc` как зерно S3, GPU mul-таблицы, `LivenessResult`, bootstrap из Contract и отрицательный контроль dual-run.

## Границы этого анализа

- Эмпирика — 8 маленьких `u8` функций с двумя аргументами, 1 444 прогона на production Z80; не корпусный замер. Утверждение «дефект узкий» относится к этой выборке.
- Исчерпывающий режим судьи (65 536 входов) предложен, но здесь не реализован и не измерен по времени.
- VIR на текущем main не перезапускался (нужен `z3`); его строка в таблице `gcd` — из августовского аудита.
- Корневая причина `gcd` проверена чтением кода и ассемблера, исправление не написано.
