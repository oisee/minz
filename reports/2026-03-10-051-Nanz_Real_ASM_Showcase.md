# Report #051 — Nanz Compiler: Real Z80 Output Showcase

**Date:** 2026-03-10
**Status:** All examples compiled with `mz file.nanz` — no hand-editing

---

## What this report is

Every code block below is **actual compiler output**, generated by running
`./mz <file>.nanz -o <file>.a80` on the current build.  No assembly was
written by hand.  The goal is to show what the Nanz→MIR2→Z80 pipeline
actually produces today, feature by feature.

## 1. Struct field access — `Color`, `palette`

```nanz
struct Color {
    r: u8
    g: u8
    b: u8
}

global palette: Color

fun set_rgb(rv: u8, gv: u8, bv: u8) -> void {
    palette.r = rv
    palette.g = gv
    palette.b = bv
}

fun get_r() -> u8 { return palette.r }
fun get_g() -> u8 { return palette.g }
fun get_b() -> u8 { return palette.b }
```

**Compiled Z80:**
```z80
set_rgb:
    LD HL, palette
    LD (HL), C          ; palette.r ← rv  (offset 0)
    LD HL, palette
    INC HL
    LD (HL), D          ; palette.g ← gv  (offset 1)
    LD HL, palette
    INC HL
    INC HL
    LD (HL), E          ; palette.b ← bv  (offset 2)
    RET

get_r:
    LD HL, palette
    LD C, (HL)          ; load offset 0
    LD A, C
    RET

get_g:
    LD HL, palette
    INC HL
    LD C, (HL)          ; load offset 1
    LD A, C
    RET

get_b:
    LD HL, palette
    INC HL
    INC HL
    LD C, (HL)          ; load offset 2
    LD A, C
    RET

; globals
palette:
    DB 0, 0, 0          ; 3-byte inline struct in data section
```

**What happened:**
- `struct Color` is a 3-byte record in memory.  Field offsets are computed at
  **parse time** by `makeFieldExpr()` in `pkg/nanz/parse.go`.
- `palette.r = rv` lowers to `OpStore(addr_of(palette) + 0, rv)`.
- `palette.g = gv` → `OpStore(addr_of(palette) + 1, gv)`, implemented as
  `LD HL, palette; INC HL; LD (HL), D`.
- `get_g()` and `get_b()` use `INC HL` chains instead of `ADD HL, DE`
  — correct for small known-constant offsets.
- The global is emitted as `DB 0, 0, 0` (zero-initialized).

**Known gap:** `LD HL, palette` is reloaded for each field in `set_rgb`
instead of reusing HL across stores.  A future `HL-reuse` peephole could
merge those three loads into one.

## 2. UFCS method dispatch — `Acc.add`, no vtable

```nanz
struct Acc {
    val: u8
}

global acc_g: Acc

fun Acc.add(self_ptr: u16, amount: u8) -> u8 {
    self_ptr[0] = self_ptr[0] + amount
    return self_ptr[0]
}

fun Acc.reset(self_ptr: u16) -> void {
    self_ptr[0] = 0
}

fun sum_two(a: u8, b: u8) -> u8 {
    acc_g.reset()        // UFCS: acc_g.reset() → Acc_reset(addr_of(acc_g))
    acc_g.add(a)         // UFCS: acc_g.add(a)  → Acc_add(addr_of(acc_g), a)
    acc_g.add(b)
    return acc_g.val
}
```

**Compiled Z80:**
```z80
Acc_add:
    EX DE, HL           ; self_ptr arrives in HL (ClassPointer)
    LD D, (DE)          ; load self_ptr[0]
    LD A, D
    ADD A, C            ; + amount
    LD C, A
    EX DE, HL
    LD (DE), C          ; store result
    LD C, (HL)
    RET

Acc_reset:
    LD C, 0
    LD (HL), C          ; *self_ptr = 0
    RET

sum_two:
    LD HL, acc_g        ; addr_of(acc_g)
    CALL Acc_reset
    LD HL, acc_g
    LD A, C             ; a
    CALL Acc_add
    LD HL, acc_g
    LD A, mem           ; b  ← this is a known bug: 'mem' sentinel instead of D/E
    CALL Acc_add
    LD HL, acc_g
    LD C, (HL)
    LD A, C
    RET
```

**What happened (and what to notice):**

The MIR2 dump shows the rewrite clearly:

```
fun @sum_two(%r18: u8 [acc], %r19: u8 [general]) -> u8 [acc]
  block @entry:
    %r20 = addr_of @acc_g : ptr [pointer]
    %r21 = move %r20 : Acc [pointer]
    call @Acc_reset(%r21)          ← direct CALL Acc_reset, not through a pointer
    ...
    %r24 = call @Acc_add(%r23, %r18) : u8 [acc]
```

- `acc_g.reset()` became `call @Acc_reset(addr_of acc_g)` — **direct CALL, zero vtable**.
- `acc_g.add(a)` became `call @Acc_add(addr_of acc_g, a)` — same.
- The struct pointer travels in **HL** (ClassPointer per calling convention).
- In `Acc_add`: self_ptr is HL, `self_ptr[0]` = `(HL)`.  The `EX DE,HL` is
  a minor inefficiency — PBQP assigned the load to DE first.

**Known bug:** `sum_two` emits `LD A, mem` for the second argument to the
second `Acc_add` call — `mem` is a literal sentinel, indicating a register
allocation failure for the second argument b.  The first call clobbers the
ClassGeneral slot holding `b`.  This needs a caller-save fix.

## 3. Zero-cost interface dispatch — `Dog.speak`, no vtable

```nanz
interface Animal {
    speak
}

global g_dog: Dog
global g_cat: Cat

fun Dog.speak(self: Dog) -> u8 { return 1 }
fun Cat.speak(self: Cat) -> u8 { return 2 }

fun demo() -> u8 {
    return g_dog.speak()     // UFCS: → Dog_speak(addr_of(g_dog))
}
```

**Compiled Z80:**
```z80
Dog_speak:
    LD C, 1
    LD A, C
    RET

Cat_speak:
    LD C, 2
    LD A, C
    RET

demo:
    LD HL, g_dog
    CALL Dog_speak      ← direct CALL, not JP (HL) or table lookup
    RET
```

**What happened:**
- The `interface Animal { speak }` declaration is recorded in the HIR module
  but generates **zero runtime overhead** — no vtable, no dispatch table.
- `g_dog.speak()` is resolved at compile time to `Dog_speak` because the
  static type of `g_dog` is `Dog`, which implements `Animal`.
- The result: a plain `CALL Dog_speak`.  If you add a `Cat` variant, you get
  a plain `CALL Cat_speak` for that branch.  Same performance as hand-written assembly.

This is CTIE (Compile-Time Interface Execution) — trait monomorphization at
the call site, not virtual dispatch.

## 4. abs_diff: пять оптимизационных проходов до предела

```nanz
fun abs_diff(a: u8, b: u8) -> u8 {
    if a == b {
        return 0          // программист написал как «микро-оптимизацию»
    }
    if a < b {
        return b - a
    }
    return a - b
}
```

### Финальный Z80-вывод (4 инструкции, 18T)

```z80
abs_diff:
    SUB B       ; A = a − b, carry = (a < b unsigned)   4T
    RET NC      ; если a ≥ b → возвращаем a−b в A       11T/5T
.b_minus_a:
    NEG         ; A = −A = b−a                           8T
    RET         ;                                        10T
```

Это **минимально возможный** размер для корректной реализации abs_diff на Z80:
никаких сравнений, никаких переходов кроме условного RET, никаких спиллов.
Итого: 4 инструкции / 6 байт.  Путь «a ≥ b»: 4+5=9T.  Путь «a < b»: 4+11+8+10=33T.

---

### Цепочка проходов: от исходника до предела

#### Шаг 0 — после парсинга и HIR-лоуэринга

MIR2 содержит три блока: `@eq_check`, `@lt_check`, `@a_minus_b`.

```
@eq_check:   eq = cmp_eq(a, b);  br_if eq → @zero, @lt_check
@zero:       ret 0
@lt_check:   lt = cmp_lt(a, b);  br_if lt → @b_minus_a, @a_minus_b
@b_minus_a:  r1 = sub(b, a);  ret r1
@a_minus_b:  r2 = sub(a, b);  ret r2
```

Предполагаемый Z80 (до оптимизаций): ~11 инструкций, 2 CP, 2 JP, 1 XOR A.

---

#### Шаг 1 — BranchEquiv (VM-доказанное удаление ветки)

**Вопрос:** нужна ли ветка `if a == b → return 0`?

Компилятор запускает MIR2-VM для всех 256 пар `(v, v)`:
```
original(v, v) → @zero → returns 0
patched(v, v)  → пропускает @zero → CP C (a<b? нет) → SUB C → returns v−v=0
```
Для всех 256 граничных значений результат одинаков.  Ветка удаляется.

```
@lt_check:   lt = cmp_lt(a, b);  br_if lt → @b_minus_a, @a_minus_b
@b_minus_a:  r1 = sub(b, a);  ret r1
@a_minus_b:  r2 = sub(a, b);  ret r2
```

Сохранено: `JP Z` (10T, 3B) + второй `CP C` (4T, 1B) + мёртвый блок `@zero`.
Итого **−14T, −4 байта**.

---

#### Шаг 2 — CondRetSink

Паттерн: `br_if cond, @then, @else` где `@else` — тривиальный блок возврата
(нет параметров, нет побочных эффектов, единственный предшественник).

`@a_minus_b` удовлетворяет всем условиям:

```
@lt_check:   lt = cmp_lt(a, b)
             r2 = sub(a, b)        ← поднято из @a_minus_b
             cond_ret lt, [r2], @b_minus_a
@b_minus_a:  ...                    ← @a_minus_b теперь мёртв
```

Новый терминатор `TermCondRet`:
- `cond == 0` → вернуть `vals` (путь «a ≥ b»: `r2 = a−b`, сразу возврат)
- `cond != 0` → прыжок в `@b_minus_a`

На Z80 это `RET CC` — условный возврат, без перехода к метке.

---

#### Шаг 3 — applySubSwapNeg

После подъёма `r2 = sub(a, b)` блок `@b_minus_a` ещё содержит `r1 = sub(b, a)`.
Два вычитания с перевёрнутыми операндами — лишняя работа.

Проход обнаруживает: `sub(b, a)` — это операнды `sub(a, b)` в обратном порядке.
Замена: `r1 = neg(r2)`.  На Z80: одна инструкция `NEG` вместо `LD A,B; SUB C`.

```
@b_minus_a:  r1 = neg(r2) [ClassAcc];  ret r1
```

---

#### Шаг 4 — hoistReorderSubBeforeCmp + CmpSubCarry

В блоке `@lt_check` после подъёма Sub порядок инструкций:

```
lt = cmp_lt(a, b)   ← был здесь раньше
r2 = sub(a, b)      ← только что поднят
```

`hoistReorderSubBeforeCmp` переставляет Sub **перед** Cmp:

```
r2 = sub(a, b)      ← теперь первый
lt = cmp_lt(a, b)   ← теперь второй
```

...и одновременно преобразует CmpLt в `CmpSubCarry(r2, b)`:

```
r2  = sub(a, b)            ; A = a−b, carry = (a<b)
lt  = cmp_sub_carry(r2, b) ; = carry из предыдущего Sub, CP не нужен
cond_ret lt, [r2], @b_minus_a
```

`CmpSubCarry` семантика (MIR2 VM): `(r2 + b) ≥ 256` = `(a < b unsigned)` — математически эквивалентно carry из `a−b`.

**Два эффекта:**

1. **CP устранён в Z80-кодогене:** `genCmp` для `CmpSubCarry` ничего не эмитирует — флаг carry уже выставлен Sub.

2. **Спилл `LD C, A` устранён в PBQP:** `a` больше не является операндом `cmp_sub_carry` (Src[0]=`r2`, не `a`), поэтому PBQP не видит конфликта `a(→A)` vs `r2(→A)` и выделяет `r2 → A` без спилла.

---

#### Шаг 5 — Z80-кодоген: финальная склейка

```
sub(a, b) → r2 [A]    : SUB B          (A = a−b, carry = a<b)
cmp_sub_carry(r2, b)  : (пусто)
cond_ret lt, [r2], @b_minus_a:
    return vals: r2 уже в A (return reg) → ничего дополнительно
    RET invertCC("C") = RET NC
@b_minus_a:
    neg(r2) [ClassAcc] : NEG            (r2 в A от Sub — NEG верен)
    ret r1             : RET
```

Итог: `SUB B / RET NC / NEG / RET`.

### Выживание при inline

При инлайне `abs_diff` в вызывающую функцию `TermCondRet` не превращается в
`RET CC` — вместо этого он разворачивается в `TermBrIf`:

```
cond_ret lt, [r2], @then
    ↓  (inline: ret → jmp @cont)
br_if lt, @then(%ta...), @abs_diff_cont(r2)
```

На Z80 условный возврат становится **условным переходом**:

```z80
; abs_diff inlined в caller
    SUB B
    JR NC, .caller_uses_result   ; a ≥ b → r2 = a−b в A → прыгаем к использованию
    NEG                          ; a < b → A = b−a
.caller_uses_result:
    ; A уже содержит |a−b|, продолжаем caller-код без RET/CALL
```

Никакого `CALL abs_diff` / `RET`.  Четыре инструкции остаются теми же самыми,
только `RET NC` → `JR NC, .label`.  Это корректно потому что `TermCondRet` на
уровне MIR2 — абстракция потока управления, а не Z80-специфичная инструкция:
Z80-кодоген сам решает, что эмитировать (`RET CC` или `JR CC`), исходя из того,
является ли текущий контекст функцией верхнего уровня или инлайн-фрагментом.

**Размер abs_diff как standalone: 6 байт.**
**Размер CALL + RET: 3 + 1 = 4 байта.**
Инлайн выгоден по скорости (−17T на call overhead), по размеру — нет для одного
вызова (6 > 4).  PBQP с таблицей T-state косто проголосует за inline при частых
вызовах или при N≥2 call-sites в одном hot-path.

## 5. LUTGen: compile-time loop evaluation → 3-instruction lookup

```nanz
fun popcount(x: u8<0..255>) -> u8 {
    var n: u8 = 0
    var v: u8 = x
    while v != 0 {          // 8 iterations worst case
        n = n + (v & 1)
        v = v >> 1
    }
    return n
}
```

**Compiled Z80:**
```z80
popcount:
    LD H, popcount_lut^H    ; load high byte of page-aligned table address (7T)
    LD L, C                 ; C = input, L ← index (4T)  [H unchanged = page base]
    LD A, (HL)              ; table lookup (7T)
    RET

    ALIGN 256
popcount_lut:
    DB 0, 1, 1, 2, 1, 2, 2, 3, 1, 2, 2, 3, 2, 3, 3, 4, ...  ; 256 bytes
```

**Total: 18T. The while-loop body never runs at runtime.**

What LUTGen did:
1. Detected `u8<0..255>`: range exactly 256 → page-aligned fast path eligible
2. Ran `vm.CallFunc(f, [0..255])` — evaluated the loop 256 times at compile time
3. Emitted `ALIGN 256; DB 0, 1, 1, 2, ...` global table
4. Replaced the function body with: `LD H, sym^H / LD L, C / LD A, (HL) / RET`

The `^H` suffix is MZA syntax for "high byte of address" — since the table is
page-aligned, H holds the page constant, and only L needs to be set to the input.
This avoids `LD HL, addr` (10T) — we save 3T and 1 byte vs the general LUT path.

## 6. forEach with closure capture — DJNZ loop, no CALL overhead

```nanz
fun sum_chain(buf: ^u8, n: u8) -> u8 {
    var s: u8 = 0
    buf.forEach(|x: u8| { s = (s + x) }, n)  // lambda captures outer 's'
    return s
}

fun max_chain(buf: ^u8, n: u8) -> u8 {
    var m: u8 = 0
    buf.forEach(|x: u8| {
        if x > m { m = x }             // conditional capture
    }, n)
    return m
}
```

**Compiled Z80 — `sum_chain`:**
```z80
sum_chain:
    LD D, 0             ; s = 0
    LD B, C             ; B = n (DJNZ counter)
    LD C, D             ; C = s (accumulator in ClassGeneral)
.fe_head:
    LD A, B
    AND A               ; B == 0?
    JRS Z, .fe_exit
.fe_body:
    LD D, (HL)          ; x = *buf
    LD A, C
    ADD A, D            ; s = s + x   [lambda body, inlined]
    LD C, A
.fe_cont:
    INC HL              ; buf++
    DJNZ .fe_body       ; B-- and loop (13T taken / 8T exit)
.fe_exit:
    LD A, C
    RET
```

**Compiled Z80 — `max_chain`:**
```z80
max_chain:
    LD D, 0             ; m = 0
    LD B, C             ; B = n
    LD C, D             ; C = m
.fe_head:
    LD A, B
    AND A
    JRS Z, .fe_exit
.fe_body:
    LD D, (HL)          ; x = *buf
    LD A, C
    CP D                ; m > x ?
    JRS NC, .trmp0
.if_then:               ; (empty — fall through to cont)
.fe_cont:
    INC HL
    DEC B
    LD C, D             ; m = x  [captured: update outer 'm']
    JRS .fe_head
.fe_exit:
    LD A, C
    RET
.trmp0:
    LD D, C             ; restore D=x (undone by copy resolution)
    JRS .if_then
```

**What happened:**

- The lambda `|x: u8| { s = (s + x) }` captures outer variable `s`.
- `hasFreeVars()` detects the free reference to `s` and **skips** standalone
  lowering of the lambda function — it would panic (s not in scope).
- `lowerFusedForEach()` inlines the lambda body directly into the loop,
  threading `s` as a block param.  No `CALL lambda_0`.
- `buf` stays in `HL` throughout (`INC HL` per element, no index arithmetic).
- `n` moves to `B` for `DJNZ` — the tightest possible Z80 loop construct.
- **Per-element cost for sum_chain:** `LD D,(HL)` (7T) + `LD A,C` (4T) +
  `ADD A,D` (4T) + `LD C,A` (4T) + `INC HL` (6T) + `DJNZ` (13T) = **38T**.
  Compare with calling a separate function per element: CALL (17T) + RET (10T)
  alone = 27T overhead before even doing the work.

## 7. GCD — loop with two mutable variables

```nanz
fun gcd(a: u8, b: u8) -> u8 {
    while a != b {
        if a > b { a = a - b }
        else     { b = b - a }
    }
    return a
}
```

**Compiled Z80:**
```z80
gcd:
    LD A, D             ; swap A↔D to match PBQP register assignment
    LD D, C
    LD C, A
.loop_head:
    LD A, C
    CP D                ; a == b?
    JRS Z, .exit_trmp
.loop_body:
    LD A, D
    CP C                ; a > b?
    JRS NC, .else
.if_then:               ; a > b: a = a - b
    LD A, C
    SUB D
    LD C, A
    LD A, C
    LD C, D
    LD D, A
.loop_back:
    LD A, D
    LD D, C
    LD C, A
    JRS .loop_head
.else:                  ; b > a: b = b - a
    LD A, D
    SUB C
    LD D, A
    LD A, C
    LD C, D
    LD D, A
    JRS .loop_back
.exit:
    LD A, D
    RET
.exit_trmp:
    LD A, C
    LD C, D
    LD D, A
    JRS .exit
```

**What happened (honest assessment):**

GCD has two live variables `a` and `b` that are mutated on each iteration.
The loop also has two exit paths (normal + trampoline), creating multiple
parallel-copy chains.  The compiler generates correct output — GCD(12,8)=4,
GCD(35,14)=7, etc. — but there are 8+ redundant `LD A, …; LD x, A` moves from
block-boundary parallel copy resolution.

The PBQP allocator assigns `a → C, b → D` but each block boundary requires
re-synchronizing the physical registers.  Post-allocation coalescing (Phase 6c)
helps for simpler cases; GCD's diamond CFG is still leaving room for improvement.

This is one of the honest gaps: the compiler is correct, not yet optimal for
multi-variable loop mutation.

## Nanz syntax used in this report

```nanz
struct Foo { field: u8 }          // struct declaration
global g: Foo                     // global variable (zero-initialized)
fun Foo.method(self: Foo) -> u8   // method (stored as Foo_method)
obj.method(args)                  // UFCS: → Foo_method(obj, args)
interface I { method }            // zero-cost interface (compile-time only)
fun f(x: u8<0..255>) -> u8        // ranged type → LUTGen candidate
buf.forEach(|x: u8| { … }, n)    // forEach with capturing lambda
```

All examples compile with the current `mz` binary on the `master` branch.
