Мой вердикт: архитектура уже красива; язык узнаваем; качество ASM неоднородно. Маленький reader превращается в четыре инструкции. В сложной arena-функции остаются длинные сохранения регистров и многословная работа со стеком. Это видно в реальном листинге ниже.

01

Какой язык у нас получился?

Уместнее всего назвать его экспериментальным системным профилем Crystal для MinZ. Parser, macros, вывод типов и разрешение overloads остаются нативными. Наш адаптер принимает выбранные конструкции и определяет, как их смысл выразить в HIR и target memory.

Ruby узнаётся в ритме def … end, в выражениях, @fields, вызовах методов и отсутствии синтаксического шума. Crystal добавляет статические типы и compile-time специализацию. Например, один def twice(x); x &+ x; end уже даёт отдельные native специализации для UInt8 и UInt16.

Пока шероховатости хорошо заметны: pointerof, явные разрядности, wrapping operators и специальные marker-функции. Разрядности и владение памятью действительно важны для Z80. Marker-протокол — временный шов интеграции, который хочется спрятать за общим meta API.

Реальный исходник · meta_arena_showcase.cr

def meta_arena_memory(seed : UInt8)
  storage = StaticArray(UInt8, 16).new(0_u8)
  arena = MetaArena.new(storage.to_unsafe, 16_u16)
  p = arena.alloc(3_u16)
  p[0_u16] = meta_repeat(seed, 3_u8, 7_u8)
  arena.set_marker(p[0_u16])
  meta_byte(arena, "marker") ^ seed
end

Ruby всё ещё прекрасен. Его выразительность особенно видна в обработке коллекций. Чтобы сохранить её здесь, нам ещё нужны удобные buffers/slices, lowering блоков и проверенные map/filter/reduce. Сейчас эти возможности нельзя считать частью работающего subset.

И универсальность пока проявляется прежде всего в архитектуре: разные синтаксисы смогут обращаться к общей генерации и backend. Для конкретного языка каждый раз придётся сохранять правила вычисления, ошибок и памяти. Например, числовой ноль в Crystal истинен, а null pointer ложен; это уже проверено нативным oracle и учтено importer.

На target · runtime

Z80 instructions → регистры / stack → buffer + arena → результат

Из semantic AST мы берём уже разрешённые вызовы и специализации. Примитивы становятся HIR operations, методы структуры — обычными функциями с явным self pointer. Layout вычисляется по нашим target types, без переноса host offsets.

Nanz meta-функция исполняется на существующем meta VM во время компиляции. Она генерирует typed HIR; сам target получает обычные инструкции. Meta VM, compiler AST и host allocator в этот target-пример не попадают.

Ниже HIR и optimized MIR2 одного и того же helper. В первом ещё видны локальная переменная и return. Во втором остаются pointer addition и byte load.

HIR · настоящий dump

fun @meta_layout_byte_8_7(base: ptr) -> u8
  var result: u8 = 0:u8
  (result:u8) = load(((base:ptr) + 7:u16):ptr):u8
  return (result:u8)

MIR2 после оптимизации · настоящий dump

fun @meta_layout_byte_8_7(%r164: ptr [pointer]) -> u8 [acc]
  block @entry:
    %r166 = const 7 : u16 [pointer]
    %r167 = add %r164, %r166 : ptr [acc]
    %r168 = load %r167 : u8 [general]
    ret %r168
В scalar spike работают native inference, overloads, ограниченный raise/rescue и exact-body merge: 19 специализаций стали 18 функциями. В record path теперь работают repeat и layout-aware meta helpers. Полная модель exceptions ещё не объединена со всеми record-возможностями.

Уже компактно

Поле по target offset 7

meta_layout_byte_8_7:
    LD HL, 7
    ADD HL, DE

Аргумент base приходит в DE; результат — в A. Пара HL вычисляет адрес, load читает байт. Никаких object headers, lookup таблиц или dynamic dispatch здесь нет.

Уже компактно

То же действие по offset 0

meta_layout_byte_3_0:
    LD A, (HL)
    RET

Здесь base приходит сразу в HL. Нулевое смещение исчезло: остались load и return. Это соседний helper того же модуля, а не вручную написанный образец.

В фактическом helper регистр C после этих загрузок не читается. Видны кандидаты на удаление лишних LD C,7 и объединение цепочки сложений. Для compiler-pass нужно отдельно учесть flags, ABI и wrapping semantics.

Meta развернула цикл успешно — runtime loop больше нет. Но «генерация во время компиляции» не означает автоматически «идеальный машинный код». Оптимизатор ещё должен убрать то, что осталось после генерации и register allocation.

Большая функция показывает цену консервативного codegen

В rec_meta_arena_memory_0 локальные данные занимают 24 байта: buffer на 16 плюс MetaArena на 8. Текущий листинг резервирует их через 24 отдельных DEC SP и освобождает через 24 INC SP. Между вызовами много PUSH/POP и перемещений регистров. Весь текст функции содержит 134 инструкций.

Это многословно. При этом stack adjustment не всегда можно заменить короткой последовательностью без анализа живых регистров и flags. Хорошие следующие цели — frame lowering, более точные clobber sets, byte store/address selection и оптимизация после allocation. Подтверждённых измерений выигрыша по тактам пока нет.

04

Самый важный результат — offset 20 стал offset 7

Native host Crystal24 B / offset 20MetaArena / поле marker · pointer 8 B
Наш Z808 B / offset 7Та же схема полей · pointer 2 B

Программа читает одно и то же значение при разном представлении структуры. Go importer вычисляет target offset, sizeof структуры и pointer width. Эти числа получает Nanz meta-генератор, который строит byte reader.

В том же модуле другая структура, HeaderProbe, имеет marker на offset 0. Это проверяет и правильный layout, и то, что cache не спутал два одноимённых поля. Копирование arena дополнительно проверяет, что helper получает адрес нужного экземпляра.

Здесь MetaArena с дополнительным marker занимает 8 байт. ByteArena предыдущей итерации без этого поля занимает 7; смешивать эти два измерения нельзя.

Честная граница: текущий Crystal macro допускает literal имя marker и pointerof локальной структуры. Native fallback читает соответствующий getter. Это специальный проверенный protocol; общий MetaContext и произвольная field reflection ещё не реализованы.
05

Можно ли пересадить frontend прямо в mzc?

Да — практическое переиспользование уже доказано через отдельный процесс. Crystal compiler написан на Crystal и self-hosted: его собирает предыдущий Crystal compiler. Это подтверждают и установленный исходник compiler, и официальные инструкции сборки.

Сейчас проверочный Python runner запускает Crystal-exporter, сохраняет typed JSON/Lanz и запускает Go-consumer. Production CLI mzc ещё не вызывает exporter самостоятельно. Естественная следующая интеграция — добавить в Go CLI управляемый запуск через os/exec, versioned protocol, source locations и проверку совместимой версии frontend.

.cr → exporter, собранный Crystal → typed JSON / Lanz → Go importer → HIR

«Встроить внутрь Go-процесса» — другая задача. Понадобится C ABI/FFI граница, согласование runtime initialization, GC и владения объектами. Такой вариант мы не проверяли. Переписать весь semantic frontend на Go тоже можно только как отдельный существенный порт.

Наш exporter использует Compiler#no_codegen, но это не делает сам host executable независимым от LLVM: native compiler library всё ещё имеет LLVM dependencies. От target Z80 эта host-инфраструктура отделена. Обновление Crystal потребует повторной проверки внутренних API и семантики адаптера.

06

ABAPiti, ANTLR и Tree-sitter: где мост уже есть?

ABAPiti действительно имеет путь TypeScript → собственный HIR → Go. Frontend использует vendored tsgo. Но его объектный HIR и MinZ HIR — разные IR: ABAPiti хранит богатую объектную семантику, MinZ работает ближе к target memory. Это явное архитектурное решение проекта, а не готовый общий формат.

Поэтому идея перевести TS parser/runtime через ABAPiti интересна как отдельный experiment. Успех на abaplint ещё не доказывает поддержку другой библиотеки: generality probe документирует оставшиеся language/API gaps. Этот путь не превращает Crystal source в Go.

Неожиданный короткий путь: Go backend уже был в MinZ

Проверка репозитория нашла minzc/pkg/mir2go. Мы подключили scalar/meta Lanz к этому backend и получили работающий путь Crystal → HIR → MIR2 → Go, без ABAPiti. Повторный native Crystal reference и generated Go прошли 7 функций × 256 byte inputs = 1792 набора.

Это unsigned scalar/meta corpus. Ни records/arena на Go, ни весь Crystal compiler этим не проверены. Probe отклоняет output с TODO от неподдержанного opcode. Generated Go использует int64 register variables, маски, goto и flat byte heap; host program живёт на обычном Go runtime. «Без GC на Z80» не является обещанием о runtime этой Go-программы.

07

А можно переписать Autosiril?

Музыкальное ядро — разумная следующая цель. Полный converter потребует расширения subset и библиотек. Я посмотрела локальный autooisee.rb: там уже выделены стадии key detection, flattening, ornaments, delays и downmix. Репозиторий Autosiril описывает этот pipeline и указывает autooisee как продолжение разработки.

Для первого переноса я бы выбрала monophonic selection или ограниченную обработку chord/ornament buffers. Это заставит добавить полезные конструкции: slices, нужные операции над small arrays и явную модель Note. Память можно организовать по времени жизни песни, pattern и временных вычислений, сохраняя состояние echo между нужными границами.

В полном Ruby-коде есть midilib, File I/O, strings, вложенные динамические массивы, hashes, сортировка и float-округление MIDI time. Они сейчас не проходят через наш bridge целиком. На Z80 дополнительно нужны streaming и лимиты памяти; обычный host converter можно портировать на полный native Crystal отдельно от этого target-профиля.

Самые интересные риски — музыкальная семантика. В apply_diatonic_transpose используется (note - key) % 12: отрицательные значения требуют правильного modulo. Копирование Ruby objects нельзя механически заменить value-copy structs. А изменение округления tick → row может сдвинуть музыку, даже если код стал быстрее.

Нужен тот же принцип проверки: Ruby как oracle, сравнение промежуточных note events и затем музыкального output. В этой работе Autosiril ещё не портировался; здесь дана оценка по исходнику.

08

Что именно доказано

768 наборов входных данных = 3 сценария × все 256 значений seed. Каждый сценарий выполняется в native Crystal, raw MIR2, optimized MIR2 и Z80 emulator. Сценарии: arena + repeat + marker read; копия структуры и изменение оригинала; чтение поля у двух layouts. Это не 768 возможностей языка.

Дополнительно проверены 7 отказов, а прежние корпуса — 1792 meta-набора и 2372 arena-набора — прошли повторно. Числа не суммируются в процент покрытия языка. Они подтверждают выбранные программы, а не всю stdlib и не оптимальность ASM.
