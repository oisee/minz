Ровесник спектрума: как рендер Autosiril
учился жить в памяти Z80

Один день, две изолированные ветки, 114 честных исполнений, одна найденная причина 62 расхождений — и вовремя нажатая пауза.
2026-10-27 · ветка spike/autosiril-native-render · остановлено на 4% недельного лимита · статья самодостаточна: только HTML+CSS+SVG

Сегодняшний день начался не с кода, а с точки: реализация остановлена, недельный лимит потрачен на 4%, и всё, что описано ниже — это уже сохранённые, проверенные и честно застенографированные результаты, а не приглашение продолжать. Книга к этому моменту была выпущена; оставшийся день ушил на то, чтобы нативная шестая стадия Autosiril — рендер строк трекерной музыки кодом для Z80 — продвинулась от «модели на хосте» до «исполняемого образа с доказанной побайтовой точностью». И это получилось. Частично. Что именно получилось — вся эта статья.

01 · контекстЗачем вообще Ruby и Crystal, если цель — Z80

Проект MinZ давно живёт вокруг одной идеи: много языков — одно промежуточное представление. Оригинальный Autosiril написан на Ruby, и он используется как эталон-оракул: его код заморожен по SHA-256 (autooisee.rb, 41f621b5…1cdd4c01) и только читается. Crystal дал другую линию: вместо написания «ещё одного парсера, похожего на Ruby» был выращен мост к настоящему фронтенду Crystal — inference, перегрузки и специализации выполняет сам Crystal, а закрытый системный сабсет уезжает в Lanz/HIR/MIR2. За двенадцать итераций этот мост накопил доказательства: от 844 случаев native-инференса в первой итерации до 2048 generator-наборов и 525 ring-FIFO наборов в последних; frame генератора сжался с 53 до 13 байт. Это не «весь Crystal на Z80» — это проверенный сабсет с ареной и явным владением, без GC.

Но главный герой дня — не они. Главный герой — нативный рендер Autosiril: шестая файловая стадия конвейера, которая превращает промежуточное kind5-представление песни в текстовые строки трекера, как это делает Ruby-функция render_into_text.

02 · главный дизайнПоток строк, а не песня в памяти

Z80 адресует 64 КБ. Песня Chronos — 3215 ячеек, 1352 строки рендера, 67 600 байт текста. Вывод очевиден: никаких whole-song массивов в RAM. Вместо этого ядро рендера построено как поток с крошечным фиксированным состоянием:

  • три «головы» каналов по 16 байт (bounded window вместо всей дорожки);
  • одна текущая строка из трёх мутабельных нот + два retained/sentinel слота;
  • предыдущие формы и penote, один 52-байтный line-пакет и один 82-байтный state-пакет;
  • на вход — максимум 9216 исходных ячеек, несортированные строки отвергаются.

В файловой CP/M-версии у каждого из трёх читателей — собственные FCB, буфер и позиция: никакой общей DMA-царапалки, которую один курсор испортит другому. Это тот же урок, что и в пятой стадии: «owned cursor ≠ shared scratch».

Вот настоящий код из research/autosiril-native/render/kernel.nanz — не иллюстрация, а строка в строку из репозитория:

// Bounded native Autosiril row renderer. Source/sink byte transports are
// explicit fixture traps reserved for the later independently linked file stage.
global line_packet:[u8;52]
global state_packet:[u8;82]

fun octave_value(note:i16)->i8 {
    if note < 0 { return -1 }
    let divided:i16 = note / 12
    if divided - 1 < 1 { return i8(divided) }
    let result:i16 = divided - 1
    if result > 8 { return 8 }
    return i8(result)
}
fun refresh(index:u8) {
    note_pitch[index] = pitch_value(signed_note(note_note[index]))
    note_octave[index] = octave_value(signed_note(note_note[index]))
    if note_kind[index] == 101 {
        if note_volume[index] >= 1500 {
            note_envelope[index] = env_forms[note_note[index]]
            note_sample[index] = 2
        } else {
            note_envelope[index] = 15
            note_sample[index] = 2
            note_pnote[index] = note_note[index]
        }
        note_enote[index] = i16(note_note[index]) + env_offsets[note_note[index]]
    } else {
        note_enote[index] = -1
    }
}

А вот старт файлового адаптера research/autosiril-native/render/cpm.nanz — обратите внимание на три набора курсорных полей, по одному на читателя:

03 · методЛестница доказательств: каждая ступень — против Ruby

Ключевой принцип дня: зелёная галочка — это не требование. Согласие двух промежуточных представлений не доказывает корректность бэкенда. Поэтому каждая граница проверяется на четырёх исполнителях, и все четверо сравниваются с замороженным оригинальным Ruby, а не друг с другом.

04 · ядро203 случая, 609 исполнений, ни одного лишнего байта

Первый checkpoint дня — строковое ядро рендера доказано целиком. Команда research/autosiril-native/render/prove_kernel.py прогнала 203 случая (по 10 320 строк) на трёх исполнителях — raw MIR2, final MIR2 и собранный Z80, итого 609 прогонов. Каждый ASCII-байт текста (515 988 байт) и каждый байт post-row состояния (794 640 байт) совпали с Ruby. Эмулятор при этом проверял не только результат: контракт возврата, границы PC, пол SP, состояние IRQ, отсутствие записи куда-либо, кроме глобалов/spill/стека, отсутствие исполнения данных, отсутствие лишних портов и канарейки.

Второй checkpoint — верхние границы: случаи 65 535, 65 536, 65 567 строк и пустой вход. 262 174 состояния строк на каждого из трёх исполнителей — и снова побайтовое равенство. Заодно выяснилась милая деталь формата: начиная со строки 65 536 state-пакет растёт с 77 до 79 байт, потому что номер строки перестаёт влезать в u16. Обе исторические кодировки сохранены.

Размер образа ядра — 7 839 байт: 6 961 код, 790 глобалы, 88 spill; пиковый стек — 34 байта. Для машины, где вся адресуемая память — 64 КБ, это не «детали», это и есть дизайн.

05 · файловая стадияИз fault 956 — в 114 зелёных исполнений

Файловая CP/M-стадия в этот день сначала не работала — и это честно зафиксировано: raw-mir2 fault 956 на декодировании END/count/magic, а диагностический «пропуск magic» упёрся в газовый лимит VM и был откачен. Причиной оказались вполне приземлённые вещи: рассинхрон фаз валидации, общий cursor_record_count на всех читателей вместо собственного у каждого и пропущенные теги записей. После точечных правок (без поднятия газа и ослабления framing — иначе это была бы ложная победа) стандартное доказательство prove_cpm.py прошло:

PYTHONDONTWRITEBYTECODE=1 python3 research/autosiril-native/render/prove_cpm.py \
  --artifacts /tmp/minz-ci270-artifacts/autosiril-mix-fresh \
  --autosiril /Users/alice/dev/autosiril \
  --planning  /tmp/minz-render-planning-v4 \
  --out       /tmp/minz-z-workers/render-results/checkpoint5-cpm-n
> PASS 114 actual-kind5 CP/M executions

114 = 25 сохранённых kind5-входов × 3 исполнителя (75 прогонов) + 13 защит × 3 исполнителя (39 прогонов). Chronos точен: 67 600 байт текста и 105 456 байт состояния; пустой вход честно даёт ноль логических байт. Защиты бьют по делу: неверный заголовок, битые definitions, регрессия сортировки ячеек, corruption END/magic, ненулевой физический паддинг и инжекции отказов BDOS на открытии, чтении, создании, записи и закрытии — с точными fault-кодами, проверкой неизменности входа и очисткой живых хэндлов.

Финальный образ — 28 474 байта: 21 589 код + 6 432 глобалы + 453 spill. Контракты зафиксированы письменно: STATE.BIN v1 (length-prefixed строки), META.BIN v1 (компаньон «ARMD», не kind5), REND.INF v1 (логические длины, чтобы нулевой паддинг 128-байтных записей не выдали за полезные байты).

06 · детектив62 расхождения, которые ни в чём не были виноваты

Параллельно разворачивалась лучшая история дня. При одинаковых канонических настройках native-цепочка Chronos расходилась с Ruby на 62 ячейках p-канала: первая разница — строка 259, нота 51/орнамент 4 вместо 58/орнамент 0. Подозревали всех: arrange, echo, mix, компилятор. Что называется, стандартная процедура — каждый алиби проверялся.

Настоящий виновник оказался скучным и оттого красивым: рассинхронизация профиля. Native-цепочка и её референсы были сгенерированы с max_offset 24, а канонический argv Ruby — с max_offset 6 (профиль chronos.mid 2me,1p,1m 8 6 12 0 64 2 6). Механизм расхождения понятен до ноты: Ruby-шный squize_ornament на диаде {58,51} с медианой 7 и фильтром max_offset=6 удаляет смещение 0 и пересаживает всё на ноту 58; native-путь со своим max_offset свернул диаду иначе — и ошибка честно размножилась эхо-копиями.

После явного canonical6-профиля — с перекомпилированным ARRANGE-CANONICAL6.COM и неизменными апстримными ECHO.COM и MIX.COM — паритет наступил на всех границах:

ГраницаСравнение с RubyРасхождений
ARRANGE.BIN@6 (stage 3)lmod0 (2 097 ячеек)
DELAYED.BIN@6 (stage 4)dmod0 (3 215 ячеек)
MIXED.BIN@6 (stage 5, файл)mmod0 (3 215 ячеек)
stage 1–2 (NOTES/EVENTS)переиспользованы проверенные выходыбайт-в-байт

Доказательство переносимо: research/autosiril-native/p-channel-fix/fixtures/canonical6-frozen.json.gz замораживает хэши и ожидания, а replay_canonical6.py перепроверяет всё это без запуска Ruby — при этом fresh-режим сверяет саму заморозку с живым Ruby, так что фикстура не может тихо сгнить в самосогласие. CI-задания встроены в PR #272; на момент передачи запуск 40540793356 был в процессе, и слияние не предполагается, пока не позеленеет обязательное и не будет проверен скачанный артефакт. (Да, и уже ставшая знаменитой фраза дня: green badge ≠ requirements.)

07 · VT2Хост-модель: 267 511 слотов паттернов, без целой строки play-order в потоке вывода

Проверенный результат VT2 сегодня — host-модель. Черновик native-ядра уже сохранён, но успешный сквозной target-прогон пока не подтверждён. Зато модель научилась главному: вывод собирается стримингом — шаблонные литеральные сегменты пишутся как есть, play-order льётся по одной u32-записи из файла порядка, орнаменты — фрагмент за фрагментом, паттерны копируются из spool кусками. Целая header-строка никогда не собирается на пути вывода — она существует только в доказательной статистике, которая считается после записи. Проверено 558 случаев против реального Ruby Step9–11, плюс 548 форсированных коллизий (все паттерны — нули) и 3 канонических варианта Chronos — 267 511 слотов паттернов. Важная тонкость формулировки: коллизия в dedup — это совпадение байтов паттерна, а не музыкальная эквивалентность; полный header как строка — анти-паттерн.

09 · размеры67 600 против 65 280: почему сегментация, а не GC

Один файл TRD — это максимум 255 секторов × 256 байт = 65 280 байт. Чистый текст Chronos — 67 600 байт. Он не влезает в один файл, и это не досадная мелочь, а проектное ограничение, вокруг которого нужно строить дизайн: явную сегментацию вывода или честный отказ по вместимости. Сборщик мусора тут не спасёт — проблема не в утечках, а в ёмкости носителя. (Наивный RLE тоже не спасает: на этом тексте он раздувает 67 600 до 69 822 байт. Сжатие, которое увеличивает файл, — редкий, но поучительный вид искусства.)

Зато связка «bounded арена + span + owned cursors» оказалась именно тем набором абстракций, который Z80-проекту и нужен: фиксированные бюджеты кода/глобалов/spill/стека считаются явно, владение курсорами исключает взаимное повреждение, а отсутствие кучи делает поведение воспроизводимым до байта. Ничего из этого не требует GC — и это, пожалуй, главный переносимый вывод для любого «малого» железа.

10 · урокиЧто забрать с собой

  1. Тесты на границах — осмысленные границы. 65 535 / 65 536 / 65 567 и пустой вход нашли реальное поведение формата (77→79 байт), которое «средний» случай не показал бы никогда.
  2. Оракул обязан быть независимым. Замороженный по SHA-256 Ruby, fresh-прогон против frozen-реплея: два MIR, согласные друг с другом, ничего не доказывают о Z80.
  3. Ступени raw → final → native раздельно. Ошибка в оптимизациях и ошибка в кодогенераторе ловятся на разных ступенях; смешивать их — терять диагноз.
  4. Зелёная галочка ≠ выполненные требования. У CI #272 может позеленеть — это будет означать только то, что прошли заведённые проверки, а не что конвертер готов.
  5. «Не баг, а профиль» — тоже результат. 62 расхождения не были ошибкой компилятора; это спасло от охоты за несуществующим призраком в arrange/echo/mix.
  6. Ёмкость — это дизайн. 67 600 > 65 280 решается сегментацией и явным отказом, а не надеждой. Bounded-арена без GC — правильный сосед для Z80.
