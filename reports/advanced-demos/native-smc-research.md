# Нативный Nanz для compiled sprites: что уже было и чего не хватает

**Продолжение:** [первый рабочий SMC-контракт](native-smc.md) реализует source-вызовы,
типизированный setter и сохранение состояния в VM. Ограничения ниже относятся
к исследовательскому checkpoint этого отчёта.

14 октября 2026. Исследование на `feat/advanced-demos`, checkpoint `7de28857`.
Это проект следующего шага, а не новая реализованная возможность компилятора.
Под «SNC» из вопроса Alice здесь понимается SMC — изменяемые операнды инструкций.

Идея осуществима: описывать запись строки обычным Nanz, постоянные пиксели
специализировать, а изменяемый адрес хранить в инструкции. Часть этой цепочки
уже работает. Не хватает завершённого контракта вызова и структурных patch-sites,
после которых можно безопасно выбирать loop, unroll и compiled stores.

## Реально работающий маленький пример

Этот исходник уже компилируется:

```nanz
struct Row2 { b0: u8, b1: u8 }

fun draw_row(@smc r0: u16) -> void {
    r0^ = Row2{ b0: 195, b1: 60 }
}
```

Полученная строка:

```asm
draw_row:
    LD HL, 0
draw_row$r0$imm EQU $-2
    LD (HL), 195
    INC HL
    LD (HL), 60
    RET
```

Это 9 байт и 46 T от входа до RET без contention и внешнего CALL.
Данные рисунка находятся в инструкциях, а не читаются из массива.
`hir/lower.go` связывает параметр с `PatchSlotNamed`; chained struct stores
дают последовательные записи с одним живым указателем.

Существующий setter тоже генерируется, но только в финальном ASM:

```asm
draw_row_set_r0:
    LD A, L
    LD (draw_row$r0$imm), A
    LD A, H
    LD (draw_row$r0$imm+1), A
    RET
```

Тело занимает **44 T**, а не 24 T, указанные старым showcase.
`LD (nn),HL; RET` для того же слова занимал бы 26 T; этот вариант уже
использует текущая sprite-библиотека. В оба числа не входит внешний CALL.
Старые утверждения «56×» и таблицы ADR не переносим в новые замеры.

Шесть существующих `TestSMCParam_*` снова прошли. Они подтверждают разбор
и форму ASM; сквозной setter → patch → draw ими не проверяется.

Нативный pointer walk тоже уже даёт этот короткий kernel:

```nanz
fun draw(@smc dst: ^u8) {
    var p: ^u8 = dst
    p^ = 0xc3
    p = p + 1
    p^ = 0x3c
}
```

Sol проверил исполнение generated setter и draw на семи адресах в трёх режимах.
Те же 9 байт / 46 T для draw, весь модуль с setter — 18 байт.
Но `dst[0]` / `dst[1]` даёт более дорогую форму: 131 T и 32 байта модуля.
Само наличие одинаковой семантики пока не гарантирует одинаковое качество ASM.

Существующая структурная `@sprite` внутри `draw(@smc dst:^u8)` также даёт
тот же модуль 18 B / draw 46 T: typed HIR и SMC уже соединяются на маленьком
примере. Её pointer-ветка не выпускает текстовые ASM load/store.

Для четырёх одинаковых байтов статический loop с явным pointer walk занимает
223 T / 25 B модуля; тот же индексный loop — 703 T / 41 B. Ни ordinary,
ни Grace Speed/Size не разворачивают эти циклы автоматически. Даже вручную
развёрнутые чтения `const data[0..3]` остаются чтениями данных: 176 T / 51 B.
Значит, специализация массива в instruction immediates — ещё отдельная задача.

## Почему одного hint недостаточно

* HIR сохраняет `SMC` в списке параметров, а lowering исключает его из MIR ABI.
  Обычный call lowering всё ещё передаёт все исходные аргументы. Нужно определить
  и реализовать семантику такого вызова, а не обходить проверку сигнатуры.
  В probes `draw()` отклонён HIR: 0 аргументов вместо 1; `draw(addr)` отклонён
  MIR: 1 аргумент вместо 0. Необъявленный setter может пройти как unknown-symbol
  call; явное extern-объявление конфликтует с резервируемым generated symbol.
* Setter должен существовать до codegen как типизированная функция/операция,
  с известными аргументами и эффектами. Сейчас его позднее ASM-имя не обеспечивает
  HIR-проверку или правильную передачу HL.
* Lowering принудительно делает SMC-параметр указателем; поддержанные типы нужно
  явно ограничить и диагностировать, а не молча игнорировать объявленный тип.
* VM `OpPatchSlot` возвращает адрес хранилища слота, а Z80 загружает значение
  immediate. Прямое использование результата как экранного указателя требует
  согласования этих двух моделей.
* Обычный MIR inliner уже запрещает SMC-операции, сохраняя адресные якоря.
  Для специализации нужны отдельные экземпляры и корректные relocations;
  простое копирование функции с теми же patch symbols не годится.
* Все SMC-параметры сейчас загружаются во входном блоке. Две строки работают,
  но восемь в probe заставили spill породить недопустимый `LD _spill_draw_r6,0`:
  assembler отвергает результат во всех трёх режимах. Для большого рисунка
  нужны загрузки адресов у места использования или специальная модель слотов;
  сохранение всех row pointers одновременно не масштабируется.
* Общий Z80 `OpPatch` пока содержит TODO. Структурный builder пока выпускает
  блоки операторов; определения функций и SMC-параметров им не создаются.
* Measured workload collector сейчас явно отклоняет SMC. Допуск изменяемого
  кода в селектор потребует собственного проверяемого контракта.

## Рекомендуемая форма

Первый шаг сохраняет известные два действия: **разместить** рисунок и **исполнить**
его. Библиотечный объект может скрывать setters, но не смешивает стоимость этих
действий. Если положение не меняется, повторный draw не должен патчить адреса.

На уровне обычной функции `draw_row(addr)` должен сохранять обычный смысл вызова:
получить данный адрес и нарисовать туда. SMC hint может реализовать передачу
через patch + call, с согласованными проверками и VM-семантикой. Это предложение,
не нынешнее поведение. Раздельные place/draw нужны для библиотечного экземпляра,
который намеренно удерживает положение между вызовами.

Следующий пример — проект API, сейчас он не компилируется:

```nanz
let actor = baked_sprite(shape, ZXBitmap)
actor.place(screen_address(x_byte, pixel_y))
actor.draw()
```

`shape` и layout известны при компиляции; адрес верхней строки динамический.
`place` вычисляет его один раз и проходит по строкам правилом DOWN_HL.
Адреса patch-sites символические и постоянные: backend может писать
`LD (patch_symbol),HL`. Наличие pointer walk не означает, что нужно ещё
обходить указателем машинный код.

Необязательно добавлять новый специальный синтаксис для каждого примитива.
Обычные struct/array stores, статические данные и layout-функции уже выражают
смысл. Typed specialization должна подставить известные значения и развернуть
подходящий ограниченный обход. SMC определяет **где хранится изменяемый адрес**,
а запекание определяет **какие значения известны заранее** — это разные решения.

Одна row-функция с одним slot не хранит адреса всех строк: очередной setter
заменяет предыдущий адрес. Последовательность patch → draw для каждой строки
корректна, но оплачивает патч каждый раз. Чтобы отдельно подготовить весь sprite,
а потом исполнить его, специализация должна создать независимые row instances
или объединённую функцию со slots у мест использования. Третий вариант — один
SMC-адрес начала и runtime DOWN_HL при рисовании: меньше патчей, больше работы
на draw. Все три имеют понятную семантику; выбор определяется измерением.

Для полного fill физический порядок 6144 байт проще экранного порядка строк.
Для картинки и масок важна перестановка Spectrum; для overlap, volatile и
carry-зависимых операций сохраняется порядок. Произвольный цикл нельзя
объявлять безопасным для перестановки только потому, что адреса регулярны.

## Минимальный следующий эксперимент

1. Сделать один типизированный SMC slot и accessor видимыми в HIR/MIR,
   согласовать source calls, ABI и VM/native значение слота.
2. Вывести два непрозрачных байта из обычного Nanz; выполнить setter и draw
   через реальные скомпилированные вызовы, проверить всю RAM и PC/SP.
3. Повторить для двух независимых экземпляров, трёх строк и живых caller values;
   исключить общие symbols, неверное удаление слотов и ошибочное сохранение.
4. Добавить восемь строк с одним исходным адресом: compact и inline DOWN_HL.
   Сравнить точный ASM/BIN и **place + draw** с текущим direct kernel.
5. Только затем перенести этот путь под библиотечную поверхность и выбирать
   Speed/Size среди доказанно допустимых реализаций.

В контракт входят writable code, точные изменяемые операнды, lifetime экземпляра,
запрет конфликтующего повторного входа и проверка после peepholes. DI не нужен
автоматически для каждого SMC: важно, способен ли обработчик исполнять/патчить
тот же экземпляр. Подмена SP — отдельный эффект с отдельной проверкой.
Таблицу запретов recursion/ISR из старого ADR нельзя считать действующей
реализацией: отдельный SMC ownership/reentry verifier в проверенном пути не найден.
Native тест должен наблюдать реальные instruction fetches и изменения кода;
успешного VM-теста для этого недостаточно.

Это исследование не заменяет следующую интеграцию пиксельного Tetris. Текущий
измеренный kernel остаётся рабочей базой, пока нативная форма не докажет такую
же корректность и сравнимую стоимость.

## Проверка исследования

Первичный просмотр Astra подтвердил существующий путь parser → PatchSlotNamed →
patcher, затем завершился rate limit. Завершённым независимым ревью Astra этот
результат не считается. Sol xhigh проверил 20 небольших исходников в трёх режимах:
60 результатов компиляции, включая ожидаемые diagnostics и выявленный invalid ASM.
189 запусков setter + draw и ещё шесть caller-сценариев не имеют ошибок оракула.
У caller, который рисует, сам вызов draw сделан через ASM: нативная source-сигнатура
пока не позволяет вызвать его без runtime-аргумента.

Проверяется вся flat 64-КБ RAM с исключением заранее выделенных 16 байт стека,
адресные операнды и возврат PC/SP. Это исследовательские probes с более слабым
stack allowlist, чем точные kernel-тесты предыдущего этапа; они не доказывают
сохранение каждого регистра, ZX address permutation, ROM/ULA или INT/NMI.
Исходники, HIR/MIR, ASM/BIN, symbols, runner и полный JSON сохранены вместе.
Каждый kernel повторно патчится по семи адресам без перезагрузки executable;
проверяется, что EQU действительно указывает на immediate `LD rr,nn`.

Локальные логи и probes: `grace-reports/2026-10-14/native-smc-research/`;
после завершения пакет сохраняется также на `/mnt/safe/minz/grace/2026-10-14/`.
