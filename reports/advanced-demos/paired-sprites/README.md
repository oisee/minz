# Один спрайт — две запечённые процедуры

14 октября 2026. Реализовано в `zx.sprite`; Tetris пока использует сохранённый
shadow-кандидат. Этот этап добавляет прямое маскированное стирание и основу
для миграции игры, а не объявляет её уже работающей на 50 FPS.

Форму описываем один раз. Поле `erase` просит метафункцию запечь также очистку:

```nanz
import zx.sprite

@zx_sprite("Ship") {
    size 16 8
    erase
    pixels "......####......"
    pixels ".....######....."
    pixels "...##########..."
    pixels "..############.."
    pixels ".##############."
    pixels "####__####__####"
    pixels "###...####...###"
    pixels "......####......"
}

fun draw(x:u8,y:u8)->bool {
    let ship:Ship=Ship{x:x,y:y}
    return ship.draw()
}

fun clear(x:u8,y:u8)->bool {
    let ship:Ship=Ship{x:x,y:y}
    return ship.erase()
}
```

`#` рисует единицу, `_` рисует ноль, `.` оставляет пиксель прежним.
Очистка превращает все непрозрачные `#`/`_` в нули, сохраняя `.`.
Поэтому на пустом игровом поле можно стереть движущуюся фигуру, сохранив
соседние пиксели. Если непрозрачная часть спрайта накрыла декоративный фон,
`erase()` этот фон не восстановит: такую задачу должен решать владелец сцены.

Генератор написан на Nanz и эмитит типизированный Nanz: обычные маскированные
записи и pointer walk. Native SMC закрепляет адрес строки в `LD HL, nn`.
Отдельных растровых данных, runtime-генератора и теневого bitmap здесь нет.
Например, для строки `.##############.` получена такая очистка:

```asm
Ship_clear_row_4:
    LD HL, 0
Ship_clear_row_4$dst$imm EQU $-2
    LD C, (HL)
    LD A, C
    AND 128
    LD (HL), A
    INC HL
    LD C, (HL)
    LD A, C
    AND 1
    LD (HL), A
    RET
```

Обе координаты проверяются до записей: X кратен восьми, весь прямоугольник
должен помещаться в bitmap 256×192. Переход к следующей строке следует
DOWN_HL из Antique Toy, включая границы 63/64 и 127/128.

## Подготовка до кадра, записи после него

```nanz
let old:Ship=Ship{x:old_x,y:old_y}
let next:Ship=Ship{x:new_x,y:new_y}

old.stage_erase()  // Только подготовка адресов очистки.
next.stage()       // Только подготовка адресов нового вывода.
// Владелец сцены ждёт подходящий момент вывода.
old.erase_staged()
next.publish()
```

В настоящем коде нужно проверить возвращаемые `bool` перед публикацией.
Сцена отвечает за синхронизацию и режим прерываний; методы сами не выполняют
`HALT`, `DI` или `EI`. Адреса очистки и рисования независимы. Подготовка нового
рисования не портит старую позицию, ожидающую стирания. Если формы пересекаются,
сначала очищаем все старые маски, затем рисуем все новые.

Одна форма хранит одну подготовленную позицию для вывода и одну для очистки.
`@zx_sprite_instances` передаёт поле `erase` каждой из 1–4 независимых копий.
Переиспользуемый SMC-код должен находиться в доступной для записи RAM; методы
одной копии не допускают одновременного вызова из основного кода и обработчика.

## Что проверено и измерено

`TestZXPairedSpriteNative` проверяет 74 позиции × два фона × три режима
компилятора, отдельно для прямого стирания и для перекрывающегося staged-перехода.
Всего 888 native-вызовов и 1776 вызовов raw/final MIR VM. Независимый оракул
работает по пиксельным координатам. Для Z80 проверяется вся 64-КБ память,
кроме ограниченного 64-байтного call stack, с точными ожидаемыми SMC-операндами
и состоянием readiness. Проверяются PC/SP, пиксели, атрибуты, края bitmap,
ошибочные координаты и отсутствие экранных записей при подготовке.

Дополнительно проверяются диагностики директивы `erase`, независимость двух
инстансов, прозрачность и значения результата на native и raw/final VM.
Прежняя библиотека без `erase` также повторно проходит свои проверки.

| Измерение для Ship 16×8 | Такты Z80 |
|---|---:|
| Полный `.erase()` с проверкой и вычислением адресов | 3490–3546 |
| Подготовленный `.erase_staged()` | 772 |
| Подготовленный `.publish()` | 870 |
| Полный проверочный сценарий: первоначальный draw, обе подготовки, erase и publish | 12931–13038 |

Два подготовленных kernel-замера включают возврат, исключают подготовку
и внешнюю инструкцию CALL. Полный standalone-модуль теста прямой очистки
занимает 1507 байт; staged-сценария — 1701 байт. Это размер всего модуля
с библиотечными методами и setter-процедурами, а не одного kernel.

Финальная матрица и диагностики проходят за 24.191 с. ASM/BIN, исходники,
логи и SHA256 сохраняются в `/mnt/safe/minz/grace/2026-10-14/paired-sprites/`.

Следующий шаг — четыре парных блока в Tetris, полный цикл с игровой логикой
и клавиатурой, сроки относительно ULA, два уровня скорости и настоящая запись
50-Гц кадров. Замеры отдельных kernels ещё не доказывают частоту всей игры.

## Повторное использование подготовленного placement

Если следующий кадр продолжает последний успешно подготовленный вывод,
`old.stage_previous_erase()` переносит его адреса в отдельные операнды
очистки. Вызывать до подготовки нового положения. Метод не пересчитывает
координаты и не пишет в экран; до первого успешного staging или после
неудачного staging возвращает false. `.draw()` не сохраняет staged-кэш.
Кэш принадлежит сгенерированному типу, а не произвольному объекту этого типа;
независимые слоты создаёт `@zx_sprite_instances`.

В [целой сцене](../typed-sprite-scene/README.md) это уменьшило подготовку
5723 → 3870 T без изменения размера модуля. Маски, отказ без staging и
сохранность старых адресов после нового placement проверены отдельным
`TestZXSpritePreviousEraseNativeVM` на native Z80 и raw/final VM.
