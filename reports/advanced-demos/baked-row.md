# Декларативная строка спрайта текущими средствами Nanz

14 октября 2026. Ветка `feat/advanced-demos`; в main и релизные ZIP этот этап
ещё не включён. Продолжение [нативных SMC-вызовов](native-smc.md).

Теперь данные можно описывать декларативно, а вывод остаётся обычной
типизированной процедурой Nanz. [Библиотека](../../stdlib/hw/baked_row.nanz)
целиком написана на Nanz; нового синтаксиса parser или file-reading host
для этого шага не потребовалось.

## Маппинг именованных полей

```nanz
import hw.baked_row

@baked_row("sprite0") {
    b0 0xc3
    b1 0x3c
}

fun draw() {
    sprite0(0x4000)
}
```

Метафункция создаёт обычные объявления Nanz:

```nanz
struct sprite0_Row { b0: u8, b1: u8 }

fun sprite0(@smc dst: u16) {
    dst^ = sprite0_Row{ b0: 195, b1: 60 }
}
```

Имена полей определяют форму структуры, значения — её запечённые данные.
Порядок полей в блоке задаёт порядок байтов. Это новый тип, полученный из
описания; переиспользование произвольного ранее объявленного типа через
reflection в эту библиотеку не добавлено.

## Последовательность байтов

Когда имена полей не нужны:

```nanz
@baked_bytes("sprite1") {
    byte 195
    byte 0x3c
}
```

Она создаёт обычный pointer walk:

```nanz
fun sprite1(@smc dst: ^u8) {
    var p: ^u8 = dst
    p^ = 195
    p = p + 1
    p^ = 60
}
```

Обе формы дают одинаковые инструкции:

```asm
sprite0:
    LD HL, 0
sprite0$dst$imm EQU $-2
    LD (HL), 195
    INC HL
    LD (HL), 60
    RET

sprite0_set_dst:
    LD (sprite0$dst$imm), HL
    RET
```

Kernel — 9 B / 46 T, setter — 4 B / 26 T; внешний CALL не включён.
Данные находятся в операндах инструкций, отдельная runtime-таблица не нужна.
Метапрограмма исполняется только при компиляции на MIR2 VM. Внутри генератора
используется существующий текстовый `emit` **обычного Nanz**, который затем
разбирается в HIR. ASM-строк библиотека не строит. Это промежуточная реализация
на нынешних средствах; expression-level typed aggregate builder ещё впереди.

Поддержаны 1–64 байта, hex и decimal. Дубликаты полей, неверное число аргументов,
значения вне 0..255 и неверное имя процедуры отклоняются при компиляции.
Binary `0b...` пока не поддержан lexer Nanz; такой пример нельзя выдавать
за уже работающий синтаксис.

## Индексная форма тоже стала короткой

```nanz
fun draw(@smc dst: ^u8) {
    dst[0] = 0xc3
    dst[1] = 0x3c
}
```

| Два байта | Kernel, T | Полный модуль с setter, B |
|---|---:|---:|
| Индексы, предыдущий checkpoint | 131 | 27 |
| Индексы, текущий checkpoint | 46 | 13 |
| Ручная структура / pointer walk | 46 | 13 |
| `@baked_row` / `@baked_bytes` | 46 | 13 |

Новый lowering сохраняет небольшое смещение как immediate, вместо расширения
индекса в отдельном регистре и ADD HL,DE. Первый допуск ограничен индексами
именованного SMC-параметра с буквальным смещением 0–3 байта на 16-битной цели.
MZV/Agon и остальные указатели сохраняют прежний путь. Это не обещание, что
произвольный длинный ряд индексов теперь оптимален.

Первый слишком широкий эксперимент мешал существующему объединению байтовых
обращений FAT12 в словные. Он отменён: обычный PtrAdd-граф остаётся доступным
sequential-byte fusion; специальный короткий путь применяется к SMC-base.
`TestFATSequentialWordFusionNative` снова проходит.

## Проверки и запуск

[Полный исходник](baked-row/demo.nanz) использует обе формы, настоящие source-вызовы
и переиспользование адреса через setter. [Полученный ASM](baked-row/demo.a80) и
[измерения](baked-row/measurements.json) сохранены рядом. Из этой ветки:

```sh
cd minzc
go run ./cmd/minzc ../reports/advanced-demos/baked-row/demo.nanz -o /tmp/baked-row.a80
```

Обычный путь, Grace Speed и Grace Size проверены одинаковыми независимыми
ожиданиями. Расширенные source-тесты: 27 вариантов, 162 запуска native Z80
и 162 запуска VM до/после оптимизаций. Проверяются данные, изменённый операнд,
PC/SP, повторное использование executable и вся RAM кроме ограниченных
32 байт стека вызовов.

Отдельные kernels проверены на 210 комбинациях формы, режима и адреса,
включая 0xfffd, 0xfffe, 0xffff. Проверяются полная RAM с ограниченным стеком,
реальный патч и возврат. Для этих CPU-проб ROM-защита отключена; адрес 0
действительно является RAM. Чтение индексов 0–3 дополнительно проверено
12 вариантами VM и 36 native source-wrapper запусками. Есть два словных
store и четыре byte-store: little-endian и wrap сравниваются с явными байтами.

Эти новые проверки не моделируют показанный ULA framebuffer, INT или NMI.
Они не делают процедуры повторно-входимыми и не разрешают runtime-патчи
в ROM. Ограничения первого SMC-контракта остаются в силе.

## Что дальше

Отдельный import из файла может передавать те же значения этому генератору;
`@map_file` пока является проектом. Сначала полезно перенести реальную строку
спрайта и соединить её с проверенным DOWN_HL-размещением.

Alice предложила следующий исследовательский шаг: выражать прямой/обратный
pointer walk обычным Nanz и при доказанной эквивалентности выбирать PUSH/POP.
Здесь недостаточно равенства конечной памяти: порядок байтов, aliasing,
перекрытие copy, MMIO, владение временным SP и прерывания входят в контракт.
[Исследование Astra и измеренные пробы](backward-walk-astra.md) завершены.
Новый SP-stream lowering этим шагом не включён.

Максимальная строка из 64 разных байтов также прошла 30 standalone native
вариантов: 1038 T, 195 B kernel + 4 B setter, включая wrap в адрес 0.
