# Нативный Nanz → запечённые записи Z80: первый рабочий SMC-контракт

14 октября 2026. Ветка `feat/advanced-demos`; этот этап ещё не интегрирован в main
и не входит в опубликованные релизные ZIP. Продолжение
[исследования нативного SMC](native-smc-research.md).
Следующий checkpoint: [декларативные строки и короткие индексы](baked-row.md).
Измерения ниже относятся к первому допуску до улучшения индексной формы.

Теперь короткую строку спрайта можно написать обычными типизированными
операциями Nanz. Компилятор оставляет данные непосредственно в инструкциях,
а адрес назначения — в изменяемом операнде. Из Nanz работают и полный вызов
с новым адресом, и отдельная подготовка адреса для последующих вызовов.
Текстовый ASM-генератор для этих примеров не нужен.

## Два естественных способа описать строку

[Структура](native-smc/row_struct.nanz) удобна, когда у строки фиксированная форма:

```nanz
struct Row2 { b0: u8, b1: u8 }

fun draw(@smc dst: u16) {
    dst^ = Row2{ b0: 0xc3, b1: 0x3c }
}
```

[Pointer walk](native-smc/row_typed_walk.nanz) удобен для последовательного вывода
и дальнейшего вычисления адресов:

```nanz
fun draw(@smc dst: ^u8) {
    var p: ^u8 = dst
    p^ = 0xc3
    p = p + 1
    p^ = 0x3c
}
```

Оба дают одинаковый короткий kernel; локальный `p` не добавляет отдельного
хранения или пересылок:

```asm
draw:
    LD HL, 0
draw$dst$imm EQU $-2
    LD (HL), 195
    INC HL
    LD (HL), 60
    RET

draw_set_dst:
    LD (draw$dst$imm), HL
    RET
```

`@smc` здесь относится к передаче адреса: он хранится в двух байтах операнда
`LD HL, nn`. Данные `195` и `60` запекаются обычным lowering константных записей.
Это не автоматическое превращение произвольного цикла или массива в спрайт.

[Индексная форма](native-smc/row_typed_index.nanz) тоже работает:

```nanz
fun draw(@smc dst: ^u8) {
    dst[0] = 0xc3
    dst[1] = 0x3c
}
```

Она выразительна, но текущий backend ещё сохраняет лишние адресные вычисления.
Прямое присваивание array literal пока не поддержано; первый этап использует
структуру или отдельные записи через указатель.

## Как вызывать

Для варианта с типизированным указателем:

```nanz
global buffer: [u8; 64]

fun run() {
    draw(&buffer[4])
    draw_set_dst(&buffer[12])
    draw()
    draw()
}
```

Первый вызов вычисляет аргументы, вызывает типизированный setter, затем `draw`.
Последующие вызовы без SMC-аргумента используют последний подготовленный адрес.
Setter создаёт компилятор; объявлять его как `extern` не требуется.
Для прежней сигнатуры с `u16` применяется `draw(u16(&buffer[4]))`.

[Полный проверенный исходник с caller](native-smc/caller.nanz) можно собрать
из этой ветки:

```sh
cd minzc
go run ./cmd/minzc ../reports/advanced-demos/native-smc/caller.nanz -o /tmp/native-smc.a80
```

Можно сочетать один SMC-адрес с обычными аргументами и скалярным возвратом:

```nanz
fun draw(@smc dst: ^u8, value: u8) -> u8 {
    dst^ = value
    return value + 1
}
```

`draw(addr, value)` устанавливает адрес, `draw(value)` переиспользует его.
Адрес может стоять и последним параметром. Все аргументы полного вызова
вычисляются **до** патча: вложенный вызов в аргументе не оставляет внешнему
рисованию чужой адрес.

## Что изменилось в компиляторе

HIR проверяет типы и обе допустимые формы вызова. Setter существует как
типизированный MIR-код с фиксированной передачей адреса в HL, а не только как
добавленный в конце ASM label. Обычная проверка MIR контролирует связь setter
с его изменяемым операндом. Удаление неиспользуемых функций удерживает живую
пару kernel/setter и удаляет полностью недостижимые пары.

VM теперь хранит именованные SMC-значения между вызовами одного экземпляра,
в том числе когда setter вызван раньше первого `draw`. На Z80 сохраняется
тот же экземпляр исполняемого кода и действительно меняются байты операнда.
Общий механизм анонимных patch slots этим этапом не завершён.

Ревью также выявило прежнюю ошибку parser: локальное имя, совпадающее с именем
функции, превращалось в её адрес. Приоритет лексических значений исправлен;
параметр `draw = 9` и локальный `draw = 7` возвращают именно 9/7 на VM и Z80.

## Измерения и границы доказанного

Три формы, обычный путь, Grace Speed и Grace Size дали одинаковые результаты
в своих строках. Размер указан для **полного маленького модуля**, включающего
kernel и setter. Такты — от входа процедуры до `RET`, без внешнего `CALL`.

| Форма | Kernel, T | Setter, T | Модуль, B |
|---|---:|---:|---:|
| Структура | 46 | 26 | 13 |
| Pointer walk | 46 | 26 | 13 |
| Индексы | 131 | 26 | 27 |

Структура и pointer walk: kernel 9 B, setter 4 B. В предыдущем исследовательском
checkpoint setter занимал 9 B / 44 T; новый использует одну 16-битную запись.
Сами 46 T kernel здесь не являются новым выигрышем.
[ASM и машиночитаемые измерения](native-smc/measurements.json) сохранены рядом.

Проверки источников охватывают пять форм × три режима: структуру, pointer walk,
индексы и две позиции SMC-аргумента с вложенным вызовом. Для них выполнены
90 запусков VM (до и после оптимизаций) и 90 запусков Z80. Нативные проверки
сравнивают все 64 КБ RAM, исключая ограниченные 32 байта стека вызовов,
проверяют данные, изменённый операнд, возврат PC/SP и повторное использование
одного executable. Два исходных заполнения RAM помогают выявить зависимость
от прежнего содержимого.

Отдельный замер трёх коротких kernels проверяет 63 комбинации формы, режима
и адреса: семь адресов около границ экранных областей. Это линейные записи,
а не проверка перехода `DOWN_HL` к следующей сканлинии Spectrum.
Прерывания, NMI, ULA contention и показанный видеокадр этим новым набором
не моделируются; прежние ULA-проверки спрайтов описаны отдельно в
[общем отчёте](README.md).

Первый допуск ограничен одним SMC-адресом на функцию, прямыми вызовами и
скалярным/void возвратом. Рекурсивные циклы с SMC, истинное получение адреса
SMC-функции, косвенные вызовы внутри неё и конфликтующие объявления setter
отклоняются. Эти проверки не доказывают отсутствие повторного входа через
внешний ASM или обработчик прерывания. Исполняемый код должен находиться
в изменяемой RAM; caller обеспечивает отсутствие конфликтующего патча.
Никакое автоматическое обрамление DI/EI или сохранение всех регистров
здесь не добавлено. Объявляемые CALL-clobbers пока консервативны.

HIR, MIR2 и Nanz завершились PASS. Быстрый pipeline: 387/387, три независимых
параллельных процесса; глубокий release-набор этим этапом не перезапускался.
Дополнительно выполнена настоящая CLI-компиляция pointer-walk с caller.

## Следующий полезный шаг

Перенести одну реальную строку из baked sprite-библиотеки на этот нативный
контракт и сравнить код с существующим ASM kernel. Затем соединить строки
с уже проверенным `DOWN_HL`-размещением. Разворачивание статических циклов,
несколько независимых SMC-слотов и специализация array data требуют отдельных
доказательств и замеров; их не следует считать уже работающими.

## Предложение Alice: форма отдельно, данные из файла

Следующая поверхность может выглядеть так; **это проект синтаксиса**, который
текущий compiler ещё не принимает:

```nanz
struct Row2 { b0: u8, b1: u8 }
const sprite0: Row2 = @map_file("sprite.spr")

fun draw_row(@smc dst: u16) {
    dst^ = sprite0
}
```

Тип определяет layout, файл — значения. Для первого случая с двумя u8-полями
достаточен явно выбранный raw-формат: ровно два байта в порядке полей.
Расширение `.spr` само по себе не определяет формат; размеры, упаковка, маски
и порядок байтов должны задаваться importer или форматом ресурса.

Работающий фундамент уже есть: Nanz-метафункции исполняются при компиляции,
а `hir_int`, `hir_store` и `emit_hir` строят типизированные записи без склейки
ASM. В нынешнем host API нет чтения файлов ресурсов; также ещё нет готового
expression-level `@map_file`, возвращающего типизированный aggregate value.
Поэтому сначала нужен import ресурса с разрешением пути относительно исходника,
проверкой размера и учётом содержимого в зависимостях сборки. Затем тот же
декодер может строить row values или непосредственно известные HIR stores.
Обычная runtime-переменная с массивом не должна выдаваться за запечённые данные.

Минимальный следующий эксперимент: два raw-байта из файла дают тот же
9 B / 46 T kernel, что ручной Row2, без runtime-чтения отдельной таблицы.
Меняем файл и проверяем изменение immediate bytes; неправильный размер
отклоняется при компиляции. Обобщённое отображение типов и форматов — позже.

В дальней перспективе одно описание формы можно использовать и для генерации
в RAM во время исполнения. Самый компактный первый runtime-вариант — готовые
kernels с патчами адресов и данных. Следующий — ограниченный генератор известных
Z80-инструкций в code buffer. Это отдельная библиотека кодогенерации на цели,
а не запуск нынешней compile-time VM внутри Spectrum. Возможность runtime-JIT
не реализована этим checkpoint и не входит в ближайший допуск SMC.
