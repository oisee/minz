# Нативный pointer walk → PUSH/POP: исследование Astra

14 октября 2026. Независимое исследование `gpt-6-astra`, reasoning `xhigh`,
через Codex CLI **без профиля**, provider `openai`. Первая tool-попытка
прервалась по rate limit; эта CLI-попытка завершена. Исходники и git
исследователь не менял. Компилятор: `4009defe`, ветка `feat/advanced-demos`.
Это проект следующего допуска, не внедрённая автоматическая оптимизация.

**Да: обратные записи естественно превращаются в PUSH, а прямые чтения — в POP. Но это оптимизация проверенной области памяти с временным использованием SP, а не простая замена пары `load/store` одной инструкцией.** Прямую запись тоже иногда можно выполнить обратной последовательностью PUSH, однако равенство конечной RAM ещё не доказывает допустимость перестановки обращений.

Отчёт основан на прочитанном рабочем дереве репозитория и локальном Antique Toy, commit `7313ecfaab710d1a105b7bff3be19aaf04dc5935`. Исходники и git не изменялись, другие агенты не запускались. Новых компиляций и native-прогонов я не выполнял: ниже существующие результаты отделены от предлагаемых преобразований и расчётных стоимостей.

**В репозитории уже есть нужные строительные блоки, но общего преобразования pointer walk → PUSH/POP пока нет.**

- Нативный `@smc` связывает типизированный параметр, setter и изменяемый immediate. Обычные записи структуры и прямой pointer walk уже дают двухбайтовый kernel **9 B / 46 T**, setter — **4 B / 26 T**. Это передача адреса через SMC и запекание константных записей; SP здесь не используется. [native-smc.md:25](../../reports/advanced-demos/native-smc.md#L25), [измерения:130](../../reports/advanced-demos/native-smc.md#L130).
- `@baked_row` и `@baked_bytes` генерируют обычный Nanz: соответственно присваивание структуры и последовательные записи через указатель. Это подходящая поверхность для будущего выбора машинного исполнения. [baked_row.nanz:35](../../stdlib/hw/baked_row.nanz#L35), [pointer walk:80](../../stdlib/hw/baked_row.nanz#L80).
- `@push_fill` уже генерирует ASM с сохранением SP в immediate восстановления. Он требует разрешённую RAM, положительную чётную длину и заявленный контракт отключённых IRQ. Сегодня библиотека вручную сохраняет BC/DE, а для длинного тела — также AF. Это существующее исполнение, не требование к будущему пользовательскому API. [push_fill.nanz:40](../../stdlib/hw/push_fill.nanz#L40), [генерация:71](../../stdlib/hw/push_fill.nanz#L71).
- PUSH-ветка `@sprite_chain` требует чётную ширину и непрозрачные маски, обходит строку справа налево и собирает пары для PUSH. Direct-ветка уже обходится без общего сохранения всех регистров. [sprite_chain.nanz:85](../../stdlib/hw/sprite_chain.nanz#L85), [пары байтов:150](../../stdlib/hw/sprite_chain.nanz#L150).
- MIR2 `OpPush`/`OpPop` прямо обозначены как **callee-save scaffold**. У них неявный стек; `OpPop.Uses()` не содержит адреса источника. Эмиттер даже расширяет одиночный регистр до пары через `toPair`. Эти операции нельзя считать готовыми типизированными операциями потока данных. [ops.go:116](../../minzc/pkg/mir2/ops.go#L116), [inst.go:154](../../minzc/pkg/mir2/inst.go#L154), [эмиттер:1410](../../minzc/pkg/mir2/z80codegen_inst.go#L1410).

Книга Nanz полезна для синтаксиса указателей и ASM, но не полностью описывает текущее состояние: например, её утверждение, что auto-clobber всегда включает F, уже устарело относительно `z80effects`. Существующее поведение следует устанавливать по коду. [Nanz Language Book:291](../../docs/Nanz_Language_Book_v7.md#L291), [старое описание clobbers:485](../../docs/Nanz_Language_Book_v7.md#L485).

**Направление обхода и порядок байтов нужно описывать независимо от little-endian представления слова.**

Для пары `DE = 0x3412`:

| Инструкция и начальный SP | Первое обращение | Второе обращение | Конечное состояние |
|---|---|---|---|
| `PUSH DE`, `SP = a+2` | запись `0x34` в `a+1` | запись `0x12` в `a` | `SP = a`; память `[12,34]` |
| `POP DE`, `SP = a` | чтение `a` в E | чтение `a+1` в D | `SP = a+2`; `DE = 0x3412` |

Следовательно, PUSH сохраняет little-endian раскладку слова, **выполняя записи от старшего адреса к младшему**. POP читает от младшего адреса к старшему. Для BC/DE/HL это соответственно 11 T и 10 T, по одному байту кода. IX/IY требуют префикса и стоят дороже. Это соответствует описанию инструкций Zilog. [Z80 CPU User Manual, PUSH/POP](https://www.zilog.com/docs/z80/um0080.pdf#page=129).

Для строки в возрастающем порядке адресов:

```text
адрес:    a     a+1   a+2   a+3
данные:   12    34    56    78
```

нужны:

```asm
LD SP, a+4
LD DE, 0x7856
PUSH DE
LD DE, 0x3412
PUSH DE
```

Порядок записей: `(a+3,78)`, `(a+2,56)`, `(a+1,34)`, `(a,12)`. Обращается порядок **пар**, но внутри каждой пары значение по младшему адресу остаётся младшим байтом регистра.

В локальном Antique Toy есть ошибка именно в этом месте: фраза о помещении правого байта в младшую половину регистра противоречит описанной там же семантике PUSH. Правый байт пары должен быть старшим. Реальная реализация `sprite_chain` собирает пару правильно: `pair_high * 256 + graphic`. [Antique Toy, ch16:349](https://github.com/oisee/antique-toy/blob/7313ecfaab710d1a105b7bff3be19aaf04dc5935/chapters/ch16-sprites/draft.md#L349), [sprite_chain.nanz:175](../../stdlib/hw/sprite_chain.nanz#L175).

**Исходный алгоритм вполне можно оставлять обычным Nanz.** Например, прямой вывод:

```nanz
fun row_forward(@smc dst: ^u8) {
    var p: ^u8 = dst
    p^ = 0x12
    p = p + 1
    p^ = 0x34
    p = p + 1
    p^ = 0x56
    p = p + 1
    p^ = 0x78
}
```

Здесь последовательность записей возрастает по адресам. Приведённый выше PUSH-код сохраняет конечную память, но меняет эту последовательность.

Обратный алгоритм с указателем **за концом** области выражается столь же непосредственно:

```nanz
fun row_backward(@smc end: ^u8) {
    var p: ^u8 = end

    p = p - 1
    p^ = 0xf0
    p = p - 1
    p^ = 0xde
    p = p - 1
    p^ = 0xbc
    p = p - 1
    p^ = 0x9a
    p = p - 1
    p^ = 0x78
    p = p - 1
    p^ = 0x56
    p = p - 1
    p^ = 0x34
    p = p - 1
    p^ = 0x12
}
```

Его итоговая строка — `[12,34,56,78,9a,bc,de,f0]`. Четыре PUSH могут сохранить и данные, и порядок обращений.

Для чтения ситуация зеркальная:

```nanz
fun read_forward(src: ^u8) -> u16 {
    var p: ^u8 = src
    let lo: u8 = p^
    p = p + 1
    let hi: u8 = p^
    return u16(lo) | (u16(hi) << 8)
}

fun read_backward(end: ^u8) -> u16 {
    var p: ^u8 = end
    p = p - 1
    let hi: u8 = p^
    p = p - 1
    let lo: u8 = p^
    return u16(lo) | (u16(hi) << 8)
}
```

`read_forward` соответствует порядку POP. `read_backward` возвращает то же слово из той же пары адресов, однако POP меняет порядок чтений. Дополнительное переставление SP перед каждой парой не устраняет это различие.

Эти примеры используют обычные объявления и операции языка. Предлагаемая новая возможность — распознавание и проверенный выбор исполнения, а не новый обязательный синтаксис PUSH/POP для автора алгоритма.

**Есть три разных уровня эквивалентности.**

1. **Равенство результата:** совпадают возвращаемые значения и конечная доступная программе память.
2. **Равенство последовательности обращений:** совпадают чтения и записи, их адреса, значения, порядок, а при проверяемом доступе — также выполненный префикс до ошибки.
3. **Равенство аппаратного наблюдения:** учитываются время обращений, прерывания, DMA, ULA и иные наблюдатели.

Оптимизация обычно меняет время исполнения. Поэтому даже сохранение порядка байтов не обещает одинаковый показанный видеокадр. Для экранной RAM контракт должен отдельно определять допустимое окно рисования или проверяемое свойство изображения.

Это различие уже существенно для текущего MIR2. `SequentialBytes` означает последовательность **low-to-high**, включая частично выполненные обращения перед отказом. `SequentialByteOrigins` сохраняет исходную идентичность байтовых операций, а `SequentialAddressDefs` — доказательство адресов. VM проверяет доступ и выполняет наблюдение отдельно для каждого байта. [inst.go:35](../../minzc/pkg/mir2/inst.go#L35), [vm.go:739](../../minzc/pkg/mir2/vm.go#L739).

Поэтому существующий `OpStore u16` с `SequentialBytes=true` нельзя просто выбрать как PUSH: он обещает противоположный порядок записей.

В частности:

- Для MMIO порядок может запускать разные действия устройства. Два соседних адреса не обязательно являются обычным словом.
- Для изменяющейся памяти POP читает второй байт раньше, чем исходная программа могла бы его читать.
- При отказе второго обращения первая запись уже могла состояться. Предварительная проверка всей пары способна изменить эту семантику.
- Даже одинаковые байты fill не делают порядок ненаблюдаемым: это верно только при соответствующем контракте области.

Текущий DSE намеренно не удаляет неиспользуемые `OpLoad`, поскольку они могут обращаться к отображённому в память устройству. Оснований автоматически считать любой `^u8` обычной ненаблюдаемой RAM нет. [dse.go:15](../../minzc/pkg/mir2/dse.go#L15).

**Копирование требует более сильного доказательства, чем заполнение.**

Обычный прямой цикл:

```nanz
fun copy_forward(src: ^u8, dst: ^u8, count: u16) {
    var s: ^u8 = src
    var d: ^u8 = dst
    var n: u16 = count

    while n != 0 {
        d^ = s^
        s = s + 1
        d = d + 1
        n = n - 1
    }
}
```

задаёт чередование:

```text
read s; write d; read s+1; write d+1; ...
```

Преобразование в «прочитать пару, затем записать пару» меняет его на:

```text
read s; read s+1; write ...; write ...
```

При `dst = src+1` исходный цикл распространяет первый байт дальше: следующая итерация читает уже перезаписанную память. Предварительное чтение двух байтов даёт иной результат. Нельзя исправлять такой цикл до предполагаемого `memmove`, если исходная функция этого не обещала.

Для обратного копирования естественна форма с `src_end`/`dst_end` и уменьшением обоих указателей **перед** чтением и записью. Но и там пакетное чтение требует доказательства отсутствия разрушенных зависимостей. Удобный первый допуск — непересекающиеся обычные области; поддержка безопасных направлений overlap может появиться отдельно.

Кроме того, у Z80 **один SP**. После:

```asm
POP DE
PUSH DE
```

без переключения SP слово записывается обратно в тот же участок, из которого было прочитано. Для двух буферов нужно переключать SP, удерживать оба курсора и учитывать цену этих действий. Пакет из нескольких POP с последующей серией PUSH может амортизировать переключение, но требует нескольких регистров и обратного порядка выгрузки пар.

Именно поэтому приведённые в Antique Toy 10+11 T нельзя принимать за полную стоимость копирования двух байтов между независимыми буферами. Более того, обычная повторяющаяся итерация LDIR переносит **один** байт за 21 T. [Antique Toy, ch03:199](https://github.com/oisee/antique-toy/blob/7313ecfaab710d1a105b7bff3be19aaf04dc5935/chapters/ch03-demoscene-toolbox/draft.md#L199).

**Временное использование SP должно быть отдельным проверяемым эффектом.**

Для первого допустимого региона нужны следующие обязательства:

| Обязательство | Что требуется доказать |
|---|---|
| Адреса | Все обращения находятся в разрешённой области; длина и арифметика адресов определены |
| Семантика памяти | Сохранён исходный порядок либо доказано разрешение перестановки |
| Значения | Упаковка пары сохраняет правильные байты; вычисления не пересечены через зависимые обращения |
| Обычный стек | Данные потока не пересекают живые frames, адреса возврата, сохранения и временные stack slots |
| Код | Destination не пересекает исполняемый код и patch-sites; источник POP не конфликтует с изменяемыми операндами |
| Управление | На каждом выходе SP восстановлен до потребления обычного стека |
| Асинхронное исполнение | Во время подмены SP исключены несовместимые INT/NMI и повторный вход |
| ABI | Сохранены необходимые живые значения; результаты не уничтожаются восстановлением |

«Стек не пересекается с буфером» означает больше, чем неравенство `SP` и адреса буфера. Нужно учитывать весь живой стек и записи, которые появятся из-за ABI, spill, helpers и пролога. Если исходная программа пишет в собственный локальный буфер на стеке, она от этого не становится неправильной; просто такой кандидат не проходит первый допуск к SP-оптимизации.

Внутри области нельзя допускать обычные CALL/RST, RET, случайные spill PUSH/POP или `EX (SP),HL`. CALL запишет адрес возврата в поток данных, RET примет данные за адрес продолжения. В первом варианте разумен один вход, один выход и отсутствие вызовов внутри. Специализированный stackless-переход можно исследовать позже.

RET-цепочка из существующего отчёта использует настоящий стек продолжений. Она совместима с PUSH-kernel только после восстановления этого стека перед RET. [sprite-ret-walk.md:59](../../reports/advanced-demos/sprite-ret-walk.md#L59).

**DI не должен автоматически переноситься ко входу функции.**

Допустимая последовательность может выглядеть так:

```asm
; Здесь обычный стек и разрешённые INT.
HALT
; Обработчик завершился согласно контракту платформы.
DI
; Сохранение SP, его подмена, поток данных.
...
; Восстановление обычного SP.
; Дальнейшая политика INT определяется контрактом.
```

Анализ должен проверять состояние **в точке подмены SP и до восстановления**, а не требовать DI первой инструкцией функции. В частности, функция может сначала ждать кадр, вычислять адреса и вызывать helpers.

Нельзя также безусловно добавлять EI в эпилог. DI сбрасывает IFF1/IFF2, EI устанавливает оба и имеет задержку принятия маскируемого прерывания до завершения следующей инструкции. `LD A,I` отражает IFF2 через P/V, а не предоставляет универсальную копию всего interrupt-состояния. Произвольный NMI-контекст такой оболочкой прозрачно не восстанавливается. [Z80 CPU User Manual, interrupt state](https://www.zilog.com/docs/z80/um0080.pdf#page=32).

Для первого допуска достаточно ясного контракта: непосредственно перед областью `IFF1=IFF2=0`; область их не меняет. Caller может обеспечить это после HALT. Позднее можно добавить проверенную оболочку для известного нормального контекста с разрешёнными INT.

NMI — самостоятельное ограничение: DI его не блокирует. Аппаратный вход уже использует текущий стек до первой инструкции обработчика, поэтому «NMI-handler сразу переключит SP» само по себе не спасает данные. Первый допуск должен требовать отсутствия NMI в этом окне либо отдельного, существенно более сильного протокола платформы.

Такой порядок уже зафиксирован в местном дизайне: HALT может предшествовать DI, а SP/INT требуют анализа путей. [design.md:24](../../reports/advanced-demos/design.md#L24).

**Восстановление SP через SMC удобно, но создаёт собственное состояние экземпляра.**

Рабочая схема:

```asm
LD (restore_sp+1), SP
...
restore_sp:
LD SP, 0
```

Первая инструкция записывает младший и старший байты SP в два байта immediate второй. Если есть необходимые сохранения на обычном стеке, фиксировать SP следует **после них**, а восстанавливать — **до соответствующих POP и RET**.

Из этого следуют дополнительные условия:

- operand восстановления находится в изменяемой RAM;
- его символ и ширина сохраняются после размещения и peepholes;
- запись не затрагивает opcode и соседние инструкции;
- повторный вход не перезаписывает сохранённый SP незавершённого вызова;
- destination не уничтожает operand восстановления;
- другой поток исполнения не использует промежуточно обновляемое состояние.

Для восстановления важен интервал от записи сохранённого SP до его использования. Для адресного `@smc` дополнительно важна согласованность setter → draw. Отсутствие рекурсии в исходном call graph не доказывает отсутствие входа через ISR или внешний ASM.

Сегодня named SMC ограничен одним исходным адресным параметром на функцию. Скрытый operand восстановления SP будет новым внутренним ресурсом backend; его существование не следует автоматически из поддержки `@smc`. [hir/smc.go:10](../../minzc/pkg/hir/smc.go#L10).

SMC также не является обязательным способом восстановления. Отдельный RAM-slot или свободная пара могут быть допустимыми альтернативами. Их выбор зависит от стоимости, liveness и владения; RAM-slot сам по себе тоже не решает reentry.

**Сохранения регистров должны следовать из эффектов и ABI, а не становиться обязанностью автора Nanz.**

Текущий `z80effects` уже различает физические половинки регистров, банки, флаги, память, `StackDelta`, замену SP и INT-эффекты. Для PUSH он отмечает чтение пары, запись памяти и изменение SP; для POP — чтение памяти и запись пары. POP AF дополнительно изменяет F. [effects.go:77](../../minzc/pkg/z80effects/effects.go#L77), [PUSH/POP:313](../../minzc/pkg/z80effects/effects.go#L313).

Нужный принцип сохранения:

```text
изменяемые физические ресурсы
∩ значения, живые через область
с учётом объявленных результатов и требований ABI
```

Отсюда, например:

- PUSH DE не портит DE; его портит предшествующий `LD DE,constant`.
- PUSH/POP BC/DE/HL и `LD SP,...` не требуют сохранения AF только из-за своего присутствия.
- `DEC HL` и `DJNZ` сохраняют флаги; `DEC B` изменяет часть флагов.
- POP AF нельзя выбирать как обычную загрузку произвольного слова без моделирования нового F.
- Нельзя восстановить старый HL поверх результата, возвращаемого в HL.
- Альтернативная банка тоже ресурс: EXX требует анализа её содержимого и ISR-контракта.

При этом точные локальные ASM-effects ещё не означают точные clobbers всей функции. Текущий `computeClobbers` для обычных функций возвращает консервативный набор, поскольку allocation destinations не описывают все неявные записи и helpers. [z80codegen_call.go:1140](../../minzc/pkg/mir2/z80codegen_call.go#L1140).

Поэтому предлагаемое улучшение должно включать проверку фактически выбранного машинного исполнения. Убирать сохранения, опираясь только на исходный список SSA-результатов, нельзя.

**Первый небольшой kernel стоит сделать из восьми обратных константных записей.**

Для показанного `row_backward` предлагается:

```asm
row_backward:
    LD (row_backward_restore+1), SP

    LD SP, 0
row_backward$end$imm EQU $-2

    LD DE, 0xF0DE
    PUSH DE
    LD DE, 0xBC9A
    PUSH DE
    LD DE, 0x7856
    PUSH DE
    LD DE, 0x3412
    PUSH DE

row_backward_restore:
    LD SP, 0
    RET

row_backward_set_end:
    LD (row_backward$end$imm), HL
    RET
```

Это **предложение генерации**, не результат новой компиляции.

При `end=a+8` инструкция за инструкцией записываются:

```text
a+7:F0, a+6:DE, a+5:BC, a+4:9A,
a+3:78, a+2:56, a+1:34, a:12
```

Последовательность совпадает с исходным Nanz. Нет чтений destination и нет перестановки исходных записей. Предусловия: допустимая RAM, отсутствие пересечений, несовместимых прерываний и reentry; DE доступен согласно ABI.

Расчёт без contention, от входа до RET:

| Часть | B | T |
|---|---:|---:|
| `LD (restore+1),SP` | 4 | 20 |
| `LD SP,end` | 3 | 10 |
| Четыре `LD DE,nn` | 12 | 40 |
| Четыре `PUSH DE` | 4 | 44 |
| `LD SP,saved` | 3 | 10 |
| RET | 1 | 10 |
| **Kernel** | **27** | **134** |
| Setter | 4 | 26 |

Полный модуль kernel + setter: **31 B**. Повторный вызов с уже подготовленным адресом: **151 T** вместе с внешним CALL. Setter-call + kernel-call: **194 T**, без вычисления аргумента и дополнительных ABI-сохранений.

Для сравнения, расчётная буквальная реализация восьми pre-decrement записей через HL занимает **28 B / 148 T**. Прямой вариант с семью INC HL — **27 B / 142 T**, но имеет другой порядок обращений. Это сравнение конкретных последовательностей, не утверждение глобальной оптимальности.

Для двух различных байтов та же SP-оболочка стоила бы **15 B / 71 T** против существующих **9 B / 46 T** обычного kernel. Поэтому начинать с двух байтов полезно для проверки семантики, но не для демонстрации выигрыша.

Для восьми одинаковых байтов достаточно одного `LD DE,value*257`: получаются **18 B / 104 T**. Здесь особенно важно не скрывать цену оболочки за рекламными «5,5 T на байт».

**POP выгоден прежде всего как длительный поток чтения, а не как замена одиночной загрузки слова.**

При `src` в HL одиночное чтение слова в HL можно реализовать обычными инструкциями:

```asm
LD A,(HL)
INC HL
LD H,(HL)
LD L,A
RET
```

Это 5 B / 34 T. Вариант с SMC-сохранением SP, `LD SP,HL`, `POP HL`, восстановлением SP и RET — 10 B / 56 T.

Потенциальный выигрыш появляется при нескольких последовательных словах, когда одна оболочка обслуживает много POP. При этом нужно проверить:

- доступность обоих байтов каждой пары и семантику нечётного хвоста;
- отсутствие MMIO и недопустимого раннего чтения;
- потребителей обоих байтов и возможность разместить их в паре;
- отсутствие вызовов и stack-spill внутри области;
- необходимость вернуть наружу конечный логический курсор;
- пересечение источника с обычным стеком и изменяемым кодом.

POP сам не записывает источник, поэтому неизменяемая таблица, включая подходящую ROM, принципиально допустима. Однако SMC-оболочке всё равно требуется собственная RAM, а прерывание с подменённым SP способно попытаться записать в область источника.

Для fill нужны чётная длина в первом допуске, корректный нулевой случай, допустимый порядок записей и доказанная область назначения. Особенно нельзя путать `B=0` у DJNZ с нулём итераций: это 256 итераций. Существующий `push_fill` решает этот случай через заранее вычисленное число chunks. Его измеренные результаты полной очистки уже показывают практическую пользу, но относятся к библиотечным ядрам и конкретной модели Spectrum. [push_fill.nanz:51](../../stdlib/hw/push_fill.nanz#L51), [README.md:74](../../reports/advanced-demos/README.md#L74).

Для неизменяемого спрайта известность пикселей позволяет убрать runtime-чтения рисунка. Она **не** доказывает ненаблюдаемость экранных записей. Первый PUSH-вариант должен обрабатывать непрозрачные пары без чтения фона. Маски требуют read-modify-write, прозрачные байты — пропусков; запись «прежнего значения» вместо пропуска тоже может изменить наблюдаемое поведение.

Каждая строка Spectrum должна иметь правильно вычисленный адрес. Нельзя продолжить линейное уменьшение SP через весь прямоугольник, как будто соседние визуальные строки соседствуют в RAM. DOWN_HL и размещение row operands остаются отдельной задачей. [Antique Toy, ch02:172](https://github.com/oisee/antique-toy/blob/7313ecfaab710d1a105b7bff3be19aaf04dc5935/chapters/ch02-screen-as-puzzle/draft.md#L172), [sprite-ret-walk.md:43](../../reports/advanced-demos/sprite-ret-walk.md#L43).

**Свежий эксперимент с `PtrAdd → Field` показывает, почему порядок проходов и происхождение адресов входят в дизайн.**

В текущем `FuseSequentialByteWords` адресный анализ проходит через `Move` и `PtrAdd` с типизированной константой. `Field` не входит ни в этот разбор, ни в набор разрешённых промежуточных операций, ни в сохраняемый адресный DAG. Проверяющая функция также знает только соответствующий ограниченный набор. [byte_word_fusion.go:50](../../minzc/pkg/mir2/byte_word_fusion.go#L50), [проверка provenance:308](../../minzc/pkg/mir2/byte_word_fusion.go#L308).

Следовательно, сообщённый результат эксперимента — глобальная замена разрушает слияние FAT helpers — объясняется текущим кодом: исчезает распознаваемая связь соседних адресов. Сам тест требует ровно два слияния и проверяет упорядоченные байтовые события. [fat_word_fusion_test.go:121](../../minzc/pkg/pipeline/fat_word_fusion_test.go#L121).

Текущее ограничение уже видно в `smallSMCIndexOffset`: база должна быть непосредственно именем SMC-параметра; допускаются только маленькие проверенные смещения. Обычные указатели сохраняют `PtrAdd`. Это разумная локализация изменения, но пока не общее решение эквивалентных адресных форм. [lower.go:2612](../../minzc/pkg/hir/lower.go#L2612).

Есть ещё две существенные детали:

- Обычное выражение `p = p ± 1` проходит через арифметические `Add/Sub`; новый распознаватель не должен ограничиваться только формой индексного `PtrAdd`. [lower.go:2785](../../minzc/pkg/hir/lower.go#L2785).
- **`Field(base,-1)` сейчас не означает декремент указателя.** Это специальное SoA256-кодирование увеличения младшего байта. Нельзя использовать его для обратного обхода. [vm.go:719](../../minzc/pkg/mir2/vm.go#L719).

Для дальнейшего развития допустимы два пути: сохранять семантическую адресную форму до распознавания потоков либо одновременно расширить matcher, проверку provenance и сбор адресных доказательств на новые формы. Изменение только matcher недостаточно.

Текущий fusion выполняется после ряда MIR-упрощений и только при `FuseByteWords`; это нужно сохранить в регрессионной матрице обоих путей pipeline. [pipeline.go:319](../../minzc/pkg/pipeline/pipeline.go#L319), [второй путь:596](../../minzc/pkg/pipeline/pipeline.go#L596).

**Минимальное расширение MIR я предлагаю строить вокруг типизированной последовательности памяти и отдельного региона SP.**

Для первого допуска не требуется превращать SP в обычный allocatable pointer во всём MIR.

1. **Сохранить семантику байтов.** Добавить описание упорядоченных доступов: исходная операция, адресное выражение, байт значения, порядок, происхождение и режим наблюдаемости. Существующий `SequentialBytes` оставить означающим low-to-high; новый descending-вариант должен иметь явное представление, а не переосмысление старого флага.
2. **Добавить ограниченный `SPRegion` как целевое исполнение типизированного тела.** В нём известны входной курсор, все обращения, выходы, ресурс сохранённого SP и условия допуска. Первое тело — фиксированная последовательность константных store без результатов. Для VM сохраняется исполнение исходных байтовых операций.
3. **Выбирать PUSH/POP внутри региона после проверки.** Существующие `OpPush`/`OpPop` сохраняют назначение ABI-scaffold. Если позднее понадобятся отдельные stream-opcodes, они должны иметь явные адресные операнды и порядок доступов.
4. **После allocation проверить фактический код региона.** Не появились ли stack-spill, CALL/helper, лишняя запись F или непредусмотренный выход? При неудаче использовать обычные load/store.
5. **Структурно описать patch-sites.** Символ, ширина, допустимый operand, владелец и время жизни. После финальных peepholes и assembly проверить, что символ действительно указывает на нужные байты инструкции.

Текущих `MemoryRead/MemoryWrite bool` достаточно для консервативного clobber, но недостаточно для доказательства непересечения и порядка. Нужны адресные диапазоны и последовательность эффектов. Аналогично `StackDelta` не доказывает восстановление после `LD SP,...`; необходима связь с конкретным сохранённым значением.

Происхождение операций должно переживать DSE, renumber и допустимое клонирование. Уже существующий код специально перенумеровывает metadata-only адреса, а inliner отказывается от функций с `SequentialBytes`, чтобы сохранить идентичность callback. Новая оптимизация должна учитывать эти ограничения. [renumber.go:143](../../minzc/pkg/mir2/renumber.go#L143), [inline.go:99](../../minzc/pkg/mir2/inline.go#L99).

На уровне Nanz автор продолжает объявлять `fun`, типизированные указатели, данные и операции. Машинные clobbers выводятся. Явными остаются только факты окружения, которых нет в инструкциях: владение RAM, допустимость перестановки, NMI/reentry и interrupt-контракт. Их следует представлять типизированными библиотечными/компиляторными контрактами; готового синтаксиса таких контрактов просмотренный код ещё не предоставляет.

**Для production-компилятора внешняя Z3 здесь не нужна.**

Первый checker может быть полностью детерминированным:

- сведение адресов к `base + constant` с известной разрядностью;
- проверка соседства, длины и диапазонов;
- проверка типов, доминирования и использования значений;
- анализ пересечений доступных областей;
- конечный анализ состояний SP/INT по CFG;
- проверка машинного рецепта и relocations.

При недостатке доказательств выбирается обычный код. Для исследования можно использовать отдельный SMT-инструмент, но production-путь не должен запускать внешний solver или принимать непроверяемый ответ как основание корректности.

**Native-оракул должен проверять не только итоговый буфер.**

Рекомендуемая матрица:

| Измерение | Обязательные случаи и ожидаемая проверка |
|---|---|
| Направление | Обратные store → PUSH; прямые load → POP; противоположные направления требуют отдельного разрешения |
| Данные | Несимметричные пары, `00/FF`, `12/34`, повторяющиеся и разные слова; выявление перестановки байтов |
| Длина | 0, 1, 2, 3, 8, границы unroll; корректный fallback и отсутствие лишнего чтения хвоста |
| Адреса | Чётные/нечётные начала, переход `xxFF/xx00`, границы RAM; отдельно wrap около `FFFF` |
| Наблюдаемость | Точная последовательность `read/write,address,value`; MMIO и отказ на первом/втором байте |
| Alias | Непересечение, `src=dst`, сдвиги overlap ±1/±2; совпадение с исходным алгоритмом либо отказ кандидату |
| Обычный стек | Разные SP, живые caller values, guard-байты, пересечение с frames; точные PC/SP после возврата |
| SMC | Два разных SP и адреса назначения при повторном использовании одного executable; точные operand bytes |
| ABI/flags | Разные регистровые состояния, банки, флаги, живые половинки пар и возвращаемые значения |
| Управление | Ранний выход, внутренний CALL, injected spill, условный путь мимо DI/restore — ожидаемый отказ |
| INT/NMI | INT до области и после восстановления; HALT до DI; попытка допуска с включёнными INT; NMI как исключённый или отдельно поддержанный сценарий |
| Pipeline | Ordinary/Grace Speed/Grace Size, fusion on/off, формы `PtrAdd`/SMC-index, повторная проверка provenance после renumber |

Для восьмибайтового kernel при входе непосредственно в процедуру разрешены записи только в восемь destination bytes и два байта operand восстановления SP. Setter отдельно меняет два байта адресного operand. Если harness выполняет настоящий CALL, его запись адреса возврата учитывается точно. Широкое исключение «несколько десятков байтов около стека» может скрыть ошибку и здесь не нужно.

Сравнивать следует исходный байтовый алгоритм, оптимизированную VM и реально собранный Z80. Native-трасса должна различать обращения к данным, instruction fetch и служебные записи SMC. Для strict-order случая сравнивается последовательность данных; для разрешённой перестановки — явно выбранный более слабый контракт. Ускорение не требует равенства числа fetch или refresh-R.

Существующие тесты дают хорошую основу: проверяются префиксы доступа и wrap, исходная callback-идентичность, поддельное provenance и сохранность metadata после renumber. [byte_word_fusion_test.go:37](../../minzc/pkg/mir2/byte_word_fusion_test.go#L37), [identity и renumber:246](../../minzc/pkg/mir2/byte_word_fusion_test.go#L246). PUSH-fill тест уже проверяет регистры, IFF, SP и ограниченные области изменяемой RAM. [hardware_push_fill_test.go:25](../../minzc/pkg/pipeline/hardware_push_fill_test.go#L25), [RAM oracle:107](../../minzc/pkg/pipeline/hardware_push_fill_test.go#L107).

Для экранного применения следующим уровнем должен быть Spectrum/ULA-прогон: адреса и конечная RAM не доказывают корректный показанный кадр. Репозиторий уже различает эти проверки. [README.md:46](../../reports/advanced-demos/README.md#L46).

Практический порядок внедрения: сначала восемь обратных непрозрачных константных записей с сохранением порядка, затем повторяющийся fill, затем прямой поток POP из неизменяемой таблицы. Перестановку прямых записей, копирование с overlap и masked sprites стоит допускать отдельными проверяемыми расширениями. Такой путь сохраняет обычный Nanz на поверхности, выводимые эффекты внутри компилятора и конкретное доказательство для каждого выбранного SP-региона.
## Дополнительные измерения текущего compiler

После исследования root выполнил отдельные нативные пробы простых циклов.
Они не выбирают PUSH/POP: это текущие forward/backward алгоритмы на Nanz.

```nanz
fun forward(@smc dst: ^u8) {
    var p: ^u8 = dst
    for i: u8 in 0..2 {
        p^ = 195
        p = p + 1
    }
}

fun backward(@smc dst: ^u8) {
    var p: ^u8 = dst + 2
    for i: u8 in 0..2 {
        p = p - 1
        p^ = 195
    }
}
```

В этих примерах переменная range не используется: проверяется число итераций,
а не её значение. Обе процедуры оставляют `[195,195]`. Словный вариант
записывает два `0x3cc3` с явным byte-шагом 2; Nanz pointer arithmetic здесь
не заменяется предположением о C-масштабировании.

| Одинаковый итоговый fill | Kernel, T | Модуль с setter, B |
|---|---:|---:|
| Прямой, два байта | 131 | 20 |
| Обратный, два байта | 152 | 24 |
| Прямой, два слова | 255 | 30 |
| Обратный, два слова | 292 | 36 |

Ordinary, Grace Speed и Grace Size совпали. 120 нативных случаев:
4 алгоритма × 3 режима × 10 адресов, включая 0xfffd/0xfffe/0xffff.
Проверены вся RAM кроме ограниченного call-frame, setter operands и PC/SP.
ROM-защита отключена, поэтому wrapping-store в адрес 0 действительно исполняется.
INT/NMI/ULA не моделируются. Это доказательство конкретных pure-RAM fills;
наблюдаемая последовательность обращений этой пробой не сравнивается.
Оно не доказывает допустимость перестановки для копирования или MMIO.

Ближайшее решение root: сохранить native Nanz как источник семантики,
добавить ограниченный проверяемый SP-region и допускать сначала непрозрачные
обратные константные byte-stores. После allocation проверять фактические
spill/CALL/flags и выбирать обычный kernel при отсутствии доказательства
или выигрыша. Обобщение copy, POP-потоков и перестановки прямых store —
следующие независимые допуски.
