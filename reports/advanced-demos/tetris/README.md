# Tetris: композиция кадра без промежуточного стирания

14 октября 2026. Первый этап renderer в `feat/advanced-demos`; main и релизные
пакеты пока не обновлены. Это **не завершение плавного пиксельного Tetris**.

Изменён именно [игровой Spectrum Tetris](../../../examples/zx/tetris_playable.nanz),
который собирает `scripts/build_zx_tetris_demo.sh`. CP/M Tetris и исторический
`tetris.nanz` — другие исходники. Предыдущая версия сохранена в
[baseline.nanz](baseline.nanz) как обязательный отрицательный контроль.

## Что теперь происходит

Раньше каждый render сначала выводил 200 клеток неподвижного поля, потом тень и
активную фигуру. Даже если фигура не сдвинулась, поле временно заменяло её цвет
чёрным. Превью также стирались до повторного рисования. Проверка конечной RAM
этого не замечала.

Теперь `compose()` собирает окончательные значения в отдельном буфере. Запечённая
библиотека [hw.scene](../../../stdlib/hw/scene.nanz) сравнивает их с последним
опубликованным изображением и сохраняет очередь изменений. После `HALT` renderer
публикует только эту очередь, в порядке экранных адресов. `shown` обновляется
после каждой фактической записи. Изменение исходного буфера после `prepare`
не меняет уже подготовленный кадр.

```nanz
import hw.scene

@scene("tetris") {
    surface 0x5800 32 24 32
    plane 11 2 10 20  // игровое поле
    plane 23 3 4 4   // следующая фигура
    plane 5 3 4 4    // удержанная фигура
}

fun render() -> void {
    compose()
    tetris_prepare()
    zx_halt()
    tetris_publish()
}
```

Генератор исполняется на compile-time VM и запекает таблицы адресов и порядок
обхода. Эмитированные runtime-процедуры — обычный типизированный Nanz, без ASM.
Это первая общая библиотека композиции owned byte-plane. Поверхность пока
числовая; объектные actors, compile-time интерфейсы и визуальные эффекты ещё
предстоит подключить. Не следует считать этот первый descriptor окончательным DSL.

## Что доказано и сколько стоит

Проверены 12 сценариев renderer: неподвижная/перемещённая фигура O, разные I/O/T
превью, пустой и заполненный hold, неподвижное нижнее поле. Все три режима:
обычная сборка, Grace Size, Grace Speed. Сравниваются все 6912 экранных байта,
вся остальная RAM с разрешением только генерируемых mutable buffers, точных
spill slots и фактически занятой области стека. Проверены неизменность игрового
состояния, return PC/SP, включённые INT и сохранение регистров обработчиком IM2.

Отдельный оракул сравнивает реальные RGBA-пиксели, которые ULA получала во время
исполнения CPU. Повторный `RenderFullScreen` из готовой RAM не используется.
Кадр обязан совпадать с полным предыдущим или полным новым изображением.

| Обычная сборка | Baseline | Композиция |
|---|---:|---:|
| Неполные показанные кадры | 96 / 120 | **0 / 72** |
| Наблюдения промежуточного стирания неизменившихся клеток | 2 017 936 | **0** |
| Максимум render, включая ожидание | 674 519 T | 358 879 T |
| Максимум публикации | не выделена | **9 230 T** |
| Размер полного тестового модуля | 4627 B | 6242 B |

Это размер с игровым кодом и launcher, а не отдельного renderer. Grace Size/Speed
дают 4635 / 6250 B; времена и вывод практически совпадают. Количество наблюдений
стирания — число проверок после CPU-инструкций, когда клетка имела неверный цвет,
а не число отдельных записей.

**Подготовка всё ещё слишком медленная:** до шести видеокадров на один render
при кадре Spectrum 48K 69 888 T. Исчезновение мерцания не означает достижение
50 кадров/с. Следующий этап — избежать полного повторного обхода неизменившегося
поля и ускорить вычисление тени; после этого добавлять пиксельные микрошаги.

Дополнительная короткая матрица библиотеки проходит MIR VM и native Z80:
232 клетки с перемежающимися плоскостями, очередь на 255 клеток, адрес `0xFFFF`,
snapshot до поздней мутации, повторная публикация и пустая очередь неизменившегося
кадра. Неверные размеры, пересечения, выход за поверхность и переполнение очереди
отклоняются при компиляции.

Контракт: обычная owned RAM, disjoint static planes, максимум 255 клеток,
последовательный prepare/publish, начальный cache `shown` совпадает с поверхностью.
В Tetris startup устанавливает нули. Другой renderer не должен писать в эти
owned клетки между публикациями. Библиотека не вводит DI/EI и не подменяет SP;
синхронизацию обеспечивает вызывающий код. Состояние NMI и физическое железо
не проверены.
