# Меньше работы на клетку: обычный Nanz ускоряет bitmap Tetris

14 октября 2026 года, `feat/advanced-demos`.
Продолжение [пиксельного игрового checkpoint](smooth-gameplay.md).

Восстановление bitmap теперь выполняет pointer walk по изменённой полосе.
Экранный адрес вычисляется один раз на полосу; индекс игровой доски и указатель
продвигаются между клетками. Внутри клетки библиотека запекает восемь записей
на расстоянии 256 байт. Всё новое написано типизированным Nanz.

Полное восстановление в тяжёлой проверке сократилось с 403 569 до 183 229 T,
на **54,6%**. Максимальное время renderer вместе с ожиданием и публикацией
сократилось с 749 064 до 539 472 T, на **28,0%**. Это результат на прежних
14 сценах Spectrum 48K, а не оценка ускорения произвольной программы.

## Три изменения и четыре измеренных варианта

| Обычный режим, та же матрица сцен | Максимум восстановления, T | Renderer + ожидание + вывод, T | Смешанные кадры |
|---|---:|---:|---:|
| Исходный цикл по восьми сканлиниям | 403 569 | 749 064 | 0 |
| Развёрнутый Nanz pointer walk внутри клетки | 281 149 | 679 248 | 0 |
| Плюс один lookup клетки и ранняя запись атрибута | 231 659 | 609 288 | 0 |
| Плюс продвижение указателя между клетками | **183 229** | **539 472** | **0** |

Атрибут записывается в частный буфер до вызова заполнения bitmap. Это сокращает
число живых значений через CALL и убирает повторное чтение доски. Публикация
остаётся отдельной операцией после завершения подготовки.

Максимумы разных фаз не обязаны складываться: ожидание HALT привязано к границе
кадра. Поэтому сохранены полные ASM/BIN и все фазовые измерения каждого варианта.
Суммарное время собственного publisher практически не меняется — около 65,8 тысяч T.

Для текущего демо выбран самый быстрый проверенный исходный вариант. Полный модуль
с launcher занимает 32 026 байт вместо 32 012: **+14 байт**. Вариант с ранними
атрибутами занимает 31 978 байт, но готовит поле медленнее; он сохранён вместе с
измерениями. Это явный обмен времени на размер. Grace Size и Speed компилируют
выбранный исходник в 31 153 байта; автоматический выбор этих исходных вариантов
компилятору в этом изменении не добавлялся.

## Как это выглядит в Nanz

```nanz
var index:u8=y*10+x
var p:^u8=ptr(zx_screen_addr(11+x,(2+y)*8)+0xa000)
while x<right {
    pixel_restore_cell(index,p)
    index=index+1
    p=p+1
    x=x+1
}
```

Восстановление клетки читает значение доски один раз:

```nanz
fun pixel_restore_cell(index:u8,p:^u8) {
    let tile:u8=board[index]
    tetris_values[index]=CELL_COLORS[tile]
    var value:u8=0
    if tile!=0 {value=255}
    pixel_band_fill_cell(p,value)
}
```

`pixel_band_fill_cell` из `zx.pixel_bands` содержит восемь обычных Nanz-записей
`p^=value` и семь продвижений `p=p+256`. Пользователь sprite API продолжает
работать с целой формой и координатами. Этот kernel — внутренний строительный
блок восстановления фона, рядом с запечёнными masked sprite-процедурами.

Сгенерированная процедура использует `LD (HL),C` и `ADD HL,DE` с шагом 256;
данные фона приходят в регистре. Данные самой падающей фигуры по-прежнему запечены
в её процедурах. Здесь есть дальнейшая возможность улучшить выбор инструкций
и размещение адресов; глобальная оптимальность кода не заявляется.

Контракт kernel: вызывающий владеет восемью адресами с шагом 256. Для Spectrum
он передаёт первую сканлинию знакоместа; через границу знакомест и третей
переходит внешний расчёт адреса. Общий `DOWN_HL` этим шагом не заменяется.
SP не подменяется, DI/EI в kernel отсутствуют. В Tetris он работает с частной RAM;
тайминг и публикацию по-прежнему обеспечивает renderer.

## Проверки

* `TestZXPixelFillCellNativeVM`: 8 192 случая в каждом из трёх режимов на native
  Z80, сыром и оптимизированном MIR2 VM — **73 728 исполнений**. Все значения
  0..255, восемь строк знакомест, переходы третей, два X, экранная и частная RAM.
  Должны измениться ровно восемь ожидаемых байтов; проверяются вся память и PC/SP.
* Повторная независимая физика Tetris: 1 596 случаев на каждый режим и backend,
  полные игровые состояния, доска и native RAM — PASS.
* Renderer: 14 сцен в каждом режиме, 58 фактически считанных кадров на режим,
  **0 смешанных**; отрицательный контроль продолжает обнаруживать смешанные кадры.
* Настоящий игровой main: 39 последовательных шагов, 24 дробные позы, 10 фиксаций,
  323 завершённых кадра поля в каждом режиме — **969 кадров без смешивания**.
  Game Over возвращает исходный SP; регистры и flags сохраняются через IM2.
* Новый SNA собран, повторно загружен и продолжает падение. Встроенный Tetris
  проходит boot-проверку; графический Linux-кандидат пересобран.

Полный main занимает 385/382/382 аппаратных кадра, включая старт и финальное
мигание. Скрипт управления задаётся по игровым шагам; это дополнительная проверка
работоспособности, а не сравнение двух игр с одинаковыми временными отметками ввода.

Быстрый pipeline — **394/394 PASS**, три процессных шарда и два workers.
Полный каталог — 751 проверка: 394 fast и 357 deep. Полный deep-корпус относится
к релизному этапу; в этом checkpoint запускались указанные глубокие матрицы.

## Артефакты и дальнейший шаг

Все четыре исходных варианта, ASM/BIN, логи и конечный кандидат сохраняются с
SHA256 в `/mnt/safe/minz/grace/2026-10-14/tetris-native-preparation/`.

```sh
/mnt/safe/minz/grace/2026-10-14/tetris-native-preparation/tools/mzx-linux-amd64 --demo tetris
```

Код обычной сборки заканчивается на `0xDD1A`, до bitmap `0xE000..0xF7FF`.
При сборке пересечение проверяется автоматически.

50 FPS пока не достигнуты: для маленьких обновлений размещение sprite-процедур,
прочая подготовка и ожидание остаются существенными. Следующий этап — интеграция
проверенной библиотеки и игрового кандидата в main с соответствующими проверками
и обновление шести платформенных пакетов. Общая цель advanced demos остаётся активной.
