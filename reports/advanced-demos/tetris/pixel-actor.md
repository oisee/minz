# Tetris: целая фигура, запечённые блоки и пиксельные фазы

14 октября 2026. Работа в `feat/advanced-demos`.

В исходнике настоящего Spectrum Tetris появился тип `FallingPose`. Он берёт
геометрию игры, рисует всю фигуру и проверяет положение по пикселям. Публикация
всей фигуры занимает до 3 653 тактов на Z80 в проверенной матрице. Игровой цикл
пока вызывает прежний renderer: это подготовка плавного Tetris, а не объявление
о готовой интерактивной версии.

## Одна форма, четыре независимо размещаемых блока

```nanz
import zx.sprite

@zx_sprite_instances("FallingBlock") {
    instances 4
    size 8 8
    pixels "........"
    pixels ".######."
    pixels ".######."
    pixels ".######."
    pixels ".######."
    pixels ".######."
    pixels ".######."
    pixels "........"
}
```

`#` устанавливает пиксель, `.` сохраняет фон. Здесь тело блока — 6×6 пикселей
в клетке 8×8. Прозрачная окантовка позволяет проверить контакт с соседними
клетками по настоящей геометрии изображения.

Описание пикселей написано один раз. Метафункция создаёт четыре типа и четыре
независимых набора SMC-операндов. Их координаты можно подготовить вместе;
подготовка третьего блока не перезаписывает адреса первого. Генератор написан
на Nanz и эмитирует Nanz, далее работает обычный HIR/MIR/Z80 путь.

Пользовательский потребитель — обычный тип:

```nanz
struct FallingPose {
    kind:u8, rotation:u8, x:u8, y:u8, phase:u8
}

let actor:FallingPose=FallingPose{
    kind:cur_type, rotation:cur_rot,
    x:cur_x, y:cur_y, phase:pixel_phase
}
actor.draw()
```

`x/y` — игровые клеточные координаты; `phase` — смещение вниз на 0–7 пикселей.
Индекс вращения и геометрия берутся из существующих таблиц Tetris. Перевод
в координаты Spectrum, разбиение на четыре блока и экранные адреса находятся
в реализации типа, а не в месте вызова.

## Подготовка до кадра, записи после него

Один `.draw()` остаётся обычным API. Для композиции сцены появились две фазы:

```nanz
actor.stage()   // проверить координаты и запомнить адреса; экран не меняется
// граница кадра и публикация окончательного фона сцены
actor.publish() // только запечённые записи по подготовленным адресам
```

У каждого запечённого типа одно подготовленное размещение. Неверный `stage()`
отменяет готовность; `publish()` без готовности возвращает `false` и не пишет
в экран. Прямой `.draw()` отменяет прежнее подготовленное размещение.
Эта поверхность не добавляет DI/EI автоматически: безопасное время публикации
и запрет одновременного входа из INT остаются контрактом владельца сцены.

У отдельного непрозрачного блока 8×8 публикация занимает **565 T**; у четырёх
маскированных блоков фигуры с общей проверкой готовности — до **3 653 T**.
Вычисление и проверка размещения не бесплатны: у всей фигуры максимум
**48 053 T** в проверенных положениях. Эти затраты вынесены из критической
фазы, но должны войти в итоговый бюджет игровой итерации.

Полный модуль с прежней игрой, её renderer и новым pixel actor занимает
27 294 байта в обычном режиме, 26 420 с Grace Speed/Size. Это цена всей сборки,
а не только новых строк. Выбор SP/PUSH здесь не реализован и не объявлен
оптимальным.

## Контакт и прежняя игровая строка

Тело блока занимает строки 1–6. При фазе 1 нижний пиксель ещё находится
в прежней клетке; при фазе 2 он уже попадает в следующую. Тип проверяет
исходную клеточную позу и дополнительное размещение, когда тело пересекает
границу. Некорректные тип, вращение, координаты и фаза отвергаются до
публикации. Весь actor проверяет готовность четырёх частей перед первой
экранной записью.

Оракул контакта перебирает реальные пиксельные строки тела и сопоставляет их
с заполненными клетками либо нижней стенкой. Он не вызывает Nanz `can_place`
и не использует условие `phase > 1` из реализации.

## Что дала проверка настоящей игры

Первые два блока фигуры I попадали правильно, третий и четвёртый получали
адреса из геометрии других фигур. Найдено копирование байта между spill-слотами:
оно брало A как scratch и затирало живой аргумент следующего CALL.

Исправлен `OpMove`: сохранение выводится из liveness, если byte-spill transfer
использует A, а логические операнды находятся в других местах. При свободном
регистре сохраняется живое значение; при полном занятии используется
ограниченный стек с восстановлением AF. Регрессия проверяет значение,
carry, занятые BC/DE/HL и SP. Изменение полезно всему Z80-backend.

Вложенные метафункции также научились объединять одинаковые импортированные
объявления. Совпадение имени недостаточно: сверяются записанная импортная
область и полное объявление. Обычные дубли сгенерированных функций остаются
ошибкой. Проверены общий импорт функции, глобальной переменной и структуры.

## Проверки и остаток цели

Матрица actor: 28 форм × восемь фаз × два фона × три режима, дополнительно
контакт с заполненным рядом и нижней стенкой. Сравниваются raw/optimized VM
и собранный Z80. Подготовка не меняет экран. Native проверяет все 64 КБ RAM,
точные SMC-операнды и ready-флаги, неизменность игрового состояния, PC/SP;
разрешены только ограниченный рабочий стек и spill-объекты реально вызываемых
функций. [Тест](../../../minzc/pkg/pipeline/tetris_pixel_actor_test.go).

Прежняя проверка целого спрайта на ULA остаётся отдельной: actor пока не
подключён к синхронизированной композиции bitmap и атрибутов Tetris.

Далее нужно:

1. Подготовить окончательный фон для изменившегося следа фигуры. Прежнее поле
   состоит из заполненных bitmap-клеток с цветом в атрибутах; простое наложение
   пиксельного actor на него не даст правильное изображение.
2. Обновлять bitmap и атрибуты вместе, с подтверждённым временем относительно
   луча. Не выполнять полную очистку bitmap каждый кадр.
3. Подключить восьмифазное движение, вращение, hold/drop и фиксацию в игровой
   цикл. Проверить семантику и реально считанные ULA кадры всей анимации.
4. Завершить интеграцию и релиз. Текущий checkpoint не закрывает эту цель.

Артефакты и SHA256: `/mnt/safe/minz/grace/2026-10-14/tetris-pixel-actor/`.

Следующий подготовительный checkpoint: [теневой renderer](shadow-renderer.md).
Игровой main ещё не переключён; новые цифры подготовки и размера приведены
отдельно, чтобы не смешивать их с этим измеренным checkpoint.
