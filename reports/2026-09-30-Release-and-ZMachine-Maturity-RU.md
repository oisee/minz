## Роль `mzv` и точная формулировка задачи

`cmd/mzv/main.go` принимает `.nanz`, `.lizp` и другие исходники, снижает их до MIR2 и вызывает `mir2.NewVM`; это host-программа. Текущий CLI не предлагает Spectrum-исполнитель MIR2 и не заявляет загрузку отдельного сериализованного MIR2-файла. Поэтому «первый слой mzv» означает быстрый запуск **одного Nanz исходника** на MIR2 VM для проверки семантики. Затем тот же core надо скомпилировать в Z80, собрать и исполнить на эмуляторе. Совпадение двух путей выявляет ошибки codegen/ABI, которые один `mzv` пропустит.

Точнее говорить «Nanz-компилятор собирает интерпретатор Z-machine; пакет содержит story Zork I». Zork I уже состоит из Z-code, который интерпретатор читает как данные. Прямое AOT-преобразование всего Z-code в Z80 — другая, гораздо более широкая задача и не требуется для проверки Nanz.

Nanz предпочтительнее Lizp для первого общего core: в примерах уже есть `u8`/`u16`, массивы, структуры и типизированные указатели, то есть конструкции, нужные для декодера и таблиц. Но это пока **гипотеза о пригодности**, а не подтверждение правильной реализации на Z80. Lizp может быть удобен для генерации fixtures или эталонной модели; две независимые production-реализации интерпретатора удвоят объём сравнения. Идиоматичность здесь измеряется тем, что решение использует обычные типы, функции и модули Nanz без asm-патчей на каждый opcode и без скрытой host-логики в core. Тонкие платформенные адаптеры памяти и ввода-вывода допустимы.

## Почему полный Zork не первый тест

По [Z-machine Standard 1.1, §1](https://inform-fiction.ifarchive.org/zmachine/standards/z1point1/sect01.html) v3 story может быть до 128 KiB; память делится на изменяемую dynamic, статическую и high, а v3 packed addresses для процедур/строк умножаются на два. Соседний воспроизводимый build `osg-research/packs/zork/src/zork1-z3.w3mi.data.z3` имеет **86 928 байт**, dynamic до offset 11 288 и high с 20 751; инструкции сборки и SHA-256 `140fc6e4664cfe66928e49dded68f3bea150356d6f3bd6a9690de9390c3f0811` лежат в `/home/alice/dev/osg-research/packs/zork/STORY-BUILD.md`. Другой локальный `cpm-abap/test-games/ZORK1.DAT` имеет 84 992 байта и иные заголовочные адреса; смешивать эти истории в тестах нельзя.

48K Spectrum не вмещает весь story одновременно с интерпретатором, стеком и экраном. 128K страничная память — вероятная первая цель, но и там нужен измеренный layout: fixed RAM для dynamic/интерпретатора/стека и banked reader для остального. `mzx` поддерживает 128K модель и GUI `--load FILE@ADDR:PAGE`; пакет `spectrum/formats` умеет сохранять/читать 128K SNA. Однако текущий `mza -t zxspectrum` документирован как **48K SNA (49 179 байт)**, а headless `mzx --tap` содержит TODO вместо установки tape trap. Способ создать и воспроизводимо запустить законченный 128K `.tap`/`.sna` пока не доказан. Это самостоятельный J4, а не флажок `-f tap` в конце проекта.

Для story брать только проверенный MIT-licensed snapshot исходников. [Microsoft объявила Zork I–III под MIT](https://opensource.microsoft.com/blog/2025/11/20/preserving-code-that-shaped-generations-zork-i-ii-and-iii-go-open-source/); локальный `STORY-BUILD.md` уже документирует rebuild из `historicalsource/zork1` commit `97b7b3d68c075dd9af7da499c3e9690ada3471fd`. В демо включить соответствующий license/notice и воспроизводимый hash, а старый CP/M `.DAT` не переупаковывать без отдельной проверки происхождения. Название Zork не считать лицензией на бренд/оформление.

## Дерево проверки зрелости

```text
J. Nanz Z-machine v3 — необязательный для ближайшего релиза E2E gate
├── J1  Q / P1  Зафиксировать spec, story hash, маленькие test stories, oracle и trace schema
├── J2  F / P1  Nanz core в mzv: header → memory → operands/stack → branches/calls → text/I/O
│   └── gate: ожидаемые PC, память, стек и текст на малых историях; без host opcode helpers
├── J3  F / P1  Тот же core через mz → mza → Z80 execution
│   └── gate: детерминированные трассы совпадают с J2/эталоном; minimised regressions в A4
├── J4  F / P2  ZX 128K memory map, banked story, loader, display/input, упаковка
│   └── gate: проверены page boundaries, RAM budget и boot на mzx/реальном формате
└── J5  E / P2  MIT Zork I: startup → LOOK → короткий scripted transcript
    └── gate: совпадение состояния/вывода, измеренное время, reproducible demo + notices
```

Ключевой тест компилятора — **J3**. Он заставляет пройти реальные 8/16-битные операции, ветвления, вызовы, указатели, массивы, рекурсию/стек и память, сравнивая MIR2 с Z80. J5 прежде всего нагрузочный интеграционный тест компилятора **и** платформенного runtime; сбой полного Zork сам по себе не доказывает ошибку компилятора. При расхождении фиксировать минимальный Nanz repro и слой (frontend, MIR2, codegen, ассемблер, эмулятор, интерпретатор или loader). Число пройденных opcode без state/output comparison не считать процентом зрелости.

Рекомендуемый порядок: сейчас J1 как quick win; J2 после чистого corpus baseline A3 и явной Nanz support matrix C3; J3 вместе с A4; J4 после работающих малых историй на Z80; J5 в конце. Ближайший correctness release D5 не зависит от J4/J5. Если J2/J3 выявят системные компиляторные дефекты, именно минимальные регрессии становятся P0/P1, а Zork остаётся диагностическим сценарием. Артефакт `zvm-zx` добавлять в релиз только при выполненном J5, отдельно от `mzv`.
