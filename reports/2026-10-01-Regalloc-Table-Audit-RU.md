### Уточнение о порядке IX-6v

Повторная проверка `z80-optimizer/cmd/gen6v-ix-feed/main.go` показала, что feed для `ix_expanded_6v_dense.bin` создавался параллельными worker'ами: задания идут по `(mask, widthCombo)`, но готовые строки складываются в общий `outCh` и пишутся в порядке завершения. GPU server сохраняет порядок **полученных** строк, а `build-ix-table` записывает результаты последовательно, без ключа формы. Логи подтверждают два диапазона масок `[0,281)` и `[281,562)` по 149 334 921 записей; отдельного manifest/order-index рядом с файлами не найдено. Поэтому даже формула для плотного подмножества не адресует надёжно **этот** бинарник; порядок worker'ов не восстанавливается из заголовка или строк результата (`cost`, `assignment`, `searchSpace`, `feasible`).

Надёжный путь: заново построить таблицу с сохранением ID формы в каждой записи (или строго упорядоченным single-worker feed), зафиксировать версию/хэш перечислителя и проверить случайные индексы независимым solver. Более ранняя `enriched_6v_dense.enr` — отдельный формат и пространство loc sets; её происхождение и порядок требуют своей проверки, она не является drop-in заменой IX-6v.

## Что исправлено

- `RegAllocTable.Size()` теперь учитывает записи загруженных бинарных таблиц. Раньше бинарная таблица без JSON выглядела пустой, поэтому VIR обходил lookup.
- ENRT 4v автоматически находится по `.enr` в соседнем `z80-optimizer`; `VIR_REGALLOC_BINARY=/path/to/table` разрешает явную загрузку другого полного бинарного файла.
- Большие 5v/6v таблицы больше не загружаются неявно при первом вызове `GetRegAllocTable()`: текущий reader разворачивает их целиком и требует существенно больше памяти, чем размер файлов. Для 5v это осознанный opt-in; 6v dense отклоняется, пока нет его собственного индексатора.
- Z80T v2 reader проверяет заголовок, полное число индексируемых shapes, длину и число записей, а также `nVregs` каждой записи. Неполная/повреждённая таблица не может тихо выдать аллокацию по неправильному индексу.

Это путь экспериментального VIR offline oracle. Основной MIR2→Z80 путь по-прежнему использует PFCCO для контрактов и PBQP для физических регистров; эти бинарные таблицы автоматически не влияют на production codegen. Host intrinsic `regalloc_lookup` в `mzv` обращается к JSON-ключам (`LookupByKey`), не к бинарному индексу.

## Дальнейший трек

1. **[Фундамент]** Для 5v сделать ограниченный по памяти индекс или потоковый oracle и прогнать выборку форм против независимого solver; после этого измерить реальные hit rate и цену/легальность в VIR.
2. **[Фундамент]** Пересобрать IX-6v с сохранёнными shape ID или детерминированным порядком, создать dense-индекс, сверить случайные записи с независимым solver и только тогда подключать lookup. Текущий параллельно созданный файл не имеет восстановимого из его формата порядка.
3. **[Фундамент]** Добавить проверку аллокации против loc-set, alias/interference, ABI и clobber для каждого табличного попадания перед эмиссией.
