# Регистр с двумя определениями

*`factorial(7)` вернул 1456 вместо 5040. Ошибка сидела не в умножении и не в цикле, а в предположении, которое было верным, пока его не сломал другой проход: «у регистра одно определение». Глава о том, как одно доказательство смотрело только на первое определение, и как после этого пришлось проверить все места, которые думали так же.*

> **Статус на 25 ноября 2026.** **В main:** [PR #309](https://github.com/oisee/minz/pull/309) (`3859f45d9`), [PR #310](https://github.com/oisee/minz/pull/310) (`650acadcf`) и [PR #311](https://github.com/oisee/minz/pull/311) (`eb6a58b8e`), все смержены 15 ноября. Листинг «после» получен компилятором из дерева `9daf7a8ba`. Листинг «до» — тем же исходником компилятора, собранным из родителя #309 (`c955ebc45`, через `git archive`). Команды — в [`examples/run.sh`](examples/run.sh).

## Программа

```nanz
fun factorial(n: u8) -> u16 {
    var acc: u16 = 1
    var i: u8 = 0
    while i < n {
        acc = acc * ((i + 1) as u16)
        i = i + 1
    }
    return acc
}
assert factorial(7) == 5040 via z80
```

Компилятор из родителя #309 на этом файле останавливается с ошибкой проверки:

```
Error: HIR compile: line 10: assert "assert factorial(7) == 5040 via z80" [z80]: got 1456, want 5040
```

MIR VM считает правильно. Ошибается только код Z80.

`1456 = 208 × 7`. А 208 — это `0xD0`, младший байт `6! = 720 = 0x02D0`. На последней итерации умножение взяло от аккумулятора только младший байт.

## Откуда у регистра два определения

В MIR2 цикл записан как блоки с параметрами. Заголовок цикла получает `acc` и `i` как параметры блока, а входной блок и тело цикла передают в них значения. Сразу после построения это SSA: у каждого регистра одно определение.

Перед размещением регистров работает проход `PreallocCoalesce`. Он склеивает параметр блока с аргументами, которые в него приходят, чтобы на переходе не нужны были копии. После него аккумулятор — **один регистр с двумя определениями**: `const 1` во входном блоке и `mul` в теле цикла. Так устроен тест из PR, который строит эту форму вручную:

```
@entry:           %acc = const <init> ; %i = const 0 ; jmp @head(%acc, %i)
@head(%acc, %i):  br_if %i < %n, @body(), @exit(%acc)
@body:            %e = ext %k ; %acc = <op> %acc, %e   (or %e, %acc)
                  %i = %i + 1 ; jmp @head(%acc, %i)
```

*Из комментария к `multiDefAccumulatorLoop` в `pkg/mir2/range_proof_multidef_test.go`.*

## Доказательство, которое смотрело на первое определение

У кодогенератора есть два вопроса о регистре, от которых зависит, каким будет умножение и деление: `provablyBelow256` («старший байт точно ноль?») и `nonNegative` («точно не отрицательное?»). До #309 оба отвечали по первой определяющей инструкции, найденной в просмотре функции. Для аккумулятора это константа 1. Ответ: «меньше 256». Значит, слово можно умножать как байт.

Вот что получилось из тела цикла (скоростной профиль по умолчанию, компилятор из `c955ebc45`):

```z80
.factorial_loop_body2:
    LD A, D
    INC A
    LD IXL, A
    LD IXH, 0
    ; mul16 HL * IX → HL (quarter-square __qsq)
    PUSH AF
    PUSH DE
    PUSH BC
    LD A, L
    LD C, IXL
    LD B, A
    ADD A, C
    ...
```

Аккумулятор живёт в HL, множитель `i + 1` — в IX. Умножение идёт через таблицу четвертей квадратов `__qsq` (511 слов, F4b, [#281](https://github.com/oisee/minz/pull/281)) и берёт от HL только `L`. Пока множимое помещается в байт, ответ верен: `6! = 120 × 6 = 720` ещё правильно, произведение двух байтов таблица даёт целиком. На следующей итерации множимое — `720 = 0x02D0`, умножение видит только `0xD0`, и `7!` превращается в `208 × 7`.

В размерном профиле путь другой — цикл умножения на 8 итераций вместо 16, — но ошибка та же: восемь итераций хватает, только если множимое меньше 256.

Второе следствие того же дефекта — деление. `genDivMod` превращал знаковое деление на степень двойки в беззнаковый сдвиг, если делимое «начинается неотрицательным». У аккумулятора, который стартует с неотрицательной константы и уменьшается в цикле, это неверно: в рукописном MIR `-1 / 4` давало 16383. Автор PR пишет, что вызвать этот случай из исходника на Nanz ему не удалось.

## Исправление: каждое определение

Новая функция `provenForEveryDefinition` в `pkg/mir2/z80codegen_muldiv.go` задаёт правило: утверждение о регистре верно, только если ему удовлетворяет **каждое** определение. Определения бывают трёх видов: результаты инструкций, параметры функции и регистры, которые передаются в параметр блока, являющийся этим регистром. Определение без своей инструкции — счётчик DJNZ, дополнительный результат вызова, выход ассемблерной вставки — не доказывает ничего.

```go
// provenForEveryDefinition reports whether r has a definition and every one of
// them satisfies the proof. Pre-allocation coalescing merges a block parameter
// with the arguments that feed it, so one register can carry several
// definitions — a loop accumulator is both its initial constant and its
// update — and a fact about the register must hold for all of them.
```

Регистр, у которого все определения — байты, доказательство сохраняет. Быстрые пути остаются там, где они верны.

То же тело цикла после исправления, дерево `9daf7a8ba`:

```z80
.factorial_loop_body2:
    LD A, D
    INC A
    LD IXL, A
    LD IXH, 0
    ; mul16 HL * IX → HL  (8-iter shift-and-add)
    PUSH AF
    PUSH DE
    LD A, IXL
    PUSH BC
    LD D, H
    LD E, L
    LD H, 0
    LD L, 0
    LD B, 8
.factorial_m16_11_lp:
    SRL A
    JRS NC, .factorial_m16_11_sk
    ADD HL, DE
.factorial_m16_11_sk:
    SLA E
    RL D
    DJNZ .factorial_m16_11_lp
    POP BC
    POP DE
    POP AF
```

Восемь итераций по-прежнему есть, но теперь по праву: байтом доказан множитель `(i + 1) as u16` — это `ext` от байта. Аккумулятор целиком, оба байта, идёт в DE как множимое. Таблица `__qsq` из программы исчезла, и файл `.a80` стал 51 строкой вместо 129.

## Тесты

Все тесты PR падают без исправления. Сквозной тест в `pkg/nanz/loop_accumulator_product_test.go` гоняет факториал через весь компилятор — сырой MIR VM, оптимизированный MIR VM и Z80:

```go
assert factorial(0) == 1
assert factorial(5) == 120
assert factorial(6) == 720
assert factorial(7) == 5040
assert factorial(8) == 40320
```

`TestRangeProofsRequireEveryDefinition` проверяет сами предикаты на склеенных регистрах:

```go
if g.provablyBelow256(acc, 16, map[Reg]bool{}) {
    t.Fatal("an accumulator updated by a multiply was proven below 256 from its initial constant")
}
...
// One unproven value on one edge is enough to lose it.
altJmp.Args[0] = wide
if g.provablyBelow256(r, 16, map[Reg]bool{}) || g.nonNegative(r, 16, map[Reg]bool{}) {
    t.Fatal("a word passed into the parameter on one edge was ignored")
}
```

`TestMul16MultiDefAccumulatorNative` запускает выданное умножение в эмуляторе: 5 размещений регистров × порядок операндов × скорость/размер, по 42 пары операндов на каждое.

В ходе ревью нашлись ещё две ошибки той же породы, обе исправлены в этом же PR:

- **Знаковое расширение.** `provablyBelow256` принимал `sext` байта, если источник неотрицателен *в ширине умножения*. Но беззнаковый байт 200 неотрицателен как слово и отрицателен как знаковый байт, поэтому его расширение — `0xFFC8`. Тест `TestWordCounterAndSextByteMultiplyAsWords`: `sextmul(200, 3)` возвращал 600 вместо −168.
- **Шаг DJNZ.** Peephole заменял «счётчик − шаг» на декремент, если находил *какую-нибудь* загрузку константы 1 в регистр шага. После склейки такой регистр может быть 1 на одном пути и другим значением на остальных. В рукописном тесте `dj(x=5, k=2, c0=6)` делал шесть итераций вместо трёх. Из исходников корпуса это не достигается: аллокатор не держал обновление счётчика в B для этой формы.

Почему этого не поймал fuzz? В описании PR сказано прямо: генератор direct-call fuzz такую форму цикла не порождает. С исправлением fuzz прошёл 3000/3000 и 1000/1000 знаковых. Падал на этой ошибке ночной тест `TestOriginalLizpLanzFamilyState` — `examples/lizp/factorial.lizp`. Теперь он проходит.

## Все, кто думал так же

После #309 стало понятно, что «одно определение на регистр» — предположение, которое `PreallocCoalesce` тихо отменяет для всего, что работает после него. Следующие два PR — аудит таких мест.

**#310, анализы CP/M runtime.** Три анализа среды CP/M читали карту `defs map[Reg]*Inst`, в которой побеждает последнее определение. `cpmGlobalStoreRoots` останавливался на регистре с `addr_of` и не смотрел, что ещё приходит в тот же регистр как параметр блока: указатель, который на входе в цикл `&ga`, а потом `&gb`, охранялся только для `ga`. `cpmLocalAddresses` брал смещение `ptr_add` из последней константы регистра: при 200 на одной ветке и 1 на другой запись на 200 байт за 4-байтовым локальным массивом признавалась допустимой. Исправление — одно описание определений функции (`cpm_runtime_defs.go`); «этот указатель — ровно этот `addr_of`» выводится только из единственного определения. По описанию PR, ни один из трёх случаев сегодня не достигается из фронтендов. Шесть новых тестов падают на старых файлах анализа.

**#311, свёртки в одном блоке.** Две свёртки кодогенератора — прямой доступ к глобальной переменной вместо адреса и слияние `load / or / store` в `SET n,(HL)` — пропускают вычисление промежуточного значения, если у него один читатель. Читателей считали внутри блока. Но регистр, определённый в блоке, можно читать и в любом блоке, который он доминирует. Тогда второй читатель в другом блоке получал регистр, в который никто не писал: в примере из PR `LD (HL), 119` пишет через HL, который не загружался. Теперь после подсчёта в блоке оба прохода поднимают счётчик до числа читателей во всей функции. Нашёл это критик #310. На корпусе — 372 исходника, которые компилируются, — выход побайтно совпал с main: ни одна программа корпуса на эту ошибку не попадала.

## Что из этого следует

Сама ошибка — несколько строк: «найди определение, посмотри на него». Она была верна, пока регистры были SSA. Проход, который сделал их не-SSA, появился позже и ради другой цели — убрать копии на переходах. Никто не нарушил ничьих правил. Правило просто не было записано.

Теперь оно записано в виде функции, которую вызывают все доказательства: `provenForEveryDefinition` используется, в частности, в `provablyBelow256`, `nonNegative` и в проверке шага DJNZ (`z80codegen_term.go`). А для CP/M — отдельным описанием определений, которое знает про параметры блоков. В следующий раз вопрос «а сколько у этого регистра определений?» будет иметь один ответ на весь кодогенератор, а не по ответу на каждый проход.
