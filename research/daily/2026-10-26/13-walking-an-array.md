# Пройти массив указателем

*Программист на C пишет `values[i]` и `i++`. Программист на ассемблере Z80 держит адрес в HL и пишет `INC HL`, а счётчик держит в B и пишет `DJNZ`. Два PR ноября учат MinZ второму способу: сначала дешевле считать адрес, потом не считать его вовсе.*

> **Статус на 25 ноября 2026.** **В main:** [PR #315](https://github.com/oisee/minz/pull/315) «ptr_add forms without the HL funnel» (`c012b0db1`) и [PR #317](https://github.com/oisee/minz/pull/317) «pointer walks with a down-counter» (`6fd07f8a9`), оба смержены 16 ноября. Листинги получены компиляторами, собранными из этого репозитория: родитель #315 (`e8bd6f020`), родитель #317 (`717b56ce4`, в нём уже есть #315) и текущее дерево `9daf7a8ba`. Такты в комментариях листингов — флаг компилятора `--annotate-tstates`. Повторить: `sh research/daily/2026-10-26/examples/run.sh <каталог>`. Такты целых бенчмарков — из [`reports/c89-benchmark-2026-11-25/`](../../../reports/c89-benchmark-2026-11-25/README.md) и из описаний PR, это сказано рядом с каждым числом.

## Воронка через HL

В MIR2 адрес элемента — инструкция `ptr_add base, offset`. На Z80 сложить два 16-битных числа можно почти только одним способом: `ADD HL, rr`. До #315 общий путь кодогенератора так и делал: база в HL, смещение в DE или BC, сложение, результат куда надо. Если в HL или в паре для смещения жило что-то нужное, его приходилось сохранять на стеке.

Вот кейс `checksum16` из heldout-набора бенчмарка:

```c
unsigned char values[256], n;
unsigned short result;
void execute(void) {
    unsigned short i = 0, sum = 0, word, next;
    while (i < n) {
        word = (unsigned short)values[i] << 8;
        i++;
        if (i < n) { word |= values[i]; i++; }
        next = sum + word;
        if (next < sum) next++;
        sum = next;
    }
    result = sum;
}
```

Индекс `i` живёт в HL, в DE — ещё одно живое слово. Адрес `values + i` до #315:

```z80
.execute_loop_body2:
    LD BC, values                       ; 10T
    PUSH HL                             ; 11T
    PUSH DE                             ; 11T
    LD D, H                             ; 4T
    LD E, L                             ; 4T
    LD L, C                             ; 4T
    LD H, B                             ; 4T
    ADD HL, DE                          ; 11T
    LD C, L                             ; 4T
    LD B, H                             ; 4T
    POP DE                              ; 10T
    POP HL                              ; 10T
    LD A, (BC)                          ; 7T
```

87 тактов на адрес до `LD A, (BC)`. Сложение — одна инструкция `ADD HL, DE` за 11 тактов. Остальное — перекладывание, чтобы освободить HL и потом вернуть.

## Формы без воронки

#315 добавил в `pkg/mir2/z80codegen_ptradd.go` несколько форм:

- смещение уже в HL, база в BC или DE: просто `ADD HL, base` — сложение коммутативно;
- база — константа (`addr_of` глобальной переменной): `LD HL, sym / ADD HL, off` или `LD rr, sym / ADD HL, rr` через свободную пару;
- сумма нужна в DE, и один операнд в DE умирает: `EX DE, HL / ADD HL, rr / EX DE, HL` — 3 байта, 19 тактов, HL не меняется;
- в остальных случаях, когда HL занят или участвует индексный регистр, сумма собирается побайтно через A и пишется сразу в нужную пару. Живой A на это время переезжает в свободный байтовый регистр.

Кроме того, `addr_of`, который используется только как база `ptr_add`, больше не грузится в регистр, а `add i, k`, питающий такой `ptr_add`, сворачивается в непосредственный операнд `sym+k`.

Тот же адрес после #315 (компилятор из `717b56ce4`):

```z80
.execute_loop_body2:
    ; ptr_add: byte-wise through A
    LD A, L                             ; 4T
    ADD A, values^L                     ; 7T
    LD C, A                             ; 4T
    LD A, H                             ; 4T
    ADC A, values^H                     ; 7T
    LD B, A                             ; 4T
    LD A, (BC)                          ; 7T
```

30 тактов вместо 87. HL и DE остаются на месте, стек не трогается.

Вторая часть #315 — расширение байта до слова. `(unsigned short)values[i]` в MIR — это `ext` байта в слово с нулевым старшим байтом. Если такое значение читает одна инструкция — сравнение, `shl 8`, `or` или сложение «слово + байт», — теперь она читает байт напрямую. В заголовке цикла `checksum16` было:

```z80
    LD A, (n)
    LD C, A
    LD B, 0
    LD A, L
    SUB C
    LD A, H
    SBC A, B
```

стало:

```z80
    LD BC, n
    LD A, (BC)
    LD C, A
    ; zero-extension fused into its consumer
    LD A, L
    SUB C
    LD A, H
    SBC A, 0
```

По описанию PR, `checksum16` в профиле по умолчанию стал 26021176 тактов вместо 44121656 (−41 %). В прогоне 25 ноября у него те же 26021176, а у SDCC 4.6 в скоростном профиле — 23303736: этот кейс MinZ всё ещё проигрывает (`tables.md`, строка `checksum16`). Из 106 строк бенчмарка #315 ускорил или уменьшил 25, замедлил 0.

## Не считать адрес вовсе

Даже 30 тактов на адрес — это много, если адрес на каждой итерации просто на единицу больше предыдущего. Возьмём другой heldout-кейс, `find_max`:

```c
unsigned char values[256], n;
unsigned short result;
void execute(void) {
    unsigned char i, maximum = 0;
    for (i = 0; i < n; i++) {
        if (values[i] > maximum) maximum = values[i];
    }
    result = maximum;
}
```

Размерный профиль (`--Osize`), компилятор из `717b56ce4`, то есть уже с формами #315:

```z80
.execute_loop_head1:
    LD HL, n                            ; 10T
    LD D, (HL)                          ; 7T
    LD A, B                             ; 4T
    CP D                                ; 4T
    JRS NC, .execute_loop_exit3         ; 12T/7T
.execute_loop_body2:
    LD E, B                             ; 4T
    LD D, 0                             ; 7T
    ; ptr_add: constant base
    LD HL, values                       ; 10T
    ADD HL, DE                          ; 11T
    LD D, (HL)                          ; 7T
    LD A, C                             ; 4T
    CP D                                ; 4T
    JRS NC, .execute_if_join5           ; 12T/7T
.execute_if_then4:
    LD E, B                             ; 4T
    LD D, 0                             ; 7T
    ; ptr_add: constant base
    LD HL, values                       ; 10T
    ADD HL, DE                          ; 11T
    LD C, (HL)                          ; 7T
.execute_if_join5:
    INC B                               ; 4T
    JRS .execute_loop_head1             ; 12T
```

На каждой итерации: прочитать `n` из памяти, сравнить с `i`, посчитать `values + i`, а если максимум меняется — посчитать его ещё раз. По аннотациям это 107 тактов на элемент, когда максимум не меняется (32 + 59 + 16), и 141, когда меняется.

После #317 (`9daf7a8ba`; код в слиянии #317 `6fd07f8a9` побайтно тот же):

```z80
execute:
    LD C, 0                             ; 7T
    LD D, 0                             ; 7T
    LD E, D                             ; 4T
    LD D, 0                             ; 7T
    ; ptr_add: constant base
    LD HL, values                       ; 10T
    ADD HL, DE                          ; 11T
    LD DE, n                            ; 10T
    LD A, (DE)                          ; 7T
    LD D, A                             ; 4T
    LD B, D                             ; 4T
.execute_loop_head1:
    LD A, B                             ; 4T
    AND A                               ; 4T
    JRS Z, .execute_loop_exit3          ; 12T/7T
.execute_loop_body2:
    LD D, (HL)                          ; 7T
    LD A, C                             ; 4T
    CP D                                ; 4T
    JRS NC, .execute_if_join5           ; 12T/7T
.execute_if_then4:
    LD C, (HL)                          ; 7T
.execute_if_join5:
    INC HL                              ; 6T
    DJNZ .execute_loop_body2            ; 13T/8T
```

Адрес считается один раз до цикла. В цикле — `LD D, (HL)`, сравнение, `INC HL` и `DJNZ`. Индекса `i` больше нет: его роль играет обратный счётчик в B, который начинается с `n`. Проверка `n == 0` выполняется один раз, при входе. По аннотациям — 46 тактов на элемент, если максимум не меняется (27 + 19), и 48, если меняется.

На всём бенчмарке, по описанию PR #317, `find_max` в размерном профиле стал 7670836 тактов вместо 17706402 (−56.7 %). Прогон 25 ноября даёт те же 7670836; SDCC 4.6 в размерном профиле — 16265727.

Пролог при этом не идеален: `LD D, 0 / LD E, D / LD D, 0` грузит ноль в D дважды. Это видно в выводе; в описании PR об этом ничего нет.

## Когда это разрешено

Превращение индексного цикла в обход указателем с обратным счётчиком — в двух файлах.

`affine_pointer_walk.go` находит аффинные адреса `base + scale·i + offset` в телах циклов, теперь и в телах из нескольких блоков (`if` внутри цикла — это уже несколько блоков). Два адреса делят один указатель, только если у них совпадают база, масштаб и смещение. В `find_max` оба чтения `values[i]` — один и тот же адрес, поэтому оба читают `(HL)`.

`affine_counter.go` заменяет индекс обратным счётчиком. Условия: беззнаковое сравнение `cmp.ult i, bound` в ширине индекса, старт с константы 0 и шаг 1. Только тогда `i < bound` — это ровно `bound − i ≠ 0`. Индекс оставляют, если после цикла читается что-то, вычисленное из него. Загрузку границы, которая не меняется в цикле, выносят из цикла, только если это обычная неvolatile глобальная переменная, а цикл ничего не пишет в память.

И третье условие — **давление на регистры** (`affinePointerProfitable`). Обход отказывается, если состояние, которое он оставляет, не помещается в HL, DE, BC и один байт в A. Бюджет — 7 байт: пары, временное слово, счётчик и нужные байтовые параметры. 16-битный параметр заголовка, который нужен и происходит из константы или адреса, считается парой. Без этого гейта на корпусе выросли 5 файлов (plasma_simple +61 байт, plasma_shadow +52, tetris_playable +31, irc_client +3, life_simple +2). С ним три из них вернулись к прежнему размеру.

## Что из этого следует

По описанию #317, лоуеринг итераторов Nanz уже даёт именно такую форму — указатель и обратный счётчик. #317 приводит к ней обычный C-цикл с индексом, тот самый, который пишут все. В прогоне 25 ноября на `fusion_fold_max` C через MinZ — 319439 тактов, идиоматичный Nanz — 309678. Но не везде так: `fusion_two_ptr_xor` из C — 1517785 тактов, из идиоматичного Nanz — 626115, у SDCC — 928050. Почему C-версия этого кейса так отстаёт, ни один из двух PR не разбирает; это открытый вопрос, а не результат этой главы.
