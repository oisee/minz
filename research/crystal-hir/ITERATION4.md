# Итерация 4: macro/meta и records в одном модуле

Теперь record path использует тот же Nanz meta generator, что и scalar/Lanz
spike. Код генераторов вынесен в `minzc/internal/crystalmeta`; CLI
`crystal-meta-bridge repeat COUNT DELTA` сохраняет прежний JSON protocol.
Nanz HIR builder, HIR/MIR2 и Z80 backend не менялись.

Проверяемый исходник: [meta_arena_showcase.cr](meta_arena_showcase.cr).

```crystal
p = arena.alloc(3_u16)
p[0_u16] = meta_repeat(seed, 3_u8, 7_u8)
arena.set_marker(p[0_u16])
meta_byte(arena, "marker") ^ seed
```

## Откуда берётся layout

Macro `meta_byte` раскрывается в явный marker
`minz_meta_layout_byte(pointerof(record), "marker")`. Exporter сохраняет
идентичность локальной структуры и имя поля; host offset/sizeof в wire не входят.
Go importer сначала создаёт MIR2 target types, затем вычисляет `ByteOffset`,
`ByteWidth(struct)` и `ByteWidth(pointer)`.

Эти три числа поступают в настоящую Nanz meta-функцию `@layout_byte` как
compile-time аргументы. Она запускается на meta VM и генерирует HIR byte load
по `base + offset`; target получает обычный helper без meta runtime и GC.
Размер/границы и ширина указателя проверяются до генерации; meta также проверяет
диапазон offset и Z80 pointer width. Адрес структуры не возвращается из helper.

| Представление | sizeof MetaArena | Pointer | marker offset |
|---|---:|---:|---:|
| native host Crystal | 24 | 8 | 20 |
| Z80 | 8 | 2 | 7 |

MetaArena здесь содержит дополнительное байтовое поле marker, поэтому её размер
отличается от 7-byte ByteArena итерации 3. В том же модуле HeaderProbe имеет
размер 3 и marker offset 0 на target. Cache lookup учитывает record identity и
field; одинаковые byte-reader helpers могут разделяться, когда size/offset
совпадают. Receipts сохраняются для каждой пары record/field.

Нативный fallback marker читает getter `marker`. Поэтому Crystal exporter v1
явно допускает только это поле, literal field name и `pointerof` локальной
структуры. Это проверка архитектуры моста, а не универсальная reflection API.
Go генератор отдельно проверяет существование и u8 тип поля. Динамические имена,
другие поля на Crystal входе и pointer expressions вместо локальной структуры
не обещаются. Полноценного MetaContext, typed quotes или lifetime analysis пока нет.

## Проверки

```sh
python3 research/crystal-hir/verify_meta_records.py
```

**768 наборов входов = 3 сценария × 256 byte seed values**, каждый исполняется
на native Crystal, raw MIR2, optimized MIR2 и Z80:

1. Выделение arena memory, meta-generated repeat с wrapping арифметикой,
   запись в buffer, перенос в marker и meta-generated byte read.
2. Копирование структуры, изменение marker оригинала, независимое чтение старого
   и нового значений. Это проверяет передачу адреса конкретного экземпляра.
3. Одноимённое поле двух структур с target offsets 7 и 0. Это проверяет, что
   specialization cache не подменяет layout одной структуры другой.

7 отрицательных контролей: неизвестное поле, u16 поле вместо u8, неизвестный
record ID, repeat count за пределами 0..32, динамическое имя поля, не-record
receiver и другое поле на Crystal входе. Отказы проверяются по диагностике,
а не только по ненулевому exit status.

Число случаев — размер корпуса, не количество поддержанных конструкций языка.
Receipts и layout: `evidence/iteration4-*`. Runtime artifacts:
`/tmp/minz-crystal-meta-record-results`.

Следующий шаг — заменить специальные marker/getter соглашения общим API
MetaContext с typed record handles, source lineage и target layout queries.
